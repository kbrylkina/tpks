% Общий глоссарий. В каждой группе термины расположены по алфавиту.
% Термины процесса. Слайды — материалы Козырева; К — строки конспекта лекций.
\term{Базовая версия}{утверждённая версия единицы конфигурации, служащая основой последующей работы. Промежуточные версии базовыми не считаются (источник: слайды 32, 75--76).}
\term{Валидация}{проверка того, что требования к системе соответствуют потребностям, ради которых её создают (источник: конспект, К:106; наша формулировка).}
\term{Верификация}{проверка соответствия результатов работы её исходным данным и установленным требованиям (источник: конспект, К:97, 161; наша формулировка).}
\term{ВУ}{высокий уровень требований: требования к поведению и свойствам ПО, полученные из системных требований и интерфейсов (источник: слайды 17--21, 38).}
\term{ГУИ}{группа управления изменениями: постоянная часть совета по управлению изменениями (источник: слайд 71).}
\term{ЕК}{единица конфигурации: данные жизненного цикла ПО, рассматриваемые при управлении конфигурацией как одно целое и определяемые уникальным именем и версией (источник: слайды 52--53).}
\term{ЖЦ ПО}{жизненный цикл ПО: совокупность процессов, через которые ПО проходит при создании и использовании (источник: конспект, К:19--27, 132; наша формулировка).}
\term{ЗИ}{запрос на изменение: описание планируемого изменения одной ЕК, порождённое утверждённым сообщением о проблеме (источник: слайды 73--74).}
\term{Интеграция}{процесс получения исполняемого объектного кода из результатов кодирования и его загрузки в целевую вычислительную среду (источник: конспект, К:484--497).}
\term{КК1}{категория контроля данных, для которой изменение после создания базовой версии выполняется через запрос на изменение (источник: конспект, К:16, 61).}
\term{КК2}{категория контроля данных с менее строгим набором мероприятий, чем КК1; конкретный порядок задаёт План управления конфигурацией ПО (источник: конспект, К:16, 61, 639; наша формулировка).}
\term{КТ-178}{русскоязычный стандарт о разработке бортового ПО, соответствующий DO-178; используется в курсе как методическая основа (источник: гайд старших курсов, раздел «Сокращения»).}
\term{НУ}{низкий уровень требований: требования к компонентам ПО, получаемые при проектировании и используемые при кодировании (источник: слайды 28, 38; конспект, К:71).}
\term{ПО}{программное обеспечение: программы и связанные с ними данные, предназначенные для выполнения задач вычислительной системой (источник: наше определение; сокращение из гайда старших курсов).}
\term{Производное требование}{требование, полученное при разработке требований или проектировании и не имеющее прямого родительского требования на уровне выше; его происхождение требует обоснования (источник: слайд 21; конспект, К:66).}
\term{Системное требование}{проверяемое утверждение о поведении или свойствах системы в целом (источник: слайды 4, 17; наша формулировка).}
\term{СКУ}{система конфигурационного управления: средства учёта версий, изменений и совместной работы с данными проекта (источник: слайд 85).}
\term{СП}{сообщение о проблеме: запись об одном несоответствии результатов исходным данным, данных стандартам или процессов планам (источник: слайды 64--66).}
\term{СПТ}{спецификация программных требований: документ с требованиями к ПО, его входам, выходам, режимам и внешнему взаимодействию (источник: слайды 18--21; сокращение из гайда старших курсов).}
\term{Трассируемость}{возможность проследить связи требования с его источниками, последующими требованиями и проверками (источник: слайды 7, 21, 36, 78).}
\term{УК ПО}{управление конфигурацией ПО: учёт состава, версий и изменений данных жизненного цикла для сохранения целостности ПО (источник: слайды 49, 89).}
\term{ФИ}{формальная инспекция: рассмотрение объекта по установленной процедуре с регистрацией обнаруженных несоответствий (источник: конспект, К:197--202, 258; наша формулировка).}

% Термины предметной области. Определения команды по notes/04, часть Б.
\term{Авторизация}{проверка разрешения на действие по ролям пользователя и ограничениям конкретной операции (источник: наше определение).}
\term{Аутентификация}{подтверждение личности пользователя при входе (источник: наше определение).}
\term{Версия компонента}{зарегистрированный результат сборки компонента с номером, уникальным в пределах этого компонента (источник: наше определение).}
\term{Внешняя система развёртывания}{система, которой разрабатываемая система передаёт задания на установку, автоматические проверки и откат и от которой получает результаты (источник: наше определение).}
\term{Внешняя система сборки}{система, которая получает дистрибутив компонента из исходного кода и передаёт сведения о сборке разрабатываемой системе (источник: наше определение).}
\term{Внешняя система учёта задач}{система со сведениями о задачах и дефектах, связанных с версиями компонентов (источник: наше определение).}
\term{Внешняя служба аутентификации}{служба, которая проверяет учётные данные и сообщает результат проверки личности пользователя (источник: наше определение).}
\term{Внешняя служба доставки сообщений}{служба передачи уведомлений пользователям; в версии 1 рассматривается как резервное расширение (источник: наше определение).}
\term{Выпуск релиза}{переход релиза в состояние «Выпущен» после успешного прохождения последнего этапа маршрута (источник: наше определение).}
\term{Дистрибутив}{набор файлов одной версии компонента, подготовленный для установки (источник: наше определение).}
\term{Журнал аудита}{хронологическая история изменений данных системы; её записи недоступны для редактирования и удаления через операции системы (источник: наше определение).}
\term{Задача пользователя}{действие, ожидаемое от назначенного пользователя: выполнение ручного шага или решение по запросу на согласование (источник: наше определение).}
\term{Компонент}{часть программного продукта, которая собирается и получает номер версии независимо от других частей (источник: наше определение).}
\term{Контрольная сумма}{значение, вычисленное по содержимому дистрибутива для проверки его целостности (источник: наше определение).}
\term{Критический дефект}{дефект, которому во внешней системе учёта задач назначена категория «критический» (источник: наше определение).}
\term{КТК}{контрольная точка качества: назначенный этапу набор критериев допуска релиза к следующему этапу; критерии проверяются по числовым порогам (источник: наше определение).}
\term{Маршрут продвижения}{упорядоченный список этапов продвижения релизов одного программного продукта (источник: наше определение).}
\term{Откат релиза}{восстановление прежнего состава среды: по запросу релиз-менеджера после ошибки этапа за ПСИ либо после успешного выпуска; автоматически --- при отсутствии подтверждения промышленного выпуска до окончания окна. При ошибке этапа и автоматическом откате восстанавливается состав до установки, при откате успешного выпуска --- состав предыдущего выпуска (источник: наше определение; решение команды).}
\term{Перечень изменений релиза}{список задач и исправленных дефектов, связанных с версиями компонентов в составе релиза (источник: наше определение).}
\term{Правило согласования}{список из M различных согласующих и число N положительных решений, требуемых для начала этапа; 1~$\leq$~N~$\leq$~M (источник: наше определение).}
\term{Принцип «четырёх глаз»}{правило, запрещающее инициатору продвижения принимать решения по согласованию этого релиза (источник: наше определение).}
\term{Программный продукт}{ПО, релизами которого управляет система; состоит из одного или нескольких компонентов (источник: наше определение).}
\term{Продвижение релиза}{последовательное прохождение релизом этапов маршрута (источник: наше определение).}
\term{Промышленная среда}{среда, предназначенная для работы продукта у конечных пользователей; в маршруте версии 1 ей соответствует последний этап (источник: наше определение).}
\term{ПСИ}{приёмо-сдаточные испытания: этап приёмки релиза с ручным подтверждением результата назначенным инженером по тестированию; также обозначается UAT (источник: наше определение; решение команды).}
\term{Ревизия исходного кода}{обозначение состояния исходного кода, из которого получена сборка компонента (источник: наше определение).}
\term{Релиз}{набор версий компонентов одного продукта, который проходит проверки и выпускается как целое (источник: наше определение).}
\term{Релиз-кандидат}{релиз с зафиксированным составом, ещё не выпущенный и не отменённый (источник: наше определение).}
\term{Сборка}{получение дистрибутива компонента из исходного кода внешней системой сборки (источник: наше определение).}
\term{Согласование}{принятие решений о допуске релиза к этапу. Запрос на согласование адресован назначенным согласующим; решение имеет значение «согласовано» или «отклонено» (источник: наше определение).}
\term{Состав релиза}{перечень версий компонентов, включённых в релиз; содержит не более одной версии каждого компонента (источник: наше определение).}
\term{Среда развёртывания}{именованный набор вычислительных ресурсов для установки, проверки или эксплуатации продукта; синоним --- стенд (источник: наше определение).}
\term{Технологическое окно}{окно обслуживания сервиса: заданный интервал времени для начала установки, повтора установки и ручного отката в промышленной среде; окно обязательно только для этой среды. До его окончания требуется подтвердить выпуск; при отсутствии подтверждения автоматический откат выполняется вне окна (источник: наше определение; решение команды).}
\term{Установка}{подтверждённое внешней системой размещение версии компонента в среде развёртывания (источник: наше определение).}
\term{Фиксация состава релиза}{действие релиз-менеджера, после которого состав релиза становится неизменяемым (источник: наше определение).}
\term{Хранилище дистрибутивов}{внешнее место хранения файлов версий компонентов; система учитывает ссылки на эти файлы (источник: наше определение).}
\term{Шаг}{действие этапа: автоматический шаг выполняет внешняя система развёртывания, ручной --- назначенный исполнитель (источник: наше определение).}
\term{Этап}{часть маршрута, относящаяся к одной среде и состоящая из последовательных шагов; этап может иметь КТК и правило согласования (источник: наше определение).}
