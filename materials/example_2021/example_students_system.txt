 Общая информация

 Проект: разработка программной системы для студентов.
 В данном пространстве Confluence расположены все документы,
 написанные в рамках работы над проектом в курсе Технология
 программирования кибернетических систем (управление программными
 проектами)

 Идея проекта

 Создать приложение для студента, которое бы позволяло:
    Отслеживать информацию об актуальных студенческих мероприятиях
    Получать информацию о релевантных и актуальных акциях/скидках и
    пр.
    Смотреть новости города и ВУЗа
    Производить управление информацией для студентов со стороны
    города, ВУЗа,
 Целевая аудитория: студенты, ВУЗы, работники городских
 администраций.
 Сутью является агрегация информации, которая является релевантной
 для студентов. Для обеспечения этого требуются разные части
 Более подробное описание отражено в бизнес-требованиях.

 Разрабатываемое приложение “Город - студенту” предоставляет
 муниципальной администрации города Москва, администрациям учебных

 информации о событиях в сфере образования, мероприятиях, услугах и
 акциях для обучающихся ВУЗов и колледжей. Предметная область
 оперирования приложения охватывает частично или полностью большое
 количество различных сфер жизни и деятельности, таких как:
    сфера высшего и среднего профессионального образования (целевая

    сфера муниципального управления образованием (муниципальная
    администрация осуществляет управление приложением,
    распространяет через него новости и прочую важную информацию,

    стороны независимых организаторов и учебных заведений в
    соответствии с внутренними стандартами);
    информационно-новостная сфера (происходит агрегация актуальных
    новостей от муниципальной администрации, администраций учебных
    заведений);
    сфера рекламы и маркетинга (происходит агрегация рекламы
    мероприятий, услуг и акций от независимых организаторов

    сфера развлечений (среди рекламируемых мероприятий, услуг и

 1. Понимание бизнес-задачи

 Необходимо четко выявить цель заказчика.
 Определение цели исследования: что является проблемой? Почему
 проблема должна быть решена? Кого затрагивает проблема? Какие есть
 альтернативы? По каким метрикам будет оцениваться успешность
 проекта?
 2. Аналитический подход

 Выбор аналитического подхода для решения поставленной бизнес-
 задачи.
 Например если ответ должен быть вида да/нет, подойдет наивный
 байесовский классификатор. Если нужен ответ в виде численного
 признака, то подойдут регрессионные модели.
 3. Требования к данным

 Подготовка требований к данным: контент, форматы и источники,
 которые будут использованы на следующей стадии проекта.
 Второй блок: работа с данными
 4. Сбор данных

 После получения данных происходит верификация данных
 пересмотрение требований к ним: принятие решения о необходимости
 дополнительных данных, могут быть выявлены лакуны в данных и

 составлен план, как их закрыть или найти замену.
 5. Анализ данных

 Строится описательная статистика: исследуется центральное положение
 (среднее, медиана, мода), ищутся выбросы и выполняется оценка
 вариабельности (размах, дисперсия и стандартное отклонение). Строятся
 гистограммы переменных, ящики с усами и другие инструменты
 визуализации. Выполняется попарное сравнение: вычисляются
 корреляции между переменными, чтобы определить, какие из них
 связаны и насколько.

 относительно поставленной задачи
 6. Подготовка данных

 данные, проверяются и при необходимости исправляются ошибки
 форматирования.

 Мобильное приложение представляет собой основную точку входа в
 систему для пользователей. Именно оно является главным
 разрабатываемым продуктом, все остальные сервисы служат для его

 Через мобильное приложение пользователь работает с лентой событий

 предоставляемого контента.
 Схема работы приложения.
 Менеджерская CRM-система
 Менержерская CRM-система представляет собой продукт для
 менеджеров и организаторов, который позволяет управлять данными по
 мероприятиям/скидкам, создавать новые события в системе,
 администрировать отзывы и репорты пользователей, а также получать
 аналитику в текстовом и графическом виде.
 Схема работы системы.
 Уровень публичного API

 Mobile Gateway
 Mobile Gateway - это сервис-шлюз для предоставления доступа к данным
 мобильному приложению. Реализует публичный API для работами с
 такими сущностями как, например, пользователи, события и проч.
 Mobile Gateway не хранит состояния и какие-либо данные, а лишь
 осуществляет предобработку запросов, занимается маршрутизацией
 запросов по получению данных в нужные сервисы, а также реализует
 аутентификацию и авторизацию пользователей.
 Схема работы сервиса описана в разделе Mobile Gateway.

 проч.
 CRM Gateway не хранит состояния и какие-либо данные, а лишь

 Процесс разработки требований к ПО является частью жизненного цикла
 ПО и взаимодействует со всеми остальными процессами, определенными
 в проекте. Упрощенное окружение процесса представлено на рисунке 1.

ТПКС, 2021 год, группа Б18-504
 Рисунок 1. Окружение процесса разработки программных требований
 Процесс разработки требований использует входные данные,
 предоставляемые заказчиком (например, спецификации системных
 требований и архитектуры) и данные, возникающие в ходе других
 процессов, связанных с данным процессом (например, результаты
 формальных инспекций). Результаты процесса разработки требований
 поступают на входы других процессов, выполняющихся в проекте.
 Верификация разработанной спецификации программных требований
 проводится с помощью процедуры формальной инспекции, которая
 регламентируется стандартом проекта «Формальные инспекции» и
 планом верификации проекта. В случае обнаружения несоответствий
 процесс разработки программных требований повторяется.
 Входные данные процесса разработки требований к ПО

 Исходными входными данными являются бизнес-требования,
 функциональные требования, пользовательские требования,
 архитектурные ограничения и описание ее программно-аппаратных
 интерфейсов, стандарты проекта(в том числе и стандарт на разработку
 требований).

 Условия конца процесса разработки требований к ПО

 Процесс разработки требований носит итерационный характер.
 Окончанием итерации является решение разработчика требований о том,

 регистрацией этого в соответствии со стандартами проекта. Пока в

 разработанных требований входным данным, процесс будет повторяться.

     разработчиком в процессе работы над соответствующей задачей /
     вносом правок.

     определяется корректность внесённой информации, её соответствие
     цели задачи и её описанию, а также соответствие проекту.

     создаётся отдельная задача и у администратора Confluence
     запрашивается разблокировка страницы.

 Gitlab

 В качестве среды для работы с репозиториями используется Gitlab. Gitlab
 - это веб-сервис для хостинга и совместной разработки проектов,
 использующий Git в качестве системы контроля версий.
 Единицы конфигурации хранятся в git-репозиториях, представляющих
 собой каталоги файловой системы, содержащие файлы конфигурации
 репозитория, файлы журналов, хранящие операции, выполняемые над
 репозиторием, индекс, описывающий расположение файлов, и
 хранилище отслеживаемых файлов. Участники разработки могут вносить
 свой вклад в файлы, находящиеся в репозитории, тем самым изменяя
 конфигурацию проекта.
 Gitlab хранит полную историю изменений проекта в виде наборов
 состояний - коммитов. В случае необходимости любое из состояний
 проекта может быть восстановлено. Состояние может быть выбрано в
 качестве очередной базовой версии разрабатываемого продукта. Версия
 может только увеличиваться при движении вперед по истории состояний.
 Gitlab, будучи основанным на Git, поддерживает систему с ветками -
 отдельными над-состояниями репозитория, характеризующимися своим
 набором коммитов, возможностью ведения параллельной разработки и т.
 д. Ветки позволяют организовать разработку в команде с большим
 числом участников, удобно сравнивать версии проекта и, в случае
 необходимости, совершать откат последней базовой версии проекта.
 Jira




ТПКС, 2021 год, группа Б18-504
 В качестве среды для управления задачами используется Jira. Jira – это
 программный инструмент для управления проектами. Jira используется
 для формирования списка задач, отслеживания общего прогресса
 команды и решения возникающих по ходу разработки продукта проблем.
 Приложение построено по принципам канбан- и скрам-досок. Эти
 принципы дополняются массой вспомогательных механизмов, которые
 добавлялись в приложение исключительно с целью упростить создание
 новых приложений, добавить в них функции, исправить ошибки и т.п.
 Также эта система управления проектами исповедует Agile-методику
 разработки.
 Основные сценарии использования Jira и сценарии, в которых удобно
 использование задач:
     Организация списка задач в виде канбан-доски с целью наглядного
     отображения текущей истории/эпика и статуса проекта.
     Управление проектом и командой, организация рабочего процесса.
     Работа с жизненным циклом задачи.
     Отслеживание ошибок, баг-трекинг, формирование списка задач на
     внесение изменений в проект.
 Confluence

 В качестве среды для создания, редактирования документов и
 управления ими используется Confluence. Confluence — это wiki движок и
 среда для редактирования текста. Он позволяет организовать
 внутренний портал/пространство, дать доступ к нему участникам
 разработки и создавать страницы будущих документов.
 Confluence позволяет пользоваться широким набором инструментов для
 редактирования текста. Возможности среды позволяют интегрироваться с
 Jira и Gitlab, автоматически подтягивать изменения из связанных
 документов и не только.
 В случае текущего проекта Confluence используется в первую очередь
 как среда редактирования текста и сбора информации о проекте. Каждая
 страница Confluence подлежит версионированию (версия фиксируется в
 момент блокировки страницы для редактирования). Функционал
 Confluence позволяет генерировать pdf-документ на основе страниц,
 который и служит базовой версией документа об организации разработки.

 1) Концептуальное (инфологическое) проектирование

 Цель инфологического проектирования состоит в получении моделей,
 отражающих предметную область и информационные потребности
 пользователей. В качестве инструмента для построения модели данных
 на этапе проектирования можно выбрать модель «сущность–связь»
 (Entity–Relationship) - метод «ER– диаграммы».
 Основные элементы ER-моделей:
     объекты (сущности);
     атрибуты объектов;
     связи между объектами.
 Связь между сущностями характеризуется:
     типом связи (1:1, 1:N, N:М);

     необязательным). Если каждый экземпляр сущности участвует в связи,
     то класс принадлежности — обязательный, иначе — необязательный.

     первичный ключ;
     Составные (состоят из комбинации нескольких компонентов) и простые
     (состоят из одного компонента);


     Однозначные (имеют одно значение для каждого экземпляра

 Нормализация

 При проектировании реляционных баз данных выполняется нормализация
 -процесс преобразования отношений базы данных к виду, отвечающему
 нормальным формам.
 Нормальные формы:
    Первая нормальная форма (1NF): переменная отношения находится в
    первой нормальной форме (1НФ) тогда и только тогда, когда в любом
    допустимом значении отношения каждый его кортеж содержит только
    одно значение для каждого из атрибутов;
    Вторая нормальная форма (2NF): переменная отношения находится во
    второй нормальной форме тогда и только тогда, когда она находится
    в первой нормальной форме и каждый неключевой атрибут
    неприводимо (функционально полно) зависит от её потенциального
    ключа;
    Третья нормальная форма (3NF): переменная отношения находится в
    третьей нормальной форме тогда и только тогда, когда она находится
    во второй нормальной форме, и отсутствуют транзитивные
    функциональные зависимости неключевых атрибутов от ключевых.
    Нормальная форма Бойса — Кодда (BCNF): переменная отношения
    находится в нормальной форме Бойса — Кодда (иначе — в усиленной
    третьей нормальной форме) тогда и только тогда, когда каждая её
    нетривиальная и неприводимая слева функциональная зависимость
    имеет в качестве своего детерминанта некоторый потенциальный
    ключ.
    Четвёртая нормальная форма (4NF): переменная отношения находится
    в четвёртой нормальной форме, если она находится в нормальной
    форме Бойса — Кодда и не содержит нетривиальных многозначных
    зависимостей.
    Пятая нормальная форма (5NF): переменная отношения находится в
    пятой нормальной форме (иначе — в проекционно-соединительной



    нормальной форме) тогда и только тогда, когда каждая
ТПКС, 2021 год, группа Б18-504
    нормальной форме) тогда и только тогда, когда каждая
    нетривиальная зависимость соединения в ней определяется
    потенциальным ключом (ключами) этого отношения.
    Доменно-ключевая нормальная форма (DKNF): переменная отношения
    находится в ДКНФ тогда и только тогда, когда каждое наложенное на
    неё ограничение является логическим следствием ограничений
    доменов и ограничений ключей, наложенных на данную переменную
    отношения.
    Шестая нормальная форма (6NF): переменная отношения находится в
    шестой нормальной форме тогда и только тогда, когда она
    удовлетворяет всем нетривиальным зависимостям соединения. Из
    определения следует, что переменная находится в 6НФ тогда и только
    тогда, когда она неприводима, то есть не может быть подвергнута
    дальнейшей декомпозиции без потерь.

 Формальная инспекция

 Формальная инспекция - одно из мероприятий процесса верификации
 ПО, направленное на обеспечение качества ПО посредством “осмотра”
 единиц конфигурации проекта.
 Цель

 Целью формальной инспекции является проверка каждой единицы
 конфигурации проекта на соответствие требованиям и стандартам
 проекта путём осмотра её заинтересованными участниками разработки.
 Одной из важных целей формальной инспекции является обеспечение не
 зависимости в оценке единиц конфигурации. Это необходимо для
 достижения наивысшего качества итогового ПО.
 Участники формальной инспекции

 В процессе формальной инспекции принимают участие несколько
 участников, каждый из которых имеет свою роль
 Роли:
    Инспектор - участник формальной инспекции, оценивающий единицу
    конфигурации в соответствии с некоторым чеклистом.
    Координатор формальной инспекции - главный инспектор,
    назначающий остальных инспекторов, назначающий начало
    инспекции и координирующий действия остальных участников ФИ.
    Автор - автор инспектируемой единицы конфигурации,
 Важно отметить, что для достижения свойства независимости в
 формальной инспекции, инспекторами должны выбираться участники
 разработки, не связанные с инспектируемой единицей конфигурации.
 Чеклисты

 Характеристика
 Каждая формальная инспекция проходит в соответствии с некоторым
 чеклистом, содержание которого определяется непосредственно
 инспектируемой единицей конфигурации проекта.
 Например, в чеклисте для проведения формальной инспекции
 требований к ПО будут содержаться стандарты, выполнение которых
 является обязательным для прохождения ФИ.

 Виды тестирования

 Модульное тестирование

 Суть
 Модульное тестирование - это тестирование отдельных функций в
 исходном коде сервисов. Это необходимо для проверки соответствия
 написанных функций поставленным требованиям нижнего уровня.
 Каждый модульный тест содержит набор входных параметров функции и
 ожидаемый результат её выполнения. Для разных функций набор
 тестовых сценариев может быть разным, в зависимости от количества
 входных параметров и сложности функции.
 Отличия
 Модульное тестирование является сугубо автоматизированным, любое
 изменение в исходном коде должно сопровождаться их прогоном для
 того, чтобы убедиться в том, что такие изменения не затрагивают
 поставленный в требованиях функционал.
 Также стоит отметить, что модульное тестирование не использует
 компоненты, интегрируемые в сервис (БД, брокеры сообщений и т.д.).
 Если есть необходимость в обращении к таковым, то используются
 специальные заглушки.
 Модульное тестирование также осуществляет сбор покрытия функций в
 коде тестами. Это осуществляется с помощью статического анализа кода,
 который проводится специальными библиотеками. Таким образом, на
 выходе получается документ о покрытии кода.

 Функциональное тестирование

 Суть
 Функциональное тестирование - это тестирование отдельных компонент
 сервиса без включения внешних интеграций с другими сервисами. Это
 необходимо для проверки соответствия написанного функционала
 требованиям высокого уровня.
 В функциональных тестах не проверяются отдельные функции, а сразу
 целые компоненты. В связи с этим такие тесты являются более сложными,
 чем модульные тесты, покрывают сразу несколько требований низкого
 уровня. Говоря в общем, один сценарий функционального теста
 описывает один процесс, происходящий в сервисе и захватывает в себя
 одну или более функцию, для которой существует модульный тест.
 Отличия
 В текущем проекте, в зависимости от сервиса, конечные цели
 функционального тестирования отличаются, т.к. компоненты разных
 сервисов отличаются. Так, выделяются следующие типы:
    Тесты API. Это функциональные тесты для backend-сервисов, в
    которых проверяется спецификация API и его функционал.
    Тесты воркеров/кронов. Это функциональные тесты асинхронных
    задач, где, в первую очередь проверяется корректность их
    выполнения в фоне. Такие тесты также могут проверять требования
    низкого уровня, говорящие о временных характеристиках работы
    сервисов.
    Тесты интерфейса. Проверяется корректная работа кнопок
    интерфейса.
 Также в функциональных тестах могут использоваться интегрированные
 в сервис компоненты, такие как БД, брокеры сообщений и пр. Это бывает
 необходимо, т.к. со стороны теста не должно быть вторжения в данные
 /события, проверяются конкретные взаимодействия сервиса с ними.

 Интеграционное тестирование

 Суть
 Интеграционное тестирование служит для проверки взаимодействия двух
 и более сервисов друг с другом. Это наиболее сложный вид тестирования,
 т.к. он затрагивает большое количество связанных друг с другом
 компонент и сложен в реализации.
 Каждый тестовый сценарий представляет собой процесс, который
 затрагивает два и более сервиса, описывает поведение каждого из них, те
 изменения, которые происходят с данными и событиями. Всё это
 трассируется на исходные системные требования, которые такой процесс
 и описывают.
 Отличия
 Интеграционное тестирование может быть как автоматизированным, так
 и ручным, оба типа допустимы и применяются в разных ситуациях.
 Для проведения ручного интеграционного тестирования требуется
 тестовый стенд, на который могут быть загружены исполняемые файлы
 необходимых сервисов и выведена их конфигурация, схожая с “боевой”.
 Составляется набор тестовых сценариев, которые описывают
 межсервисное взаимодействие, указанное в системных требованиях к
 проекту. Затем тестировщик проводит руками действия, необходимые для
 воспроизведения того или иного сценария с целью убедиться, что
 полученное поведение соответствует ожидаемому (соответствует
 требованиям).

 Как использовать?

 Для того, чтобы использовать gonkey в своём проекте, необходимо
 скопировать папку tests в корень своего проекта, связать исполняемый
 файл сервиса с файлом test_runner.go, указать необходимые переменные

 Как написать тест по существующей спецификации сервиса?

 Для написания теста нам необходимо несколько вещей:
    Спецификация тестируемой ручки API
    Схема внешних взаимодействий (для шлюзов и *редко* для backend-
    сервисов)
    Схема данных (для backend-сервисов)
    Схема бизнес-логики (для backend-сервисов)
 Из спецификации мы берём название ручек, модели запросов/ответов.
 По схеме внешних взаимодействий можно понять какие требуются
 заглушки для тестов.
 Схема данных определяет тестовые фикстуры.
 Схема бизнес-логиики определяет, как изменяются данные в разных
 бизнес-процессах в разных ручках API.
