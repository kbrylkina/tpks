1. Ссылки
Стандарт на разработку требований к ПО: файл “Стандарт на разработку требований.docx” из корневой папки.
2. Термины
УК ПО - управление конфигурацией программного обеспечения.
ЖЦ - жизненный цикл программного обеспечения.
Сообщение о проблеме - документ процесса УК ПО, содержащий описание несоответствия в данных ЖЦ ПО или в описании процессов ЖЦ ПО.
Формальная инспекция - способ верификации документов, основанный на экспертной оценке их правильности, выполняемой одним или несколькими инспекторами, как правило, с использованием проверочных перечней.
Задача - документ процесса УК ПО, созданный для внесения изменений в данные ЖЦ ПО с целью устранения несоответствия, описанного в СП.
3. Ответственные
Руководитель проекта несет ответственность за эффективное распределение задач между ответственными разработчиками. Это распределение задач должно быть таким, чтобы исключить возможность одновременной работы различных членов команды над одними и теми же частями документов.
Ответственный разработчик, назначенный руководителем проекта, обязан сопровождать свою задачу в соответствии с процессами разработки программного обеспечения, как указано в "Процессах разработки ПО".
Базовая версия данных в жизненном цикле программного обеспечения представляет собой последнюю версию данных, утвержденных верификацией.
В процессе жизненного цикла программного обеспечения появляются новые версии данных, которые после прохождения верификации могут быть назначены базовыми. В случае несоответствия требованиям эти версии данных могут быть отправлены на повторное прохождение этапа жизненного цикла.
Выявленные несоответствия в результате мероприятий процесса разработки программного обеспечения фиксируются с использованием сообщений о проблемах, которые передаются в процесс управления конфигурацией программного обеспечения. Базовые версии данных поступают в процесс управления конфигурацией программного обеспечения.
4. Информация для всех процессов разработки ПО
Условия входа в конкретный процесс разработки ПО:
	•	Наличие всех нужных документов и требований, указанных на вход задаче. Назначение задачи исполнителю.
	•	Задача переведена в статус “Backlog” после верификации.
Стандартный протокол действия в рамках процесса разработки ПО со стороны разработчиков при назначении задачи:
	•	Задаче назначается статус “In progress”
	•	Определяются документы для создания/изменения/удаления
	•	Для любых производных требований должны быть указаны “родительские требования” (требования, из которых было порождено данное)
	•	При необходимости изменения документов изменения должны вноситься в копии документов, а не в оригинал
	•	При завершении работы, задаче назначается статус “QA”(quality assurance - проверка качества)
Условия выхода из конкретного процесса разработки ПО:
	•	Все проблемы, появившиеся во время работы устранены
	•	Все изменения в документах подтверждены
	•	Руководитель поставлен в известность о завершении
5. Разработка требований
Целями процесса разработки требований к ПО являются:
	•	Разработка требований к ПО высокого уровня;
	•	Разработка производных требования к ПО высокого уровня.
Входные данные:
	•	Стандарт на разработку требований
	•	План разработки
	•	Требования к системе (включающие описание архитектуры системы и ее программно-аппаратных интерфейсов)
	•	Результат формальной инспекции
Выходные данные:
	•	Требования к ПО
	•	Сообщения о проблемах
6. Проектирование ПО
Целями процесса проектирования ПО являются:
	•	Определение архитектуры ПО;
	•	Разработка требований к ПО низкого уровня;
	•	Разработка производных требования к ПО низкого уровня.
	•	План разработки ПО
Входные данные
	•	Стандарт проектирования
	•	Результат формальной инспекции
	•	Требования к ПО
Выходные данные:
	•	Описание проекта
	•	Сообщения о проблемах
Описание процесса:
Основным методом при разработке описания проекта ПО будет являться метод структурного проектирования, представляющий собой процесс последовательного разбиения (декомпозиции) ПО на компоненты, а компонента на подкомпоненты и функции.
7. Кодирование ПО
Цель процесса кодирования ПО:
	•	Разработать исходный код трассируемый, верифицируемый, непротиворечивый и реализующий требования к ПО низкого уровня.
Входные данные:
	•	Стандарт кодирования
	•	Результат формальной инспекции
	•	Описание проекта
	•	План разработки ПО
Выходные данные:
	•	Исходный код
	•	Командные файлы с директивами для компилятора
	•	Сообщения о проблемах
Описание процесса:
Разработчики вносят изменения в модули исходного кода, руководствуясь стандартом на кодирование ПО.
При выполнении мероприятий ответственный разработчик использует инструментарий процесса кодирования.
8. Интеграция ПО
Цель процесса интеграции ПО:
	•	Загрузить на вычислительное устройство исполняемый код ПО для интеграции ПО и аппаратных средств.
Входные данные
	•	Описание проекта
	•	Результат формальной инспекции
	•	Исходный код
	•	Командные файлы с директивами для компилятора
	•	План разработки ПО
Выходные данные:
	•	Исполняемый код
	•	Командные файлы с директивами для компоновщика;
	•	Командные файлы с директивами загрузки исполняемого объектного кода в вычислитель;
	•	Протоколы сборки и загрузки исполняемого объектного кода в вычислитель;
	•	Сообщения о проблемах.
