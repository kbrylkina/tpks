1. Введение
1.1 Описание
В представленном документе “План управления конфигурацией” будут рассмотрены основные мероприятия и цели одноименного процесса в рамках разрабатываемой программной системы. 
1.2 Цель
Целью настоящего документа “План управления конфигурацией” является описание и иллюстрация тех средств, методов, а также мероприятий, которые используются при управлении конфигурацией реализуемого программного обеспечения. 
1.3 Определения и сокращения.
Коммит - пакет изменений, хранящий информацию с добавленными, отредактированными или удалёнными файлами кода.
Ветка - набор коммитов, расположенных в хронологическом порядке.
ПО - программное обеспечение.
УК - управление конфигурацией.
СП - сообщение о проблеме.
НЗ - назначенная задача.
2. Среда управления конфигурации ПО
2.1 Инструменты УК ПО
Основным средством управления конфигурацией является система контроля версий Git. Для возможности совместной работы используется сервис GitHub, предназначенный для онлайн-хостинга репозиториев. Эти инструменты предлагают обширный набор функций для управления изменениями, отслеживания проблем и создания основных версий элементов конфигурации.
В качестве системы документооборота выбран Confluence, который представляет из себя тиражируемую вики-систему для внутреннего использования организациями с целью создания единой базы знаний.
2.2 Ответственные
В рамках управления конфигурацией на реализуемом проекте каждый участник обладает минимум одной ролью, которая определяет его обязанности и полномочия. Роли распределяются с учетом специфических функций, которые выполняет каждый участник в проекте. Примеры ролей в проекте:
	•	Автор: Может создавать и редактировать конфигурационные элементы, такие как данные об источниках питания, параметры управления реле, и другие.
	•	Инспектор: Может проводить инспекции текущих конфигурационных элементов, а также вносить изменения при необходимости. 
	•	Администратор: Имеет расширенные права доступа к конфигурационным данным. Может управлять пользователями, их доступами к конфигурации, а также координировать процессы изменения конфигурации.
	•	Пользователь: Может быть автором своих собственных конфигурационных элементов (например, данных об энергопотреблении), а также инспектором, контролируя свои параметры и состояние.

3. Мероприятия процесса УК ПО
3.1 Идентификация конфигурации
Для эффективного управления конфигурацией программного обеспечения необходимо ясно определить объекты конфигурации, которые могут быть разделены на две категории:
1.  Базисные объекты: Это элементы информации, создаваемые в процессе анализа, проектирования или тестирования, например, раздел спецификации требований, часть проектной модели, исходный код компонента, или набор тестов для проверки программного кода.
2. ​​Составные объекты: Это сложные структуры, объединяющие базисные элементы. Например, конфигурационная версия программы, включающая компоненты и связанные данные.
Цель идентификации конфигурации - однозначно определить каждую единицу конфигурации, создавая основу для её управления. Каждый объект конфигурации имеет уникальный набор характеристик:
	•	Имя объекта: Уникальная строка, которая служит идентификатором объекта конфигурации.
	•	Описание объекта: Включает тип элемента (элемент модели, программа, данные), идентификатор проекта, информацию о версии или изменениях.
	•	Ресурсы: Элементы, которые используются, обрабатываются или запрашиваются объектом. Это могут быть различные ресурсы, такие как типы данных, функции, имена переменных и другие элементы, необходимые для функционирования объекта.
Учитывание взаимосвязей между объектами конфигурации при их идентификации является важным аспектом. Каждый базисный объект конфигурации должен быть идентифицирован перед началом управления изменениями и регистрации трассируемости, а составные объекты должны быть идентифицированы перед их использованием в других процессах жизненного цикла программного обеспечения.
В качестве базовых объектов конфигурации часто используются коммиты в системах контроля версий. Каждый коммит включает в себя:
	•	Уникальный хэш.
	•	Указатель на родительский коммит.
	•	Дату создания.
	•	Перечень изменений по сравнению с предыдущим коммитом.
	•	Краткое описание изменений на английском языке, не превышающее 50 символов.
Эти характеристики обеспечивают однозначную идентификацию и отслеживание изменений в проекте, что облегчает управление конфигурацией и обеспечивает прозрачность в процессе разработки.
3.2 Базовые версии и трассируемость
Все изменения в ПО осуществляются на основе базовой версии, или базовой конфигурации. Базовая версия, представляет собой совокупность реализованных функциональных и нефункциональных требований в определенной версии (итерации) программного продукта. Главная цель введения базовой версии - создать основу для последующих этапов жизненного цикла ПО, предоставляя возможность ссылаться на эту версию, контролировать её и обеспечивать трассируемость между единицами конфигурации.
В данном проекте, базовой версией считается та версия ПО, которая представлена в ветке "main". Создание новой базовой версии, или новой версии ПО, происходит путем обновления ветки "main".
Каждая версия ПО должна быть задокументирована. Документация должна включать историю изменений, указывая следующие аспекты:
	•	Внесенные изменения.
	•	Дата каждого изменения.
	•	Лицо, ответственное за внесение изменения.
	•	Причина изменения.
Все документы, относящиеся к версиям ПО, хранятся в единой базе знаний, например, в Confluence. Документ о каждой новой версии должен содержать ссылки на документы предыдущих (родительских) версий.
3.2.1 Контроль статуса единиц конфигурации
В автоматизированных средствах управления проектом для контроля степени выполнения той или иной работы используется понятие степени выполнения (progress). 
Таблица 1. Состояния изменений
Состояние
Определение

Изменение запрошено
Approved (одобрено)
Изменение проанализировано, его влияние на проект просчитано, ключевые заинтересованные в проекте лица согласились с этим требованием

Изменение предложено, но не запланировано для реализации ни в одной из будущих версий, описаны причины отклонения требования и зафиксировано лицо, принявшее это решение

Корректное функционирование реализованного изменения подтверждено в соответствующем продукте, требование отслежено до соответствующих вариантов тестирования, как следствие, требование считается завершенным

Утвержденное изменение удалено, описаны причины удаления и зафиксировано лицо, принявшее это решение
В качестве контроля статуса единиц конфигурации выбрана система Pull request, предоставляемая GitHub. При внесении изменений в главную конфигурацию (в ветку “master”) человек, вносящий изменение, заливает свою дочернюю ветку с необходимыми изменениями на GitHub и создает Pull request. Данный объект содержит запрос Proposed на вливание дочерней ветке в главную. Далее все члены команды разработки должны просмотреть запрос на изменение и оставить замечания, если они имеются. При исправлении всех замечаний проверяющий ставит одобрение данному запросу Approved. Если все замечания устранены и присутствует одобрение от всех членов разработки, то запрос на вливание дочерней ветке принимается и изменения вносятся в главную ветку. После внесения изменений главная ветка представляет новую версию ПО Verified. При недостаточном количестве одобрений запрос отклоняется Rejected. Далее новая конфигурация проекта попадает к отделу тестирования, который сверяет изменения в конфигурации с требованиями к ПО. Если тестирование одобряет данную конфигурацию Done, то эта версия проходит деплой и попадает пользователю. 
3.2.2 Трассируемость
Ниже перечислены элементы трассируемости: 
	•	потребности пользователей и заинтересованных лиц (могут быть далее сведены к запросам заинтересованных лиц); 
	•	возможности продукта;

Рассматриваемые элементы трассируемости позволяют определить:

3.3 Регистрация проблем и управление изменениями
3.3.1 Регистрация проблем
Каждый участник команды разработки должен документировать все выявленные им несоответствия, используя Git — популярную систему контроля версий, работающую на основе ациклического направленного графа. GitHub — это платформа для использования Git. Обнаруженные несоответствия могут включать:
	•	Расхождения в жизненном цикле программного обеспечения;
	•	Неувязки между выполняемыми процессами и описанными в планах, а также недочёты в результатах этих процессов;
	•	Неполадки в работе программного обеспечения и другое.
В Git регистрация проблемы осуществляется путём последовательного выполнения команд git checkout -b issuenumber - создание новой ветки для проблемы и переход к ней, git commit -a -m ‘Описание проблемы’ - создается коммит, со всеми измененными файлами. Участник детально описывает проблему и проводит её первичную классификацию, относя её к определённой категории и проверяя критичность  по таблице 2. Проблемы со степенью критичности “Высокая” регистрируются в срочном порядке. Сначала нужно переключаются на ветку main командой git checkout main, затем создают новую ветку для исправления проблемы, используя те же команды. Изменения отправляются командой git push, а для слияния веток используется git merge.

3.3.2 Рассмотрение изменений
Каждое сообщение о проблеме, зарегистрированное в системе, обязательно подлежит рассмотрению. Частота таких рассмотрений устанавливается руководителем проекта. На любом этапе времени, каждое зарегистрированное сообщение о проблеме может находиться только в одном из следующих состояний:
	•	"REGISTERED" (Зарегистрировано)
	•	"PRE ANALYSIS" (Предварительный анализ)
	•	"ANALYSIS" (Анализ)
	•	"SENT" (Направлено на реализацию)
	•	"IN PROGRESS" (Обрабатывается)
	•	"DISCARDED" (Отменено)
	•	"DONE" (Сделано)
Перед началом процесса рассмотрения все сообщения о проблемах, находящиеся в состоянии “REGISTERED”, должны быть переведены в состояние “ANALYSIS”. Для каждого из них проводятся следующие действия:
	•	Предварительный анализ проблемы:
	•	Классификация проблемы по ее характеру или области, в которой она возникла
	•	Привлечение специалиста, отвечающего за разработку данной части ПО, для детального анализа проблемы
	•	Анализ актуальности проблемы и определение дальнейших шагов:
	•	Выбор метода устранения обнаруженной проблемы
	•	Либо признание проблемы неактуальной и перевод сообщения о ней в состояние “DISCARDED” (с прекращением дальнейшего рассмотрения)
	•	Либо определение необходимости проведения дополнительного анализа или признание временной невозможности рассмотрения проблемы (с прекращением дальнейшего рассмотрения).
	•	Создание и регистрация необходимых запросов на изменения в системе поддержки разработки. Каждый такой запрос на изменение относится к одной из категорий, определяющих конкретные процессы жизненного цикла программного обеспечения, результаты которых требуют изменения для устранения выявленной проблемы

3.3.3 Внесение изменений
Процесс внесения изменений запускается, когда разработчик получает описание изменения и переводит сообщение о проблеме в статус “IN PROGRESS”. Этапы включают:
	•	Определение исходных версий конфигурационных единиц, представляющих собой базовые версии, зарегистрированные в системе поддержки разработки.
	•	Создание новых версий конфигурационных единиц на основе исходных в рамках запроса на изменение, или при невозможности завершить изменение - создание сообщения о проблеме и выход из процесса, или при отказе от изменения - перевод запроса в статус “DISCARDED” и возврат к базовым версиям.
	•	Проведение ревью, по результатам которого в системе регистрируются новые базовые версии конфигурационных единиц.
	•	Перевод запроса на изменение в статус “DONE”.
Работа выполняется в ветке, которая наследуется от главной. Для изменений в главной конфигурации (ветке master) разработчик отправляет свою ветку на GitHub и создает Pull request. Затем все члены команды просматривают и комментируют запрос. После устранения всех замечаний и получения одобрения от команды, запрос на вливание ветки принимается. Если одобрения недостаточно, запрос отклоняется как “DISCARDED”. После принятия изменений главная ветка формирует новую версию ПО. Затем новая конфигурация проекта направляется в отдел тестирования для проверки соответствия требованиям. Если тестирование успешно, версия деплоится и становится доступной для пользователя как “DONE”.
3.3.4 Закрытие сообщения о проблеме
Если все запросы на изменения, связанные с определённым сообщением о проблеме, получили статус “DONE” или “DISCARDED”, то это сообщение о проблеме также переводится в состояние “DONE”. После этого проводится актуализация рабочей ветки через rebase (git rebase main). Ветка, в которой велась работа над проблемой, объединяется с веткой master. Затем ветка, использовавшаяся для решения проблемы, удаляется с использованием команды git branch -d.
3.3.5 Соглашения по работе с репозиторием
Предусмотрены ровно 2 возможных типа веток - ветки разработки (feature_branch) и релизные ветки (release_branch). 
Любые изменения единиц конфигурации выполняются в отдельных ветках разработки, образованных от актуального состояния main-ветки (базовой версии единиц конфигурации). 
Правила именования веток разработки: 
[номер CR]_[краткий смысл на английском языке]_[bugfix], где 
[номер CR] - идентификатор запроса на изменение (Change Request) 
[bugfix] является необязательным и используется лишь в случае, если правится единичная незначительная ошибка.
Правила именования релизных веток: 
[YYYYMMDD]_[номер версии релиза в разрезе дня]_[номер CR]_[bugfix], где 
[YYYYMMDD] - год, месяц и день релиза 
Правила именования Pull Request: 
[номер CR] [BugFix] [Краткий смысл на русском языке]
3.4 Учет состояния конфигурации
Основной целью проведения мероприятий по учету состояния конфигурации является предоставление данных для эффективного управления конфигурацией в рамках жизненного цикла программного обеспечения. Это включает в себя следующие аспекты:
	•	Идентификация конфигурации:
	•	Базовые версии: 
	•	Сообщения о проблемах: 
	•	Управление изменениями: 
Все действия с конфигурационными единицами записываются в журнал изменений. Этот журнал представляет собой упорядоченный по времени список изменений, внесенных в проект. Файл changelog.md формируется автоматически при выполнении команды "changelog generate" в терминале разработчика в репозитории GitHub. Записи в формате markdown создаются на основе коммитов git и содержат информацию о дате и времени создания каждой версии единицы конфигурации, пользователе, создавшем эту версию, а также текущем состоянии конфигурационной единицы. Это обеспечивает участникам проекта доступ к актуальной информации в любой момент времени.
3.5 Архивирование и выпуск
Архивирование (резервное копирование) данных ЖЦ ПО не предусматривается. Мероприятия по выпуску ПО предусматривают создание базовой версии каталога комплектации ПО
