3. Стандарт проектирования базы данных

3.1. Этапы проектирования базы данных

3.1.1. Концептуальное проектирование
          Концептуальное проектирование направлено на создание моделей, которые
отражают предметную область и удовлетворяют информационные потребности
пользователей.      В    процессе    проектирования     будет    использоваться     модель
"сущность-связь" (Entity-Relationship) и метод ER-диаграммы для создания модели
данных.
Главные элементы ER-модели:
      ● Объекты или же сущности
      ● Атрибуты между объктами
      ● Связи между объектами
Оъекты могут относиться к следующим типам:
      1. Основная сущность - является независимой сущностью

                                             11
   2. Связанная сущность - связана с несколькими родительскими сущностями и
      содержит информацию о связях сущностей;
   3. Классифицирующая сущность – частный случай связанной сущности, не
      имеющей собственных атрибутов (только атрибуты родительских сущностей,
      мигрировавших в качестве внешнего ключа);
   4. Описательная сущность – сущность, связанная только с одной родительской и
      хранящая информацию о характеристиках родительской сущности;
   5. Подчиненная сущность – дочерняя сущность в иерархии наследования.
У атрибутов сущностей можно выделить несколько типов:
   1. Идентифицирующие атрибуты имеют уникальное значение для экземпляров
      данного типа сущности, в то время как описательные атрибуты содержат
      интересующие свойства этой сущности. Каждая сущность обязательно должна
      иметь первичный ключ. А
   2. Составные (состоящие из нескольких компонентов) или простые (состоящими
      из одного компонента).
   3. Однозначные (имеющие одно значение для каждого экземпляра сущности) или
      многозначне (имеющие много значений для каждого экземпляра сущности).
   4. Основные (значение не зависит от других атрибутов) или производные
      (значение вычисляется на основе значений других атрибутов).
   5. Обязательные (значение всегда должно быть указано при добавлении данных в
      базу данных) или необязательные (значение необязательного атрибута может
      быть пропущено).
Связи между сущностями характеризуются типом связи и классом принадлежности.
При этом, связи бывают следующих типов:
   1. Один-к-одному (1:1)      - применяется   в тех случаях, когда существует
      необходимость взаимосвязи между двумя сущностями, при этом каждая
      сущность имеет только одно соответствующее значение другой сущности.
      Примером связи один-к-одному может быть связь между сущностями "Студент"
      и "Паспортные данные". Каждому студенту может соответствовать только одна
      запись о его паспортных данных, а каждым паспортным данным будет
      соответствовать только один студент.
   2. Один-ко-многим (1:N) - используются в различных ситуациях, где существует
      необходимость связать одну сущность с несколькими экземплярами другой
      сущности.     Примером связи один-ко-многим может быть связь между

                                        12
         сущностями "Страны" и "Города". Каждой стране может соответствовать
         несколько городов, но каждый город будет принадлежать только одной стране.
   3. Многие-ко-многим (N:M) - позволяет представить сложные и взаимосвязанные
         отношения между сущностями, где каждая из них может иметь несколько
         экземпляров другой сущности. Примером связи многие-ко-многим может быть
         связь между сущностями "Студенты" и "Клубы". Здесь каждый студент может
         быть членом нескольких клубов, и каждый клуб может иметь несколько
         студентов-членов.
Результатом концптуального проектирвоания является создание ER-модели базы
данных.

3.1.2. Логическое проектирование
         Логическое проектирование направлено на определение необходимого числа и
структуры таблиц, создание запросов к базе данных, определение типов отчетов,
разработку алгоритмов обработки информации, создание форм для ввода и
редактирования данных, а также решение других задач, причем особое внимание
уделяется проблеме структуризации данных.
Важно, чтобы проектируемая БД обеспечивала целостность данных. Для этого на этапе
логического     проектирования   необходимо    накладывать   следующие    внутренние
ограничения целостности:
   ● Ограничения        на   значения   ключевых    атрибутов.   Они     определяются
         уникальностью значений первичных и альтернативных ключей в структуре
         данных. Подобные ограничения устанавливаются путем выделения ключевых
         атрибутов в концептуальной модели.
   ● Ограничения на допустимые значения атрибутов. Указывают, что все значения
         атрибутов должны соответствовать условиям, заданным для соответствующего
         домена. Эти ограничения определяются в описании доменов и атрибутов.
   ● Ограничения на существующие значения. Указывают, что существование
         некоторых сущностей (например, подкатегорий) зависит от существования
         других (например, категорий-родителей).
Результатом логического проектирования является логическая модель базы данных.
Для проектирования логической модели должна быть использована нотация “Crow’s

3.1.3 Физическое проектирование
      Цель физического проектирования включает в себя описание метода реализации
логического проекта базы данных. На данном этапе, касающемся реляционных баз
данных, сущности преобразуются в таблицы, а атрибуты – в столбцы. Взаимосвязи
между сущностями трансформируются в физическую схему базы данных.
      Также, на данном этапе решается задача оптимального распределения элементов
базы данных в памяти, создании индексов, оценке целесообразности применения
хеширования и кластеризации, с учетом особенностей выбранной системы управления
базами данных.
      Результатом физического проектирования является скрипт для создания базы
данных на языке SQL.


3.2. Стандарт оформления скрипта на языке SQL
   1. Ясные и понятные имена таблиц:
Имена таблиц должны отражать содержание данных без использования слишком
абстрактных или коротких названий.
   2. Избегайте использования зарезервированных слов:
Имена таблиц и столбцов не совпадают с зарезервированными словами в SQL, это
необходимо, чтобы избежать конфликтов.
   3. Краткость и ясность имен столбцов:
Имена столбцов должны быть краткими, но информативными. Необходимо избенать
использования неясных сокращений.
   4. Использование первичных ключей:
Каждая таблица должна иметь первичный ключ, который уникально идентифицирует
каждую запись. Это обеспечивает уникальность данных и повышает эффективность
запросов.
   5. Определение внешних ключей:
Если есть связи между таблицами, то требуется явно определить внешние ключи для
поддержания целостности данных.
   6. Комментарии к таблицам и столбцам:
К таблицам       и   столбцам должны быть     оставлены подробные комментарии,
описывающие их назначение и ожидаемые типы данных.
   7. Выбор подходящих типов данных:

Для   каждого столбца    необходимо выбрать подходящий тип данных, чтобы
минимизировать использование памяти и повысить эффективность запросов.
   8. Соблюдение нормализации:
Чтобы избежать избыточности данных и обеспечить легкость обновления, необходимо
проектировать базу данных с учетом правил нормализации. Правила нормализации и
виды нормальных форм описаны в раздела “Нормализация базы данных”.
   9. Индексы для ускорения запросов:
Создавать индексы для столбцов, используемых в условиях WHERE или JOIN, для
повышения скорости выполнения запросов.
   10. Регулярные резервные копии:
Разработать систему регулярных резервных копий базы данных для предотвращения
потери данных в случае сбоев.
   11. Ограничения целостности данных:
Задавать   ограничения   целостности    данных   (например,   NOT   NULL), чтобы
гарантировать корректность данных.
   12. Использование символов в именах:
Не использовать пробелоы и специальные символы в именах таблиц и столбцов для
избежания проблем при написании SQL-запросов.
   13. Документация скрипта:
Необходимо предоставить документацию к скрипту, описывающую структуру базы
данных, используемые индексы и любые особенности реализации.


3.3. Нормализация базы данных
      При разработке реляционных баз данных проводится нормализация, что
представляет собой процесс приведения структуры отношений в базе данных к
соответствию нормальным формам.
Виды нормальных форм:
   ● Первая нормальная форма (1НФ). Когда отношение в базе данных соответствует
      первой нормальной форме, это означает, что каждый кортеж содержит лишь
      одно значение для каждого из его атрибутов в любом допустимом состоянии
      этого отношения.
   ● Вторая нормальная форма (2НФ). Вторая нормальная форма достигается в
      отношении базы данных, когда оно уже соответствует первой нормальной




                                          15
      форме, и при этом каждый атрибут, не входящий в состав ключа,
      функционально полностью зависит от всего ключа.
   ● Третья нормальная форма (3НФ). Третья нормальная форма достигается в
      отношении базы данных, когда оно уже соответствует второй нормальной
      форме, и при этом отсутствуют транзитивные функциональные зависимости
      между неключевыми атрибутами и ключевыми атрибутами.
   ● Номрмальная форма Бойса-Кодда (BCNF) или усиленная треться нормальная
      форма. Отношение считается находящимся в этой форме, если каждая не
      тривиальная и неприводимая слева функциональная зависимость в нем имеет
      потенциальный ключ в качестве своего детерминанта
   ● Четвертая нормальная форма (4НФ). Данная НФ описывает переменную
      отношения, находящуюся в этой форме, если она соответствует нормальной
      форме   Бойса — Кодда и не содержит нетривиальных многозначных
      зависимостей.
   ● Пятая    нормальная    форма    (5НФ).    Переменная    отношения считается
      находящейся в пятой нормальной форме, тогда и только тогда, когда каждая
      нетривиальная зависимость соединения в ней определена потенциальным
      ключом (или ключами) этого отношения.
   ● Доменно-ключевая номральная форма (ДКНФ).              Переменная отношения
      считается находящейся в ДКНФ, тогда и только тогда, когда каждое наложенное
      на неё ограничение является логическим следствием ограничений доменов и
      ограничений ключей, примененных к данной переменной отношения.
   ● Шестая     нормальня    форма    (6НФ).   Переменная    отношения   считается
      находящейся в шестой нормальной форме, тогда и только тогда, когда она
      удовлетворяет всем нетривиальным зависимостям соединения. Согласно
      данному определению, переменная находится в 6НФ, только если она является
      неприводимой, то есть не может быть подвергнута дальнейшей декомпозиции
      без потери информации.


4. Исключения из правил
      Исключения из установленных правил допустимы лишь в случае, если
разработчик способен обосновать и объяснить их необходимость.
