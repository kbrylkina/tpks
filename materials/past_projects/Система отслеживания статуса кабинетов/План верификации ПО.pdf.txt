2     СРЕДА ВЕРИФИКАЦИИ
2.1    Связь с другими процессами жизненного цикла ПО
Процесс верификации взаимодействует с другими процессами жизненного
цикла ПО посредством процесса управления конфигурацией ПО, получая
из него все входные данные и возвращая в него все выходные данные жиз-
ненного цикла ПО.
   Входными данными процесса верификации являются следующие выход-
ные данные процессов ЖЦ ПО:
    • Планы проекта;
    • Требования к ПО;

    • Исходный код;
    • Результаты испытаний.
    Выходными данными процесса верификации являются:
    • Сообщения о проблемах;

    • Тестовые примеры и процедуры;
    • Результаты прогона тестовых примеров (результаты испытаний);
    • Записи о ФИ;
    • Результаты анализов.

2.2    Организация и ответственности
В мероприятиях процесса верификации ПО принимают участие сотрудни-
ки проекта, имеющие различные роли в процессах ЖЦ ПО. Большинство
мероприятий процесса верификации проводится сотрудниками группы ве-
рификации, сотрудники других процессов привлекаются к участию в фор-
мальных инспекциях. Роли, выделяемые в контексте выполняемых меро-
приятий процесса верификации ПО, приводятся в подразделах раздела 3.




                                  3
2.3     Независимость
Независимость при выполнении мероприятий верификации обеспечивается
на персональном уровне, то есть для каждого верифицируемого объекта из
множества данных ЖЦ ПО сотрудник проекта, выполняющий мероприятие
по верификации, не участвует в создании данного объекта.
   Примеры:
   • автор объекта формальной инспекции не может быть инспектором в
     данной инспекции;
   • при проведении инспекции требований к ПО как целого инспектором
     не может быть ни один из авторов, участвовавших в разработке частей
     требований;

   • автор требований и автор кода, реализующего требования, не могут
     быть авторами тестовых примеров для верификации этих требований;
   • авторы требований, кода и тестовых примеров не могут быть авторами
     отчета об анализе покрытия кода тестами.

2.5     Методы верификации
Для проведения мероприятий верификации будут использоваться методы,
описанные ниже. Порядок применения этих методов детально описан в раз-
деле 3.

2.5.1   Испытания
Испытания – метод верификации, при котором на вход ПО подаются опре-
деленные в тестовых примерах входные воздействия, а результат работы
испытуемого ПО, полученный для данных входных воздействий, сравнива-
ется со значениями, ожидаемыми на основании требований. Тестовые при-
меры разрабатываются на основе требований к ПО таким образом, чтобы
обеспечить полное покрытие требований тестовыми примерами. В зависи-
мости от совпадения результатов работы ПО с ожидаемыми значениями,


                                   4
для каждого отдельного тестового примера определяется результат "Про-
шёл/Не прошёл"("Pass/Fail").
   Если существуют тестовые примеры с результатом "Не прошел"("Fail"),
открываются сообщения о проблемах.

2.5.2    Рассмотрение
Рассмотрение – метод верификации, при котором данным жизненного цик-
ла ПО дается экспертная оценка правильности. Все рассмотрения прово-
дятся в форме формальных инспекций.

2.5.3    Анализ
Анализ – метод верификации, при котором проводится документальное под-
тверждение корректности анализируемых данных жизненного цикла ПО.
Отличительным свойством анализа является воспроизводимость, т.е. ре-
зультаты анализа, проведенного по одной и той же процедуре для одних
и тех же данных жизненного цикла ПО, но разными людьми, будут иден-
тичными.
   Несоответствия, выявленные при проведении анализа, документируют-
ся в сообщениях о проблемах и таким образом передаются в процессы, ре-
зультаты которых подвергаются анализу.

2.5.4    Формальная инспекция
Формальная инспекция – форма проведения рассмотрений и некоторых ви-
дов анализов. «Формальная» означает, что результат инспекции является
основанием для изменения статуса документа в GitHub.
   В ходе формальной инспекции одним или несколькими специалиста-
ми (инспекторами) осуществляется независимая проверка соответствия ин-
спектируемых документов исходным документам. Для самоконтроля ин-
спектора при проведении формальных инспекций, как правило, применя-
ются заранее подготовленные и утвержденные проверочные перечни, раз-
личные для разных типов объектов инспекции. Ответы на вопросы про-
верочного перечня даются инспектором на основании экспертной оценки
объектов формальной инспекции.

3.1.2   Критерии начала мероприятия
Одновременно выполнены следующие условия:
   • Установлены базовые версии входных данных, на основе которых раз-
     работаны объекты формальной инспекции.
   • По мнению автора, все изменения во все данные ЖЦ, требующие из-
     менения по ЗИ, внесены.

3.1.3   Процедура выполнения мероприятия
Инициализация Автор помещает объекты инспекции в GitHub. Если
формальная инспекция еще не проводилась, Автор создает запись о фор-
мальной инспекции из запроса на изменение, связывает ее с необходимыми
проверочными перечнями, входными данными, на основании которых раз-
рабатывались объекты инспекции, и справочными данными. GitHub авто-
матически устанавливает связь формальной инспекции с последними вер-
сиями всех единиц конфигурации, измененных по ЗИ, как с подлежащими
инспекции версиями объектов инспекции.

Экспертиза и обсуждение Инспекторы проверяют существенные ха-
рактеристики объектов инспекции, указанных на титульном листе записи о
формальной инспекции. Обнаруженные несоответствия должны быть точно
локализованы, сформулированы и записаны; при этом следует стремиться
к таким формулировкам, которые идентифицируют проблемы, но не пред-
лагают их решения. Каждое найденное несоответствие следует оформлять
отдельно в списке замечаний записи о формальной инспекции в GitHub.

Регистрация результатов Ведущий завершает заполнение проверочных
перечней, связанных с ФИ. При проведении повторной формальной инспек-
ции ответы на вопросы проверочных перечней должны быть актуализиро-
ваны, т.е. должны отражать состояние рассматриваемых версий объектов
инспекции.
   Если хотя бы одно из замечаний находится в состоянии «НАЗНАЧЕНО»,
Ведущий переводит запись о формальной инспекции в состояние «ПЕРЕ-
РАБОТКА» ("REWORK"), в противном случае Ведущий переводит запись


                                  6
о формальной инспекции в состояние «ЗАВЕРШЕНА» ("COMPLETED")
и связанный с ней ЗИ в состояние «ЗАВЕРШЕН» ("COMPLETED").

3.1.4   Критерии окончания мероприятия
Выполнено одно из следующих условий:
   • Формальная инспекция переведена в состояние «ЗАВЕРШЕНА» и
     связанный с ней ЗИ переведен в состояние «ЗАВЕРШЕН».
   • Формальная инспекция переведена в состояние «ПЕРЕРАБОТКА».

3.1.5   Выходные данные
   • Сообщения о проблемах;
   • Запись о формальной инспекции (актуализированная):

        – Титульный лист формальной инспекции;
        – Список замечаний;
        – Заполненные проверочные перечни.

3.1.6   Исправление несоответствий
В процессе переработки объектов инспекции по замечаниям проведенной
формальной инспекции для каждого зафиксированного в записи о фор-
мальной инспекции замечания в состоянии «НАЗНАЧЕНО»:
   • Если Автор согласен с наличием зафиксированного несоответствия,
     он вносит необходимые изменения в объекты инспекции и переводит
     замечание в состояние «ИСПРАВЛЕНО».
   • Если Автор считает, что исправление несоответствия нецелесообраз-
     но и несоответствие должно быть отклонено либо исправление должно
     быть отложено, то Автор снабжает замечание комментарием и пере-
     водит его в состояние «ОБСУЖДЕНИЕ».

3.2.2     Критерии начала мероприятия
Одновременно выполнены следующие условия:

   • Базовые версии для артефактов тестируемых требований к ПО уста-

3.2.3     Процедура выполнения мероприятия
Тест-инженер разрабатывает тестовые примеры для проверки соответствия
реализации требованиям к ПО. Тестовые примеры должны покрывать как
позитивные, так и негативные сценарии использования системы.
   При разработке тестовых примеров следует создавать:

   • Юнит тесты - для проверки отдельных модулей или компонентов си-
     стемы в изоляции. Юнит тесты пишутся на языке Go с использова-
     нием пакета testing и библиотеки testify/assert. Каждый юнит тест
     представляет собой функцию с именем вида TestXXX, которая прини-
     мает параметр t *testing.T. Внутри функции выполняются проверки
     с помощью утверждений assert, например:

        assert.Equal(t, expectedResult, actualResult, "Результаты должны совпадать")

        Юнит тесты размещаются в файлах с суффиксом _test.go рядом с
        тестируемым кодом.
   • Интеграционные тесты - для проверки взаимодействия между моду-
     лями системы. Интеграционные тесты также пишутся на Go с исполь-
     зованием пакетов testing и testify. Однако, в отличие от юнит тестов,
     они могут задействовать сразу несколько компонентов системы, в том
     числе внешние зависимости, такие как базы данных, очереди сообще-
     ний и т.д.
        Для изоляции тестов от внешних зависимостей используются техники,
        такие как:
          – Создание фейковых реализаций интерфейсов (заглушек)
          – Поднятие контейнеров Docker со всеми необходимыми сервисами
            для теста
          – Использование легковесных реализаций зависимостей (например,
            база данных в памяти)




                                     8
    Тестовые примеры должны быть автоматизированы там, где это воз-
можно, чтобы обеспечить возможность регрессионного тестирования. Для
запуска тестов используется либо непосредственно команда go test, либо
CI/CD система (GitHub Actions).
    Для выполнения тестов используется тестовый стенд - среда, макси-
мально приближенная к промышленной, но изолированная от нее. Тесто-
вый стенд должен быть сконфигурирован в соответствии с требованиями
к аппаратному и программному обеспечению для корректного проведения
испытаний. Конфигурация стенда описывается в виде кода (infrastructure
as code) и хранится в репозитории вместе с исходным кодом проекта.
    Если в ходе разработки тестовых примеров или их неформального про-
гона обнаружены несоответствия во входных данных процесса, то Тест-
инженер должен открыть соответствующие СП.
    По окончании разработки тестовых примеров Тест-инженер помещает
их в GitHub в директорию с исходным кодом проекта.

3.2.4   Критерии окончания мероприятия
Тестовые примеры разработаны, найденные несоответствия во входных дан-
ных процесса описаны посредством СП. Тестовые примеры идентифициро-
ваны в GitHub.

3.2.5   Выходные данные
   • Тестовые примеры;
   • Сообщения о проблемах.

3.3     Испытания ПО (формальный прогон тестовых при-
        меров)
3.3.1   Входные данные
   • План верификации ПО;
   • Исходный код;
   • Тестовые примеры.

3.3.2   Критерии начала мероприятия
Базовые версии для исходного кода и тестовых примеров установлены.

3.3.3   Процедура выполнения мероприятия
Тест-инженер извлекает тестовые примеры из GitHub и осуществляет их
формальный прогон с использованием соответствующей среды испытаний
на базовой версии исходного кода.


                                  9
   Тест-инженер помещает результаты формального прогона в GitHub. Каж-
дая версия результатов прогона должна трассироваться на версии тестовых
примеров и версии исходного кода. Такую трассировку следует осуществ-
лять созданием текстового файла с указанием идентификаторов теста, ис-
ходного кода и результатов прогона с последующим размещением этого
файла в GitHub в одной агрегации с результатами прогона.
   Если в ходе формального прогона тестовых примеров обнаружены несо-
ответствия во входных данных процесса, то Тест-инженер должен открыть
соответствующие СП.

3.3.4   Критерии окончания мероприятия
Тестовые примеры прогнаны с использованием соответствующей среды ис-
пытаний, найденные несоответствия во входных данных процесса описаны
посредством СП. Результаты прогона тестовых примеров идентифицирова-
ны в GitHub.

3.3.5   Выходные данные
   • Результаты испытаний ПО;

   • Сообщения о проблемах.

3.4     Анализ покрытия кода тестами
3.4.1   Входные данные
   • План верификации;
   • Требования к ПО;

   • Исходный код ПО;
   • Тестовые примеры.

3.4.2   Критерии начала мероприятия
Все тестовые примеры разработаны, прогнаны с использованием соответ-
ствующей среды испытаний. Тестовые примеры и результаты их прогона
идентифицированы в GitHub.

3.4.3   Процедура выполнения мероприятия
Инженер прогоняет тестовые примеры на инструментированной версии ПО,
получая данные о покрытии кода тестами. На основе полученных данных
инженер средствами GitHub формирует отчет о покрытии кода тестами.
   Используя сформированный отчет, инженер проводит анализ покрытия.
Каждый случай непокрытия элемента исходного кода следует отнести к
одному из следующих классов и при необходимости открыть СП:


                                 10
    • Неполнота тестовых примеров. Следует открыть СП для принятия ре-
      шения о модификации существующих или разработке новых тестовых
      примеров.
    • Неполнота требований. Следует открыть СП для принятия решения
      либо об удалении кода, для которого не существует требований, ли-
      бо о модификации существующих или разработке новых требований,
      позволяющих разработать основанные на требованиях тестовые при-
      меры.
    • Неиспользуемый код. Следует открыть СП для принятия решения об
      удалении кода.

   При выполнении анализа инженер заполняет отчет об анализе покрытия
кода тестами. В отчете должны быть идентифицированы версии требований
к ПО, кода и тестов, использованных для получения данных о покрытии,
перечислены случаи непокрытия и соответствующие СП.

3.4.4    Критерии окончания мероприятия
Отчет об анализе покрытия кода тестами создан и идентифицирован в
GitHub, все найденные несоответствия зафиксированы в сообщениях о про-
блемах.

3.4.5    Выходные данные
    • Отчет об анализе покрытия кода тестами;

    • Сообщения о проблемах.


4       КРИТЕРИИ ПЕРЕХОДА
Детальные критерии для начала и завершения каждого из мероприятий,
входящих в процесс верификации ПО, описаны в соответствующих подраз-
делах "Критерии начала мероприятия"и "Критерии окончания мероприя-
тия"различных секций главы "План верификации".


5       ИНСТРУКЦИИ ПОВТОРНОЙ ВЕРИФИКА-
        ЦИИ
Процесс управления конфигурацией ПО гарантирует, что для внесения лю-
бого изменения в данные жизненного цикла ПО должно быть создано со-
общение о проблеме. При рассмотрении сообщений о проблемах, группа
управления изменениями определяет самый ранний этап жизненного цикла
ПО, где требующееся изменение начинает влиять на результаты выполняе-
мых процессов жизненного цикла ПО и создает запросы на изменения для


                                  11
этого этапа и всех последующих этапов жизненного цикла ПО, затрагива-
емых изменениями. Список тестовых примеров, которые следует изменить
и/или перепрогнать в связи с изменениями, определяется при рассмотрении
сообщений о проблемах. Этот процесс гарантирует, что необходимые изме-
нения будут внесены и верифицированы для каждого из этапов жизненного
цикла, начиная с этапа, где изменение начинает влиять на результаты вы-
полнения процесса.
