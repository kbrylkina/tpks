                    1. Определения и Термины

1. BPMN (Business Process Model and Notation): Система условных обозначений и их
  описания в формате XML для моделирования бизнес-процессов.
2. LaTeX: Язык верстки документов, широко используемый для создания научных и академически
  работ благодаря его способности точно форматировать сложные документы.
3. CASE-средства (Computer-Aided Software Engineering): Комплекс инструментов и
  методов программной инженерии, направленных на разработку и проектирование программног
  обеспечения с целью повышения качества и облегчения процесса обслуживания программных
  продуктов.
4. GitHub: Веб-сервис для хостинга и совместной разработки проектов на основе системы
  контроля версий Git, обеспечивающий инструменты для управления задачами и кодовым
  аудитом.

  Ниже представлена BPMN схема жизненного цикла.
  При создании схемы использовались следующие элементы:

  – Прямоугольник с тремя отсеками (деятельность с необходимыми артефактами):

        – Сверху обозначено название действия.
        – По середине - артефакты, требующиеся для выполнения действия.
        – Внизу - артефакты, являющиеся результатом выполнения действия.

  –     - это промежуточные события-сообщения (message events), показывающие получение
      или отправку сообщений в ходе выполнения процесса.
  –     - это промежуточные простые события (plain events) использующиеся, чаще всего,
      для того, чтобы показать начало или окончание процесса.
  –     - это оператор исключающего «или», управляемый данными (data-based exclusive
      gateway).
  –       - это поток управления, задающий порядок выполнения действий.
  –      - это поток сообщений, показывающий, какими сообщениями обмениваются участники.

2.1 Разработка требований

Цели процесса

  – Разработка требований к ПО высокого уровня
  – Разработка производных требований к ПО высокого уровня


                                           4
Условия входа

   Процесс начинается при выполнении одного из следующих условий:

  1. Запрос на изменение требований к ПО назначен ответственному разработчику с установленным
     базовыми версиями всех входных данных.
  2. Несоответствия обнаружены в результате формальной инспекции запроса на изменение
     требований к ПО.


Входные данные процесса разработки требований

   – Требования к системе
   – План разработки ПО (настоящий документ)
   – Описание архитектуры системы
   – Запрос на изменение
   – Запись о формальной инспекции требований к ПО


Описание процесса

  1. Перевод запроса на изменение в соответствующее состояние и уведомление руководителя
     проекта о начале работы.
  2. Определение документов требований к ПО, подлежащих изменению, созданию или
     удалению.
  3. Создание сообщения о проблеме (при обнаружении несоответствий во входных данных)
  4. Установление трассировочных связей между требованиями к ПО и соответствующими
     требованиями к системе.
  5. Извещение руководителя проекта о завершении работы после помещения результатов
     в систему поддержки разработки.


Условия выхода

   – Зарегистрированы все несоответствия в сообщениях о проблемах.
   – Завершены работы, начатые по запросу на изменение или результатам формальной
     инспекции.
   – Руководитель проекта извещен о завершении работ.

2.2 Проектирование

Цели процесса

   – Определение архитектуры ПО.
   – Разработка требований к ПО низкого уровня.
   – Разработка производных требований к ПО низкого уровня.


Условия входа

   Процесс начинается при выполнении одного из следующих условий:
  1. Запрос на изменение описания проекта ПО назначен ответственному разработчику с
     установленными базовыми версиями всех входных данных.
  2. Несоответствия обнаружены в результате формальной инспекции запроса на изменение
     описания проекта ПО.


Входные данные процесса проектирования

   – Требования к ПО
   – План разработки ПО (настоящий документ)
   – Запрос на изменение
   – Запись о формальной инспекции требований к ПО
   – Стандарт на проектирование ПО


Описание процесса

  1. Перевод запроса на проектирование в активное состояние и информирование руководителя
     проекта о начале этапа проектирования.
  2. Определение и анализ документов требований к ПО, которые будут использоваться в
     качестве основы для проектных решений.
  3. Разработка предварительных проектных решений и создание соответствующих документов,
     включая схемы, модели и спецификации.
  4. Установление трассировочных связей между требованиями к ПО и разрабатываемыми
     проектными решениями для обеспечения соответствия и полноты.

                                          6
  5. Регулярное взаимодействие с руководителем проекта для обсуждения прогресса и внесения
     необходимых корректировок в проектные решения.
  6. Применение стандартов на проектирование ПО для обеспечения качества и соответствия
     требованиям проекта.
  7. Проведение анализа возможных рисков и проблем, связанных с проектными решениями,
     и разработка мер по их устранению или минимизации.
  8. Завершение проектирования путем утверждения окончательных проектных документов
     и передача их в разработку с последующим уведомлением руководителя проекта.
  9. Поддержание документации в актуальном состоянии в системе поддержки разработки,
     обновление трассировочных связей и документов по мере необходимости.


Условия выхода

   – Все несоответствия зарегистрированы в сообщениях о проблемах.
   – Завершены работы, начатые по запросу на изменение или по результатам формальной
     инспекции.
   – Руководитель проекта извещен о завершении работ.


Выходные данные процесса проектирования ПО

   – Описание проекта ПО
   – Сообщения о проблемах

2.3 Кодирование

Цели процесса

   Разработка исходного кода, соответствующего требованиям к ПО низкого уровня, обеспечивающе
трассируемость, верификацию, непротиворечивость и корректное исполнение требований.


Условия входа

   Процесс начинается при выполнении одного из следующих условий:

  1. Запрос на изменение исходного кода ПО назначен ответственному разработчику с установленны
     базовыми версиями всех входных данных.
  2. Несоответствия обнаружены в результате формальной инспекции запроса на изменение
     исходного кода ПО.

Входные данные процесса проектирования

  – Требования к ПО
  – План разработки ПО (настоящий документ)
  – Описание проекта ПО
  – Запрос на изменение
  – Запись о формальной инспекции требований к ПО
  – Стандарт на кодирование ПО

Описание процесса
  1. Разработка Исходного Кода:

       – Разработчик должен создать исходный код для каждого модуля программного
         обеспечения (ПО).

  2. Регистрация Исходного Кода:

       – После разработки, исходный код необходимо зарегистрировать.

  3. Определение Данных:

       – Процесс должен включать определение необходимых данных для ПО.

  4. Создание Базы Данных:

       – Разработчик создает базу данных, которая будет использоваться в ПО.

  5. Заполнение Базы Данных:

       – База данных и другие файлы данных заполняются соответствующими значениями.

  6. Дополнительные Работы:

       – Выполняются любые другие работы, необходимые для реализации проекта.

  7. Использование Инструментария:

       – В процессе разработки используются инструменты и средства, описанные в разделе
         ”Среда разработки ПО”.


Условия выхода

  – Все несоответствия зарегистрированы в сообщениях о проблемах.
  – Завершены работы, начатые по запросу на изменение или по результатам формальной
    инспекции.
  – Руководитель проекта извещен о завершении работ.

                             4. Среда Разработки


4.1 Документация Требований
   Для создания документации требований применяется LaTeX. В качестве текстового редактора
используется Visual Studio Code.

4.2 Проектирование
   Проектирование системы осуществляется с использованием CASE-инструментов, предоставляющ
возможности визуализации через draw.io. Это обеспечивает гибкость и точность в представлении
архитектурных решений.

4.3 Разработка
  1. Для серверной части проекта используется Visual Studio Code с расширением для языка
     Go, обеспечивающим интегрированную среду разработки.
  2. В проектировании базы данных применяется DataGrip, обеспечивающий удобный интерфейс
     для работы с базами данных и их схематическое представление.
