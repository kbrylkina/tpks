## 0. Как читать

**Пометки источников**

- **[К:123]**: строка 123 файла `materials/lectures/lectures_konspekt.txt` (конспект Б21-504). Текст «в кавычках» дан дословно, с опечатками оригинала. В [квадратных скобках] мои правки и пояснения. Если в конспекте список по пунктам, в цитате пункты записаны в строку, и знаки между ними («;», «:») поставлены мной.
- **[Г]**: гайд старших курсов `notes/00_guide_from_seniors.md`, версия от 17:27, где разделы «Системные требования» и «Свойства требований» приведены дословно.

- **(вывод)**: следует из конспекта или гайда, но прямо там не сказано.
- **(рекомендация)**: моё предложение для команды, не из источников.

### 1.2 Термины: жизненный цикл, требования, проектирование, код, интеграция

- **Процессы ЖЦ ПО.** В конспекте перечислено 8 процессов [К:19–27]. Интеграции в этом списке нет, хотя это отдельный процесс (см. 2.1).

- **Системные требования.** «Системные требования относятся ко всей системе целиком. (Если это самолёт, то на весь самолёт, но, конечно, на весь самолёт системные требования не делают).» [К:41]. В гайде: «Короче тут вам нужно написать требования ко всей системе».

- **Требования к ПО, они же спецификация требований и требования высокого уровня (ВУ).** «На вход процесса разработк[и] требований мы получаем то, что имеет отношение к тому, что мы собираемся делать в проекте. Кроме системных требований у нас ещё есть интерфейсы. На основании этого мы пишем требования к софту. … В итоге мы получаем спецификацию требований, требования высокого уровня.» [К:41–44]. В ВУ нельзя указывать детали реализации, и «в высоком уровне компонентов нет» [К:63]. В гайде: «Требования к ПО — это требования высокого уровня, код в них упоминать нельзя».
  - По DO-178C (не из конспекта): ВУ — требования к ПО, полученные анализом системных требований, требований, связанных с безопасностью, и архитектуры системы.

- **Требования низкого уровня (НУ).** Появляются при проектировании: «Тут должны быть определены программные интерфейсы компонент, потоки данных и потоки управления между ними и требования низкого уровня к компонентам.» [К:71]. «…в требованиях низкого уровня можно указывать детали реализации, в требованиях высокого нельзя, (но не конкретные алгоритмы), так как проверить тестами конкретные алгоритмы нельзя.» [К:63]. В гайде: «Код появляется только в требованиях низкого уровня, на этапе проектирования».
  - По DO-178C (не из конспекта): НУ получают из ВУ, производных требований и проектных ограничений. По ним исходный код можно написать без дополнительной информации.

- **Требование о взаимодействии.** «При определении требований низкого уровня (например при описании взаимодействия одного компонента с другим) надо так и писать “требование о взаимодействии”, так как в высоком уровне компонентов нет.» [К:63]. «Если две компоненты взаимодействуют, [то] необходимо писать требование на это взаимодействие» [К:80].

- **Производные требования.** «Производные требования не трассируется на требования к ПО. Каждый процесс разработки, кроме кодирования и интеграции, могут породить производные требования, то есть те, у которых есть выход.» [К:66].
  Пояснение: такие требования не трассируются на уровень выше. Для НУ уровень выше — требования к ПО, для ВУ — системные требования. Слова «те, у которых есть выход» по смыслу означают процессы, на выходе которых получаются требования: разработку требований и проектирование.
  - По DO-178C (не из конспекта): это требования, которые порождены процессами разработки ПО и (а) не трассируются напрямую на требования уровнем выше и/или (б) задают поведение сверх того, что задано системными требованиями или требованиями к ПО уровнем выше. Для каждого производного требования указывается причина его появления, и оно передаётся в системные процессы, включая оценку безопасности системы.

- **Описание проекта.** «Описание проекта включает в себя: архитектура (компоненты, программы); процессы (их может быть несколько, они могут взаимодействовать по какому-то сценарию); физический аспект (распределение кода по оперативной памяти, но не обязательно только в оперативной). В наших проектах можно не учитывать третий аспект, но первые два должны быть.» [К:50–56]. Это вход процесса кодирования [К:355].
  - По DO-178C (не из конспекта): Design Description (§11.10), включает архитектуру ПО и НУ.

- **Архитектура ПО; компонент, подкомпонент, модуль.** Архитектуру разрабатывают первой («процесс проектирования архитектуры ПО»), и «После этого процесса можно начать параллельную разработку» [К:70]. В итоге получается «пирамидальное дерево, где в вершине находятся компоненты высокого уровня, ниже их подкомпоненты и так далее» [К:74]. Модуль — «самый низший элемент компонента (компонент - подкомпонент - модуль) либо просто как синоним компоненту» [К:72]. «Для недекомпозируемого компонента должен быть определён файл исходного кода, … в котором определяются функции и данные компонента» [К:73]. «Для любых компонент данные, функции и типы данных, не входящие в интерфейс компоненты, должны быть скрыты от других компонент» [К:75].

- **Прочность модуля по Майерсу.** «Функциональная прочность по Майерсу - наивысшая степень прочности. Но тут стоит рассматривать информационную прочность. То есть все взаимодействующие функции связаны между собой. Делаем модуль таким, чтобы минимизировать связь с другими компонентами.» [К:49]. «Низшая прочность по Майерсу это прочность по совпадению, когда мы случайным принципом в процессе кодирования приняли решения объединить куски кода.» [К:78]. Источник: Майерс, «Надёжность программного обеспечения» [К:403].

- **Связь (связность) по данным и по управлению.** «Связь по данным это когда в одной компоненте данные передаются, а в другую компоненту входят.» [К:79]. Число связей по данным и по управлению нужно сводить к минимуму, это упрощает внесение изменений [К:76–77]. В лекции 8 даны определения: «Связность по данным - Зависимость компонента ПО от данных, не находящихся под исключительным контролем данного компонента»; «Связность по управлению - Способ или степень влияния, оказываемого одним компонентом программы на работу другого компонента» [К:851–852].

- **Кодирование.** «Кодирование - это переработка описания проекта в исходный код. Хорошо проработанное описание проекта существенно упрощает процесс кодирования.» [К:354].

- **Свойства исходного кода.** Корректность («соответствие требованиям, отсутствие противоречий между исходными данными процесса и результатами процесса»), трассируемость («На уровне модуля», «На уровне функции (рекомендуется)»), верифицируемость («существует конечная процедура, позволяющая оценить соответствие»), модифицируемость, переносимость [К:365–372]. Трассируемость кода бывает двух видов: «На уровне файла исходного кода (каждый файл исходного кода трассируется на реализованные в нём требования низкого уровня)» и «На уровне функции (идентификаторы требований низкого уровня, реализуемых в этой функции, перечислены в “шапке” функции)» [К:376–377].

- **Стандарт на кодирование.** «Недостатки языка компенсируются стандартом на кодирование. Чем больше недостатков в выбранном языке, тем объёмнее стандарт на кодирование.» [К:434]. Содержит правила оформления исходного кода, правила именования, правила объявления и определения, ограничения на конструкции языка, шаблоны файлов (.h, .c) [К:437–442]. Это вход кодирования, в конспекте он назван «стандарт процесса кодирования» [К:355].

- **Интеграция.** «Интеграци[я] ПО: Получение исполняемого объектного кода из исходного кода (компиляция и компоновка) и файла компонента параметрических данных. Интеграция ПО и аппаратуры: Загрузка исполняемого объектного кода в целевой вычислитель.» [К:488–491]. Подробно в разделе 3.

- **Исполняемый объектный код.** Определения в конспекте нет. Получается из исходного кода компиляцией и компоновкой [К:489], это результат интеграции [К:494], загружается в целевой вычислитель [К:491].

- **Объектный код.** «Объектный код не находится под УК (процесс управления конфигурацией): компоновка производится совместно с компиляцией (объектный код не хранится)» [К:532].

- **Компонент параметрических данных.** «Включает в себя структуру из отдельных элементов, каждому из которых может быть назначено конкретное значение. Каждый элемент обладает атрибутами, такими как тип, диапазон или набор допустимых значений, которые могут: влиять на пути выполнения Исполняемого Объектного Кода; активность или деактивность компоненты ПО и функции; адаптировать вычисления, выполняемые ПО, к конкретной конфигурации системы; использоваться в качестве данных для вычисления; определять распределение времени и памяти при обособлении; обеспечивать начальные значения для компонентов ПО» [К:500–507].
  - По DO-178C (не из конспекта): parameter data item — данные, которые в виде файла компонента параметрических данных влияют на поведение ПО, **не меняя исполняемый объектный код**, и управляются как отдельная единица конфигурации. «Обособление» здесь означает partitioning, то есть разделение времени и памяти между частями ПО.

- **Целевой вычислитель.** В него загружается исполняемый объектный код [К:491]. Идеальная среда тестирования — «целевой вычислитель с загружаемым ПО» [К:626].

- **Загрузчик: внешний и резидентный.** «Загрузчик, который выполняет загрузку исполняемого объектного кода в целевой вычислитель – внешний загрузчик. Загрузчик, который переписывает ПО с флеш-памяти в оперативную память, например, при старте работы микроконтроллера – резидентный загрузчик» [К:537–538]. «Резидентный загрузчик - часть ПО» [К:527].

- **make-файл и командные файлы для сборки.** «Требуется осторожное использование make-файлов: их следует использовать лишь для сборки»; «make-файл должен гарантировать полную перекомпиляцию (удаление имеющихся объектных файлов)» [К:550–551]. «Командные файлы для сборки» — один из выходов интеграции [К:494].

- **Стандартные библиотеки.** «Стандартные библиотеки запрещены к использованию, если для них не выполняются цели КТ-178В: 1) Не разработаны требования 2) Отсутствует описание проекта 3) Не проведена верификация. Пример: библиотека математических функций, поставляемая с компилятором.» [К:542–546].

- **Уровень ПО.** В конспекте есть пометка «Посмотреть про цели уровней ПО.» [К:249]. Уровень ПО — один из входов анализа структурного покрытия, и критерии этого покрытия «определены уровнем ПО» [К:759, 773]. «Полнота набора тестовых примеров для покрытия требования не зависит от уровня ПО» [К:774].
  - По DO-178C (не из конспекта): уровни от A до E по тяжести последствий отказа: A — катастрофические, B — опасные, C — значительные, D — незначительные, E — без влияния на безопасность. От уровня зависят: какие цели обязательны, где требуется независимость, к какой категории (КК1 или КК2) относятся данные и какой критерий структурного покрытия нужен.

- **Окружение процесса.** В конспекте встречается только в заголовках к потерянным схемам: «Окружение процесса верификации» [К:127] и «Окружение формальной инспекции» [К:233]. После второго заголовка перечислены участники: автор, ведущий, инспекторы. (вывод) Окружение процесса — это схема его связей: откуда приходят входы, куда уходят выходы, кто участвует. В гайде это раздел 3.1 Стандарта на разработку требований.

### 1.3 Термины: управление конфигурацией

- **Категория контроля: КК1 и КК2.** «к КК1 относятся те части проекта, которые могут быть изменены только путём запроса на изменение после создания базовой версии этого компонента проекта. В проекте есть и КК1 и КК2, это не относится ко всему проекту целиком!!! Например тесты относятся к КК1, а протокол тестирования к КК2.» [К:16]. «Категория контроля 1 или КК1 это одна категория мероприятий контроля, а КК2 другая. Принципиальное отличие в том, что ничего поменять в КК1 без запроса на изменение нельзя.» [К:61].
  Почему протокол тестирования относится к КК2: «сам протокол мы не будем менять, мы делаем сообщение о проблеме, потом группа управления изменениями рассматривает и принимает решение о том, в коде ошибка или в требованиях и создаёт запрос на изменение, но не протокола, а кода или требования» [К:639].
  О связи КК2 с базовой версией автор конспекта пишет неуверенно: КК2 «не отменяет возможности провести процесс верификации, а значит, тут как я понял, и не отменяет наличие базовой версии» [К:246]. По DO-178C см. 4.10.

- **Базовая версия.** «Если отсутствие ошибок подтверждено, то проверяемый объект получает статус базовой версии. Если ошибки найдены, то отправляется запрос на изменение.» [К:243]. «Если несоответствия не найдены, то продукт получает базовую версию.» [К:258]. После того как создана базовая версия, объект КК1 меняется только по ЗИ [К:16]. В гайде: «Базовая версия — самый новый коммит в ветке master (так можно писать только в плане УК ПО)».
  - По DO-178C (не из конспекта): утверждённая и зарегистрированная конфигурация одной или нескольких единиц конфигурации. Служит основой для дальнейшей разработки и меняется только через процедуры контроля изменений.

- **Запрос на изменение (ЗИ).** Определения в конспекте нет. Как ЗИ используется:
  - без ЗИ нельзя менять объект КК1 после базовой версии [К:16, 61];
  - ЗИ отправляется, если на ФИ найдены ошибки [К:243];
  - ЗИ создаёт группа управления изменениями по сообщению о проблеме, причём на код или требование, а не на протокол [К:639];
  - ЗИ можно считать сам список несоответствий или протокол ФИ [К:302];
  - ЗИ — вход процесса кодирования [К:355] и вход повторной ФИ, где проверяют, что он выполнен [К:297];
  - чтобы изменить тест, нужен ЗИ [К:725].

  В гайде: ЗИ — это issue в репозитории, но так можно писать только в Плане УК ПО.

- **Сообщение о проблеме (СП).** Определения в конспекте нет. СП создают в таких случаях:
  - ведущий выносит спор автора и инспектора за рамки ФИ: «В этом случае создаётся сообщение о проблеме, где излагается суть этой проблемы» [К:255];
  - на ФИ выявлены несоответствия [К:301–302];
  - тест дал не тот результат: протокол не меняют, вместо этого пишут СП [К:639];
  - «Если что-то непокрыто - можно написать сообщение о проблеме» [К:832].

  Кроме того, СП — выход процесса кодирования [К:358]. В гайде: СП — это issue (только в Плане УК ПО).
  - По DO-178C (не из конспекта), §11.17: СП фиксирует аномальное поведение ПО, несоблюдение планов и стандартов, недостатки данных ЖЦ, а также то, как проблему решили. Содержит: где обнаружена проблема (ЕК или деятельность процесса); какие ЕК надо изменить (или какой процесс); описание проблемы, по которому её можно понять и решить; описание корректирующего действия.

- **Процесс контроля изменений.** «Схема процесса верификации: найти ошибку - зарегистрировать её - запустить процесс контроля изменений.» [К:97].

- **Группа управления изменениями.** Рассматривает СП и «принимает решение о том, в коде ошибка или в требованиях и создаёт запрос на изменение» [К:639]. (Не из конспекта: это аналог Change Control Board.)

- **СКУ.** «Система конфигурационного управления» [К:13]. В ней сохраняется запись о ФИ [К:279].

- **Единица конфигурации (ЕК).** В конспекте нет, есть только в списке сокращений гайда.
  - По DO-178C (не из конспекта): configuration item — один или несколько программных компонентов либо элементов данных ЖЦ ПО, которые для целей УК рассматриваются как одно целое.

- **Идентификация.** Термина в конспекте нет, но само действие описано в организации ФИ: «зафиксировать текущее состояние инспектирования объекта (номер версии, дата)»; «фиксируются исходные документы (время, версия)» [К:201–202]; «ведущий создаёт идентификацию объекта и данных, поступающих на ФИ» [К:258].

### 1.4 Термины: верификация и ФИ

- **Верификация.** «Верификация - оценка соответствия результатов тем исходным данным и правила[м], на основании которых они получены.» [К:119]. «Верификация - это сделали то, что надо.» [К:109]. Цель: «убедиться, что нет ошибок и исправить их в случае нахождения. Или по другому целью процесса является снизить количество ошибок до той степени, чтобы их наличие не влияло на процесс эксплуатации программы.» [К:91]. «Доказать отсутствие ошибок можно только в частном случае.» [К:94]. «Ошибок, которые могут привести к критическим проблемам, быть не должно.» [К:100].
  - По DO-178C (не из конспекта): оценка результатов процесса на правильность и согласованность с входами и стандартами этого процесса. Задача процесса верификации — обнаружить ошибки и сообщить о них. Исправляют ошибки процессы разработки; это уточняет формулировку из К:91.

- **Валидация.** «Валидация - проверка требований самого верхнего уровня. Т.е. если речь идёт о проверки требований этого уровня, то мы производим процесс валидации, а не верификации.» [К:106]. «Валидация - сделали то, что правильно.» [К:109].
  - По DO-178C (не из конспекта): подтверждение того, что требования правильные и полные. Выполняется на уровне системы.

- **Ошибка по Майерсу.** «в программе есть ошибки, если её поведение не отвечает ожиданиям пользователя» [К:103]. «Причиной ошибки в тесте может быть ошибка в коде, ошибка в тесте и ошибка в требовании.» [К:135].

- **Методы (мероприятия) верификации.** «Методы верификации (для валидации тоже подходят): 1. Рассмотрения 2. Анализы 3. Испытания» [К:112–115]. Рассмотрения и анализы «Обнаруживают несоответствия результатов процессов ЖЦ ПО их входным данным и стандартам». Их проводят «для: а) планов и стандартов б) результатов разработки в) (некоторых) результатов верификации» [К:139–143]. Тестирование — «часть процесса верификации» [К:164] и «соответствует мероприятию испытаний» [К:557].

- **Рассмотрение.** «Рассмотрения, в отличии от анализов, являются экспертной оценкой, то есть проводятся экспертом.» [К:146]. Примеры: оценка того, «соответствует ли требование более высокоуровневому требованию» [К:152]; «оценка осмысленности комментариев» [К:155].

- **Анализ.** «Анализ же даёт объективную оценку (результаты анализа должны быть повторяемы).» [К:149]. Пример — анализ трассировки, который «проверяет проставлены ли ссылки на конкретные требования. Ссылки либо есть, либо нет, это и есть объективная оценка.» [К:152].

- **Независимость.** «Независимость тестирования! 1. сделал один - проверил другой 2. автор кода никогда не разрабатывает тесты 3. способы обеспечения: а) на персональном уровне б) на уровне организации или подразделения» [К:181–186]. «Независимость рекомендуется использовать даже если это затруднительно.» [К:189]. Для ФИ: «Люди, которые участвовали в разработке не должны входить в формальную инспекцию» [К:208].
  - По DO-178C (не из конспекта): независимость означает разделение ответственности ради объективной оценки. В верификации проверку выполняет не разработчик проверяемого элемента. В гарантии качества у проверяющего должны быть ещё и полномочия добиться корректирующих действий.

- **Формальная инспекция (ФИ).** «Формальная инспекция - это организованная форма выполнения рассмотрений и некоторых анализов.» [К:220]. «Такого термина в ДО нет. Это придумка команды преподавателя.» [К:197]. Основана на IEEE 1028-2008 и IEEE 12207-2008 [К:223]. Признаки: «Документированная процедура; Командное ролевое участие; Регистрация результатов» [К:228–230]. Подробнее в п. 8.2.

- **Запись ФИ и протокол ФИ.** «Создаётся запись формальной инспекции - то есть нам надо зарегистрировать то, что мы проводим формальную инспекцию. (Состав участников, время проведения)» [К:203]. ФИ «после обсуждения всех несоответствий, составляет протокол, в рамках которого начинается регистрация изменений» [К:214]. «Запись о ФИ сохранена в СКУ» [К:279].

- **Несоответствие и его отметки.** «Открыто - признано наличие несоответствий; Заметка - рекомендации по улучшению; Снято - наличие соответствий [по смыслу: несоответствий] не найдено» [К:306–308]. По результатам повторной инспекции несоответствие получает статус «устранено/не устранено» [К:312]. Каждое несоответствие описывается «расположением, описанием, отметкой (снято, заметка, открыто, не устранено, устранено), номером вопроса контрольной таблицы» [К:327].

- **Роли ФИ.** «Автор - один человек или представитель коллектива; Ведущий - один; Инспекторов - много» [К:238–240]. Можно добавить чтеца [К:261]. Участников назначает тимлидер [К:258]. Подробнее в п. 8.2.

- **Контрольные вопросы (чек-лист).** «Один из входов в ФИ - контрольные вопросы» [К:328]. На каждый вопрос отвечают «да/нет/не применимо» [К:321]. Если инспектор отвечает «нет», он приводит пример несоответствия и объясняет, как его нашёл; «На галочку “да” подтверждение не нужно» [К:288].

- **Протокол статического анализа.** «Код, который поступает на ФИ должен сопровождаться протоколом статического анализа, т.е. протоколом, проверяющим соответствие кода стандарту. Мы самостоятельно определяем используемые чекеры кода в стандарте.» [К:315].

- **Решение по ФИ и повторная ФИ.** Решение: «принято, доработать». Формат повторной ФИ: «сокращенный или полный». Про сокращённую сказано: «Первый представляет из себя инспекцию какого-то конкретного места, мелкой детали, которая не влияет на остальные объекты объекта ФИ.» [К:322].

### 1.5 Термины: тестирование и покрытие (темы 2-го семестра, кратко)

- **Тестирование.** «Обнаруживает несоответствия кода требованиям путём его выполнения». Состоит из разработки тестов на основе требований и их выполнения. Проводится для ПО целиком (или его исполняемого объектного кода), для сборки нескольких компонентов, для отдельного компонента [К:170–178]. «Тест по сути это определение выходов к конкретным входам.» [К:558]. Результат теста — pass/fail [К:561].
- **Тест-план.** «Пишем тест-планы, определяя входы и ожидаемые для них выходы, после чего проверяем соответствие.» [К:293]. «Самый простой тест-план - чек-лист того, что нужно нажать и что после этого получить… Такой тест-план неэффективен.» [К:618–619].
- **Тестовый пример (ТП).** «Разработан на основе требований». Содержит «Набор входных воздействий; Условия (сценарий) выполнения; Набор ожидаемых результатов; Критерии оценки результатов выполнения». Проверяет поведение ПО «В нормальном диапазоне» и «В “ненормальном” диапазоне (робастность)» [К:591–600].
- **Тестовая процедура.** «обеспечивает выполнение тестовых примеров с заложенным сценарием, то есть управляет подачей воздействия на объект тестирования и сравнивает полученную реакцию объекта тестирования с ожидаемой» [К:606]. «Учитывает среду тестирования»; «Бывает “ручной”, автоматической, полуавтоматической» [К:609–615]. Другая формулировка: «основная программа, в которой реализуется сценарий» [К:692].
- **Среда тестирования (тестовая среда).** «Программное/аппаратное окружение объекта тестирования, создающее условия для выполнения тестов». «Идеально: целевой вычислитель с загружаемым ПО». «Допустимо для части тестов: заменители целевого вычислителя (его эмуляторы и имитаторы)» [К:624–627]. В лекции 7: «железка, программа для тестирования, вспомогательные библиотеки» [К:685].
- **Тестовое окружение.** Нужно для компонентных и модульных тестов: «окружение = драйвер + заглушки» [К:688–689]. «Первое, что должен сделать тестировщик - разработать тестовую среду, затем тестовое окружение.» [К:681].
- **Протокол выполнения теста.** Содержит идентификаторы и версии объекта тестирования, теста и элементов среды тестирования; ожидаемый результат, полученный результат и их сравнение (pass/fail) для каждого ТП; вспомогательную информацию о ходе и итоге выполнения [К:650–656]. Относится к КК2 [К:639].
- **Тесты на устойчивость (робастность).** «тесты, гарантирующие, что система не откажет, если задать ей невозможные параметры (например, самолёт летит под землёй)» [К:603].
- **Классы эквивалентности и граничные значения.** Классы эквивалентности выделяют «на основе предположения о том, какие ошибки могут быть в тестируемом ПО». Затем определяют граничные значения и решают, к какому классу относится каждая граница. «Для каждой границы провести тесты со значениями непосредственно перед границей, на границе и сразу после нее.» [К:708–711].
- **Виды тестирования.** Три вида [К:659–668]:
  - интеграции аппаратуры и ПО: работа ПО в среде целевого вычислителя, соответствие требованиям высокого уровня;
  - интеграции ПО: взаимодействие компонентов, соответствие архитектуре ПО;
  - низкого уровня: работа отдельных компонентов, соответствие требованиям низкого уровня.
- **Симулятор, эмулятор, имитатор.** «Симулятор использует объектный код, который получен из исходного и ведёт себя, как железо… Но необходимо доказать, что симулятор или имуляютор [эмулятор] ведут себя также, как железка.» [К:637].
- **Покрытие.** «мера того, насколько тестирование достигло целей в КТ-178С». Покрытие требований — «Мера полноты тестов по отношению к требованиям». Структурное покрытие — «Процент элементов исходного кода, выполненных тестами» [К:782–788]. «Структурное покрытие - мера, а не метод разработки тестов» [К:835].
- **Оператор, решение, условие; MC/DC.**
  - Покрытие операторов: «Каждый оператор исходного кода выполнен хотя бы раз» [К:800].
  - Решение — «любое выражение принимающее значения TRUE или FALSE» [К:803]. Покрытие решений: каждое решение принимало значения TRUE и FALSE, пройдена каждая точка входа и выхода [К:808–810].
  - «Условие - решение не содержащее булевских операций (кроме оператора NOT)». Каждое вхождение считается отдельным условием: в (a or b) and (b or d) четыре условия [К:813–818].
  - MC/DC: покрытие решений плюс «Для каждого условия показано его влияние на решение» [К:824–826].
  - «Покрытие MC/DC > Покрытие решений > Покрытие операторов» [К:838].
- **Отключённый, мёртвый, посторонний код.** Это одни из причин непокрытия [К:841–847]. Первая — «Отключённый код», у которого два вида: «Неисполняемый код» и «Код, исполняемый на определённых конфигурациях». Вторая — «Посторонний/мёртый код».
- **Покрытие связности.** «обеспечивает правильность взаимодействия компонент[ов] программы» [К:855]. «может быть собрано только при интеграционном тестировании» [К:872].

## 2. Процессы ЖЦ ПО: назначение, входы, выходы, критерии, исполнители

### 2.1 Список процессов

По конспекту [К:19–27]: «1. Процесс планирования 2. Процесс разработки требований 3. Процесс проектирования 4. Процесс кодирования 5. Процесс верификации 6. Процесс сертификации 7. Процесс гарантии качества 8. Процесс управления конфигурацией (УК ПО)».

**Ловушка: в этом списке нет интеграции.** При этом:
- в лекции 5 есть отдельный раздел «Процесс интеграции» [К:484];
- «Каждый процесс разработки, кроме кодирования и интеграции, могут породить производные требования» [К:66], то есть интеграция считается процессом разработки;
- в гайде: в некоторых примерах «пропущен шаг интеграции, преподаватель на это злится».

(вывод) В документах писать **9 процессов**, интеграцию как отдельный процесс.

«Процесс сертификации» в другом месте назван «процесс взаимодействия с сертифицирующим органом» [К:132].

Что верифицируется: «Верифицироваться должны все почти все процессы ЖЦ ПО (в том числе процесс верификации)… Не подвергается верификации процесс управления конфигурацией, процесс взаимодействия с сертифицирующим органом и процесс гарантии качества.» [К:132].

> **По DO-178C (не из конспекта), §3.** Процессы делятся на три группы:
> 1. процесс планирования;
> 2. процессы разработки: разработка требований, проектирование, кодирование, интеграция;
> 3. интегральные процессы: верификация, УК, гарантия качества, взаимодействие с сертифицирующим органом. Они идут параллельно с процессами разработки на протяжении всего ЖЦ.
>
> Переходы между процессами задаются **критериями перехода** (§3.3): процесс можно начать или возобновить, когда выполнены запланированные критерии. Стандарт приводит примеры таких критериев: проведены рассмотрения процесса верификации; вход является идентифицированной единицей конфигурации; для входа выполнен анализ трассируемости. Каждый процесс получает обратную связь от других процессов и сам её даёт, например в виде сообщений о проблемах.

### 2.4 Ловушки во входах и выходах

Именно на таких местах, по гайду, теряют баллы («теоретические ошибки во входных и выходных данных»).

1. **Выход кодирования.** В конспекте написано: «Выходами являются сообщения о проблемах и исполняемый объектный код» [К:358]. Это противоречит самому конспекту:
   - ИОК получают в интеграции: «Получение исполняемого объектного кода из исходного кода (компиляция и компоновка)» [К:489]; «Результатом интеграции является исполняемый объектный код» [К:494];
   - вход интеграции — «результат процесса кодирования (параметры сборки и исходный код…)» [К:497].

   По DO-178C выход кодирования тоже исходный код (плюс объектный код).

   (вывод) В документах писать: **выход кодирования — исходный код и сообщения о проблемах; ИОК — выход интеграции.** Если сомневаетесь, проверьте схему в оригинале конспекта (она утеряна, [К:361]) или спросите преподавателя.
2. **ЗИ на входе, СП на выходе.** Преподаватель специально подчеркнул, что ЗИ входит в кодирование, хотя на схеме его не было [К:355], а СП — выход кодирования [К:358]. (вывод) По той же логике у **каждого** процесса разработки на входе есть ЗИ (повторный вход в процесс после изменения), а на выходе есть СП (о проблемах во входных данных). DO-178C говорит то же: каждый процесс разработки сообщает в предыдущие процессы о неадекватных или некорректных входах.
3. **План разработки и стандарт тоже входы.** В конспекте это сказано только про кодирование («стандарт процесса кодирования», «план разработки ПО» [К:355]). По DO-178C так для всех процессов разработки: в разработку требований входят План разработки ПО и **Стандарт на разработку требований**, в проектирование — План разработки и Стандарт на проектирование. Это нужно для п. 3.3 «Входные данные» нашего Стандарта.
4. **Интеграция — отдельный процесс** (см. 2.1). В гайде в структуре Плана разработки интеграция стоит со знаком «(?)», но её нужно писать.
5. **Описание проекта — выход проектирования**, хотя в К:497 оно перечислено в скобках вместе с результатами кодирования. По К:355 описание проекта входит в кодирование. По DO-178C в интеграцию из проектирования приходит архитектура ПО.
6. **Производные требования** порождают только разработка требований и проектирование. Кодирование и интеграция их не порождают [К:66].
7. **Критерии начала и окончания** в конспекте прямо не даны. (вывод) Из механики ФИ получается удобная формулировка, которая согласуется с примерами критериев перехода в DO-178B/C §3.3:
   - процесс **начинается**, когда его входы прошли ФИ и получили статус базовой версии, или когда поступил ЗИ;
   - процесс **заканчивается**, когда его выходы прошли ФИ без открытых несоответствий, получили статус базовой версии и запись о ФИ сохранена в СКУ [К:243, 258, 276–279, 311].
8. **Не верифицируются** процессы УК, гарантии качества и взаимодействия с сертифицирующим органом [К:132]. Но планы и стандарты проходят рассмотрения [К:141], то есть сам документ «План УК ПО» проверяют.

## 3. Интеграция (всё, что есть в конспекте)

### 3.1 Что такое интеграция
«Что такое интеграция? Интеграци[я] ПО: Получение исполняемого объектного кода из исходного кода (компиляция и компоновка) и файла компонента параметрических данных. Интеграция ПО и аппаратуры: Загрузка исполняемого объектного кода в целевой вычислитель.» [К:487–491]

Итого интеграция состоит из двух частей:
1. **интеграция ПО**: компиляция и компоновка, получение ИОК и файла компонента параметрических данных;
2. **интеграция ПО и аппаратуры**: загрузка ИОК в целевой вычислитель.

Двусмысленность формулировки: фразу «из исходного кода … и файла компонента параметрических данных» можно прочитать двумя способами: «ИОК получают из исходного кода и файла» или «получают ИОК, а также файл». По DO-178C (не из конспекта) верно второе: в интеграции получают ИОК **и** файлы параметрических данных, а параметрические данные влияют на поведение ПО, не меняя ИОК.

### 3.2 Входы и выходы
- **Выход:** «Результатом интеграции является исполняемый объектный код, протокол сборки, командные файлы для сборки, протокол загрузки.» [К:494]
- **Вход:** «Входом является результат процесса кодирования (параметры сборки и исходный код, описание проекта)» [К:497].
- Что используется в интеграции и какова её цель, было на вставках из DO [К:510–514], но картинки утеряны. Ниже, в п. 3.10, это восстановлено по DO-178C.

### 3.3 Компонент параметрических данных
Цитата приведена в глоссарии (1.2) [К:500–507]. Коротко: это структура элементов со значениями и атрибутами (тип, диапазон, допустимые значения). Элементы могут влиять на пути выполнения ИОК, включать и выключать компоненты и функции, подстраивать вычисления под конфигурацию системы, служить данными для вычислений, задавать распределение времени и памяти при обособлении, задавать начальные значения.

### 3.4 Компиляция и компоновка; объектный код
- «компоновка производится совместно с компиляцией (объектный код не хранится)» [К:519]
- «makefile должен гарантировать полную перекомпиляцию (удаление имеющихся объектных файлов)» [К:520]
- «Необходимо гарантировать, что компоновщик подключает лишь только что скомпилированные файлы объектного кода, не стандартные библиотеки» [К:521]
- «Объектный код не находится под УК (процесс управления конфигурацией): компоновка производится совместно с компиляцией (объектный код не хранится)» [К:532]; ещё раз то же про компоновщик [К:533]

### 3.5 Загрузка
- «Процедура загрузки исполняемого объектного кода описывается в плане разработки ПО» [К:525]
- «Контроль целостности загруженного кода описан в плане УК ПО» [К:526]
- «Резидентный загрузчик - часть ПО» [К:527]
- «Используется внешняя программа загрузки, обоз[н]аченная в плане разработки» [К:528]
- Внешний загрузчик загружает ИОК в целевой вычислитель. Резидентный переписывает ПО из флеш-памяти в оперативную, например при старте микроконтроллера [К:537–538].

### 3.6 make-файлы
- «Требуется осторожное использование make-файлов: их следует использовать лишь для сборки» [К:550]
- «make-файл должен гарантировать полную перекомпиляцию (удаление имеющихся объектных файлов)» [К:551]

### 3.7 Стандартные библиотеки
Запрещены, если для них не выполнены цели КТ-178В: не разработаны требования, нет описания проекта, не проведена верификация. Пример: библиотека математических функций, поставляемая с компилятором [К:542–546, 554].

### 3.8 Верификация результатов интеграции
- «Результаты интеграции также подвергаются верификации.» [К:289]
- С интеграцией связаны тестирование интеграции аппаратуры и ПО (соответствие ВУ) и тестирование интеграции ПО (соответствие архитектуре) [К:660–665].
- Покрытие связности «может быть собрано только при интеграционном тестировании» [К:872].

### 3.10 По DO-178C (не из конспекта)

> - **Цель интеграции (§5.4):** получить ИОК и связанные с ним файлы параметрических данных, если они есть, и загрузить их в целевую аппаратуру для интеграции ПО и аппаратуры.
> - **Входы:** архитектура ПО из проектирования; исходный и объектный код из кодирования. В интеграции также используются целевой вычислитель и данные компоновки и загрузки.
> - **Выходы:** ИОК (§11.12), данные компоновки и загрузки, файл компонента параметрических данных (§11.22).
> - **Деятельность:** получить ИОК из исходного кода и данных компоновки и загрузки; получить файлы параметрических данных; загрузить ПО в целевой вычислитель; некорректные входы вернуть как обратную связь в требования, проектирование, кодирование или планирование.
> - **Особые положения:** нужны свидетельства того, что отключённый код не будет активирован там, где он не предназначен работать. Патчи, то есть правки ИОК в обход исходного кода и сборки, не используют для изменения требований или архитектуры и для исправлений по результатам верификации. Допускаются лишь ограниченные случаи, например обход известных дефектов компилятора.
> - **Верификация интеграции (§6.3.5):** проверить, что результаты интеграции полны и правильны, например рассмотрением данных компоновки и загрузки и карты памяти.
> - В индексе конфигурации ПО (SCI, §11.16) указывают инструкции по сборке ИОК и средства контроля его целостности, если они используются.

### 3.11 Как перевести интеграцию на наш веб-проект (рекомендация, не из источников)

| Термин курса | Возможный аналог у нас |
|---|---|
| целевой вычислитель | сервер или окружение, куда развёртывается система |
| компиляция и компоновка | сборка артефакта (бинарник, образ контейнера, бандл) |
| командные файлы для сборки | Makefile, Dockerfile, конфигурация CI |
| параметры сборки | параметры и переменные сборки |
| компонент параметрических данных | конфигурационные файлы, которые меняют поведение без пересборки (если они есть) |
| внешний загрузчик | средство развёртывания (deploy-скрипт или задача CI) |
| резидентный загрузчик | скорее всего, «не применяется», так и написать |
| протокол сборки / протокол загрузки | лог сборки / лог развёртывания |
| контроль целостности загруженного кода | контрольная сумма (хеш) артефакта, которую сверяют после загрузки |

**Риск.** Если язык интерпретируемый (Python, JS), «компиляции и компоновки» в прямом смысле нет. Преподаватель говорил, что интерпретируемые языки «не очень подходят для бортового ПО (так как интерпретируемая программа требует верифицируемости и программы и среды)» [К:397]. Заранее решите и объясните в Плане разработки, что у вас считается сборкой и что считается ИОК.

**Осторожно с предметной областью.** Наша система сама автоматизирует релизы, сборки и развёртывание. Не путайте интеграцию **нашего** ПО (Планы) с функциями **продукта** (Системные требования, СПТ). Подробнее в 6.1.

## 4. Управление конфигурацией (всё, что есть в конспекте)

### 4.1 Что есть в конспекте
Отдельной лекции про УК нет. Всё ниже собрано из лекций про ФИ, тестирование и интеграцию. Сам процесс УК не верифицируется [К:132].

### 4.2 Идентификация
- При организации ФИ: «зафиксировать текущее состояние инспектирования объекта (номер версии, дата)»; «фиксируются исходные документы (время, версия)» [К:201–202].
- «ведущий создаёт идентификацию объекта и данных, поступающих на ФИ» [К:258].
- В протоколе теста указываются «Идентификаторы и версии: Объекты тестирования, Теста, Элементов среды тестирования» [К:651–654].
- «Результаты тестов должны трассироваться на версию теста, при выполнении которой они были получены, на версию кода (исходного и исполняемого) и на версию требования, по которым были написаны код и тест.» [К:721]

(вывод) Значит, версию нужно уметь однозначно указать для требований, кода (исходного **и** исполняемого), тестов, элементов среды тестирования и исходных документов ФИ.

### 4.3 Базовые версии
- Объект получает статус базовой версии, если на ФИ подтверждено отсутствие ошибок [К:243]; если несоответствия не найдены [К:258].
- После создания базовой версии объект КК1 меняется только по ЗИ [К:16].
- Для тестов: «Тесты – это категория контроля 1, нужно обеспечить возможность фиксации версии кода и версии теста -> должна быть определена формальная инспекция, чтобы можно было установить базовую версию (если не обнаружилось в ФИ никаких проблем, то фиксируется базовая версия), -> чтобы изменить тест, нужен запрос на изменение.» [К:725]
- КК2 и базовая версия: см. 1.3 [К:246] (автор конспекта не уверен).
- В гайде: «Базовая версия — самый новый коммит в ветке master (так можно писать только в плане УК ПО)».

### 4.4 КК1 и КК2
- Определения в п. 1.3 [К:16, 61].
- Главное: **категория присваивается частям проекта, а не всему проекту**: «это не относится ко всему проекту целиком!!!» [К:16].
- Что известно о конкретных объектах:

| Объект | КК | Источник |
|---|---|---|
| Тесты | КК1 | К:16, 725 (прямо) |
| Протокол тестирования | КК2 | К:16, 639 (прямо) |

| Протокол ФИ, протоколы сборки и загрузки | в конспекте нет | (вывод) по аналогии с протоколом тестирования — КК2 |

### 4.5 Контроль изменений: от ошибки до новой базовой версии (собрано по конспекту)
1. Ошибка или несоответствие обнаружены при верификации: на ФИ, в тесте, при анализе покрытия [К:97, 302, 639, 832].
2. Ошибку **регистрируют**, то есть пишут сообщение о проблеме [К:97, 255, 301, 639].
3. **Группа управления изменениями** рассматривает СП, решает, где ошибка (в коде или в требованиях), и создаёт ЗИ на код или требование, но не на протокол [К:639]. Другой вариант: после ФИ считать ЗИ сам список несоответствий или протокол ФИ [К:302]. В Плане УК выберите один вариант и опишите его.
4. **Автор вносит изменения** [К:243]. ЗИ при этом служит входом процесса, например кодирования [К:355].
5. Объект **снова идёт на ФИ**. Её входы: протокол предыдущей ФИ и обработанный ЗИ [К:297]. Формат повторной ФИ — сокращённый или полный [К:322].
6. Все «открытые» несоответствия с прошлой ФИ должны быть закрыты, по каждому ставится отметка «устранено» или «не устранено» [К:311–312].
7. Если несоответствий нет, объект получает **базовую версию** [К:243, 258], а запись о ФИ сохраняется в СКУ [К:279].

### 4.6 Сообщения о проблемах и запросы на изменение
Когда создаются и куда идут — см. глоссарий (1.3). Коротко: **СП фиксирует проблему, ЗИ — решение что-то изменить.** ЗИ составляют на код или требования, а не на протокол [К:639].

### 4.7 Хранение, СКУ, архив
- «Запись о ФИ сохранена в СКУ» [К:279].
- Объектный код не хранится [К:519, 532].
- Про архивирование, резервные копии, выпуск (release) **в конспекте нет**. См. DO-178C в п. 4.10.
- В гайде: в Плане УК описать, как хранятся код, требования, issue, merge request (скорее всего в git и GitHub), кто и как вносит изменения, какие есть роли, как происходит merge в master.

### 4.8 Что под УК, а что нет
- **Не под УК:** объектный код [К:532].
- **Под УК, прямо по конспекту:** тесты (КК1) и протокол тестирования (КК2) [К:16]; запись о ФИ хранится в СКУ [К:279].
- **Под УК, вывод:** требования и код, раз их меняют по ЗИ [К:639]; всё, на версии чего трассируются результаты тестов, включая исполняемый объектный код [К:721]; исходные документы ФИ, которые фиксируются по версии [К:202].
- **Отдельный пункт Плана УК:** контроль целостности загруженного кода [К:526].

### 4.9 Что говорит гайд про План УК ПО
- Описать, как хранятся код, требования, issue, merge request и прочее; кто и как вносит изменения; какие есть роли; как происходит merge в master. Делать по аналогии с примерами.
- «в некоторых примерах пропущен шаг интеграции, преподаватель на это злится».
- «Нужно описать весь процесс разработки, каждый шаг (кто, где, что делает), и определить каждый термин, который можно не понять. Подробность — максимальная».
- Git-формулировки «Базовая версия — самый новый коммит в ветке master» и «Запрос на изменение, сообщение о проблеме — issue в репозитории» допустимы **только** в Плане УК ПО: «так можно писать только в плане УК ПО».

## 5. Требования

### 5.1 Три уровня требований

| | Системные требования | Требования к ПО = ВУ (СПТ) | Требования НУ |
|---|---|---|---|
| К чему относятся | «ко всей системе целиком» [К:41] | к ПО. Пишутся по системным требованиям (в части, относящейся к проекту) и интерфейсам [К:41] | к компонентам ПО. Появляются при проектировании [К:71] |
| Где записаны | документ «Системные требования» | «спецификацию требований» [К:44], то есть СПТ [Г] | описание проекта [К:50, 71], 2-й семестр |
| Детали реализации | нельзя: «ЧТО делает система, а не КАК» [Г] | нельзя [К:63]; компонентов нет [К:63]; код упоминать нельзя [Г] | можно, «но не конкретные алгоритмы» [К:63]; код появляется здесь [Г] |
| Чем проверяются | валидация, «проверка требований самого верхнего уровня» [К:106] | верификация: «насколько требования к ПО удовлетворяют системным требованиям» [К:161]; тестирование интеграции аппаратуры и ПО — «Соответствие требованиям высокого уровня» [К:660–662] | тестирование низкого уровня — «Соответствие требованиям низкого уровня» [К:666–668]; тестирование интеграции ПО — «Соответствие архитектуре ПО» [К:663–665] |

Чем требования к ПО отличаются от системных, по гайду: преподаватель говорит, что они «более детальные» (и рассказывает про стиральную машинку). «По факту мы спускаемся на уровень ниже и описываем, как именно ПО получает и отправляет данные. Для сайта — что происходит при переходе на страницу, при нажатии на элемент.»

### 5.2 Производные требования
- «Производные требования не трассируется на требования к ПО. Каждый процесс разработки, кроме кодирования и интеграции, могут породить производные требования…» [К:66]
- Значит, в СПТ производные ВУ **не имеют ссылки** на системное требование, а в описании проекта производные НУ не имеют ссылки на ВУ.
- По DO-178C (не из конспекта): каждое производное требование нужно определить вместе с **причиной его появления** и передать в системные процессы, включая оценку безопасности. Каждое ВУ трассируется на системные требования, **кроме производных**.
- (рекомендация) Помечайте производные требования явно (атрибут «производное» и обоснование). Иначе при анализе трассировки они выглядят как требования, у которых потеряна ссылка.

### 5.3 Правила формулировки
По гайду, раздел 1 дословно. Сказано о системных требованиях, но применимо и к СПТ.
1. «Каждое требование должно содержать слово “должно”.» В примерах гайда при этом пишут «Система должна …».
2. «каждое определение должно описывать ЧТО делает система, а не КАК. То есть не должно быть никаких деталей реализации, всё максимально абстрактно.»
3. Требования проверяемые. Плохие примеры: «система должна использовать уран 235 в ядерных боеголовках (Как вы проверите, что в них находится?)»; «система должна использовать postgresql в качестве БД (как вы узнаете, что она его использует?)».
4. «Самая распространённая ошибка это всё же просачивание реализации внутрь требований.» Плохо: «система должна содержать пользовательский интерфейс с красной кнопкой для отправки ядерных боеголовок на Вашингтон». Реакция преподавателя: «Вы уверены, что она должна быть красная?», «Вы уверены, что это должна быть именно кнопка?». Хорошо: «Система должна содержать возможность отправки ядерных боеголовок на Вашингтон.»
5. «Ещё одна распространённая ошибка - требование не положительное, например - Система не должна отправлять оскорбительных сообщений (”А что она должна делать?”). Вместо этого, как костыль, предложенный Авианосцем [преподавателем], можно написать: Система должна не отправлять оскорбительных сообщений».
6. При этом должны соблюдаться все свойства требований (см. 5.4).

По конспекту:
7. В стандарте нужен раздел «Порядок представлени[я] правил»: «описание идентификаторов и глаголов аля должен, запрещается и др.» [К:62]
8. В ВУ нет деталей реализации и нет компонентов. В НУ детали реализации можно указывать, конкретные алгоритмы нельзя [К:63].
9. Взаимодействие компонентов описывают отдельным требованием, которое так и называется: «требование о взаимодействии». Это уровень НУ [К:63, 80].
10. Комментарии: «Наличие исключений, пояснений, обоснований и примеров прописывается в стандарте и необязательно. Но в случае, если мы планируем пользоваться этими видами комментариев, то необходимо это определить в документе.» [К:64]. «Комментарии выкинуть можно, а описание нельзя, иначе может появиться неоднозначность.» [К:65]
11. На каждое требование должен быть тест [К:38, 67] (см. 5.6).

### 5.4 Свойства требований
По гайду, раздел «Свойства требований (СПТ) — дословно». Названия свойств приведены точно, полные формулировки смотрите в гайде. Ниже ключевые фразы оттуда.
1. **Корректность**: «СПТ должна соответствовать входным данным процесса РПТ».
2. **Однозначность**: «Каждое входящее в СПТ требование должно иметь только одну интерпретацию».
3. **Полнота**. «Все системные требования, связанные с ПО, должны быть отражены в СПТ». Требования «должны охватывать как допустимые, так и недопустимые входные данные». Определены все термины, аббревиатуры, единицы измерения. У рисунков, таблиц и диаграмм есть метки, и на них есть ссылки. СПТ с «должно быть определено» (TBD) не полная. Если TBD необходим, его сопровождает описание «причин возникновения TBD и условий исключения TBD из СПТ».
4. **Согласованность** означает «ее внутреннюю непротиворечивость». Несоответствие документу более высокого уровня — это уже некорректность.
5. **Неизбыточность**: нет «невозможных сценариев или ненужных свойств/функций»; «Каждое требование в СПТ должно быть представлено только один раз».
6. **Неделимость**: «Каждое требование в СПТ должно быть атомарным». Если в требовании несколько независимых утверждений, его разбивают на несколько требований.
7. **Модифицируемость**: оглавление, индекс, перекрёстные ссылки, отсутствие избыточности, атомарность.
8. **Тестируемость**: «существует определенная методика, позволяющая человеку или машине установить, что требование реализовано в ПО». Нужен «ясный критерий оценки (например, критерий ”пройдено/не пройдено”)».
9. **Трассируемость**: «Каждое требование в СПТ должно иметь уникальный идентификатор»; «Идентификация требований должна оставаться неизменной»; требования, основанные на документах предыдущих этапов, ссылаются на эти документы.
10. **Независимость от реализации**: «СПТ должна описывать, что должна выполнять система, а не как она это должна делать». В ней нет деталей реализации (кроме явно определённых и обоснованных ограничений), сведений о процессе разработки и о тестировании.
11. **Использование комментариев**: «Комментарии должны быть четко отделены от самих требований»; «удаление комментариев из СПТ не должно влиять на ее ключевые характеристики».

По DO-178C (не из конспекта), §6.3.1: по каким критериям проверяют ВУ. Этот список пригодится для самопроверки сейчас и для чек-листа ФИ в следующем семестре:
- соответствие системным требованиям;
- точность и согласованность;
- совместимость с целевым вычислителем;
- проверяемость;
- соответствие стандартам (нашему Стандарту на разработку требований);
- трассируемость;
- корректность алгоритмических аспектов.

### 5.5 Трассировка
Цепочка: системные требования ← ВУ ← НУ ← исходный код (на уровне файла и функции); тесты связаны с требованиями и с кодом; результаты тестов привязаны к версиям.
- Анализ трассировки даёт объективную оценку (ссылки есть или нет). Соответствие требования требованию уровнем выше оценивают рассмотрением, то есть экспертно [К:152].
- Производные требования не трассируются вверх [К:66].
- Код трассируется на уровне файла и функции [К:375–377].
- «Необходима трассировка тестов на требования и на код» [К:720]. Результаты тестов трассируются на версии теста, кода (исходного и исполняемого) и требования [К:721].
- Связь «многие ко многим»: «Один тест может проверять несколько требований и одно требование может покрываться несколькими [тестами]» [К:728].
- Каждый тест трассируется на одно или несколько требований, каждое требование — на один или несколько тестов [К:769–770].
- Структурное покрытие помогает найти код, не трассируемый на требования [К:795].
- В гайде: у каждого требования уникальный неизменный идентификатор; требования, основанные на документах предыдущих этапов, ссылаются на эти документы.
- По DO-178C (не из конспекта), §5.5: данные трассировки двусторонние: СТ↔ВУ, ВУ↔НУ, НУ↔исходный код.
- (рекомендация) В СПТ у каждого требования поле «Трассировка: СТ-xx» (или пометка «производное»), а в приложении матрица СТ → СПТ. Так проще и анализ трассировки, и проверка полноты («Все системные требования, связанные с ПО, должны быть отражены в СПТ» [Г]).

### 5.6 Требования и тесты («на каждое требование — тест»)
- «Если есть требование, на него обязательно должен быть тест, однако не всех из них должны быть выполнены на машине.» [К:38]
- «На каждое требование необходимо написать тесты.» [К:67]
- «Как только появились требования, можно сразу начать писать тесты, так как тесты должны проверять выполнение требований.» [К:558]. Тесты можно составлять параллельно разработке [К:167].
- «Количество ТП должно быть таким, чтобы все требования были бы проверены»; «Для каждого требования нужно перебрать все возможные варианты поведения программы» [К:716–717].
- Противоречие в конспекте: одно требование «может покрываться десятками тестов», но тогда «нужно проверять, что вся совокупность тестов, по этому требованию, проверяет полностью всё требование. Поэтому следует избегать больше одного теста на проверку какого-либо требования.» [К:732]. (вывод) Несколько тестов на требование допустимы, но на ФИ придётся доказывать, что вместе они покрывают требование полностью. Проще стремиться к одному тесту на требование.
- «Полнота набора тестовых примеров для покрытия требования не зависит от уровня ПО» [К:774].
- В гайде: без тест-кейсов во 2-м семестре команды получали 1/5 и 2/5, а документы «он не проверил: нет тест-кейсов — нет смысла смотреть».
- (вывод для этого семестра) Формулируйте каждое требование так, чтобы к нему сразу придумывался тест: конкретные входы и ожидаемые выходы [К:558], поведение в нормальном и «ненормальном» диапазоне [К:598–600]. Явные диапазоны и допустимые значения потом позволят выделить классы эквивалентности и граничные значения [К:708–711].

## 6. Что отразить в каждом документе семестра

Во всех документах: разделы «Назначение», «Область применения», «Используемые документы» стандартны [К:60]. Термины, процессы и входы/выходы должны **совпадать во всех пяти документах**, потому что преподаватель сверяет документы между собой [Г].

### 6.1 Системные требования
- Требования относятся **ко всей системе целиком** [К:41], а не только к ПО.
- Документ — главный вход процесса разработки требований, наряду с **интерфейсами** [К:41]. (вывод) Опишите внешние интерфейсы системы (с пользователями и внешними системами), иначе у процесса разработки требований не будет второго входа.
- Из системных требований в разработку ПО берут «то, что имеет отношение к тому, что мы собираемся делать в проекте» [К:41]. (вывод) В системных требованиях могут быть пункты не про ПО, но все пункты про ПО должны отразиться в СПТ [Г: полнота].
- Системные требования — требования самого верхнего уровня, поэтому их **валидируют**, а не верифицируют [К:106]. Методы: рассмотрения, анализы, испытания, они «для валидации тоже подходят» [К:112]. Если упоминаете проверку системных требований, используйте слово «валидация».
- На каждое требование должен быть тест, не обязательно машинный [К:38]. Каждая формулировка должна давать «ясный критерий оценки (например, критерий ”пройдено/не пройдено”)» [Г].
- Правила из гайда: в каждом требовании слово «должно»; ЧТО, а не КАК; проверяемость; без реализации; без «не положительных» требований; соблюдение всех 11 свойств, включая неделимость и уникальный идентификатор (см. 5.3–5.4).
- (рекомендация) Наш продукт сам работает с релизами, версиями, сборками и развёртыванием. В глоссарии СТ и СПТ определите термины предметной области (релиз, версия релиза, сборка и т. п.) и не используйте для продукта термины нашего УК («базовая версия», «ЗИ», «СП», «КК1») в другом смысле. Преподаватель сверяет термины.

### 6.2 План УК ПО
**Структура.** Гайд её не даёт («делать по аналогии с примерами»). Каркас по DO-178C §11.4 (не из конспекта): среда УК; идентификация; базовые версии и трассируемость; сообщения о проблемах; контроль изменений; рассмотрение изменений; учёт состояния; архив, извлечение и выпуск; контроль загрузки; контроль среды; КК1 и КК2.

**Что взять из конспекта и гайда:**
- **Термины** с определениями преподавателя (см. 1.3): КК1, КК2, базовая версия, ЗИ, СП, СКУ, ФИ (это не термин DO, его надо определить [К:197]), группа управления изменениями, несоответствие и его отметки. Плюс ЕК (только в гайде; определение можно дать по DO).
- **СКУ** — где всё хранится; по гайду, скорее всего git и GitHub. Запись о каждой ФИ хранится в СКУ [К:279].
- **Идентификация**: как именуются и версионируются объекты; при ФИ фиксируются версия и дата объекта и версии исходных документов [К:201–202, 258]; версии теста, кода (исходного и исполняемого) и требования должны позволять трассировать результаты тестов [К:721].
- **Базовые версии**: устанавливаются по итогам ФИ без несоответствий [К:243, 258]. В git-терминах это коммит в master [Г] (такая формулировка допустима только здесь).
- **Таблица КК1/КК2 по объектам**, а не на весь проект [К:16]: тесты — КК1, протокол тестирования — КК2 [К:16, 639]; изменение КК1 после базовой версии только по ЗИ [К:16, 61].
- **СП**: когда создаётся (ошибка при верификации, вынос спора с ФИ, несоответствия ФИ, fail теста, непокрытие [К:97, 255, 301, 639, 832]) и что в нём пишется (поля можно взять из DO §11.17, см. 1.3).
- **ЗИ и группа управления изменениями**: кто рассматривает СП, кто решает, где ошибка, кто создаёт ЗИ [К:639]; выбранный вариант «СП → ЗИ» или «протокол ФИ = ЗИ» [К:302].
- **Цикл изменения**: шаги из п. 4.5, статусы несоответствий, решение по ФИ («принято, доработать»), повторная ФИ (сокращённая или полная) [К:305–312, 322].
- **Объектный код не под УК и не хранится**; сборка всегда с полной перекомпиляцией [К:519–520, 532].
- **Контроль целостности загруженного кода** — прямое требование конспекта к Плану УК [К:526].
- **Весь процесс разработки по шагам**: кто, где, что делает, **с интеграцией** (сборка и загрузка). Определить каждый непонятный термин [Г].
- (вывод) Сам процесс УК не верифицируется [К:132]. Не пишите «верификация процесса УК», но сам План как документ проходит рассмотрение [К:141].

(рекомендация, не из источников) Как это может лечь на git и GitHub:

| Понятие | Возможная реализация |
|---|---|
| ЕК | файл, документ или каталог под версионным контролем |
| Идентификация | имя ЕК плюс версия (тег или хеш коммита) и дата |
| Базовая версия | коммит в master после ФИ без открытых несоответствий, можно ещё и тег |
| СП / ЗИ | issue с разными метками; ЗИ ссылается на СП; реализуется через merge request |
| КК1 | защищённая ветка master, изменения только через merge request со ссылкой на ЗИ |
| КК2 | протоколы только добавляются и не исправляются; ошибки оформляются как СП на код или требования |
| ФИ | проводится на merge request в master по чек-листу; протокол — файл в репозитории; merge только при решении «принято» |
| Объектный код | в `.gitignore`, сборка всегда с нуля |
| Контроль целостности загрузки | хеш артефакта в протоколе сборки, сверка после загрузки |

### 6.3 План разработки ПО
Структура по гайду: 1. Определения и термины; 2. Жизненный цикл (2.1 Разработка требований, 2.2 Проектирование, 2.3 Кодирование, 2.4 Интеграция); 3. Организация и роли; 4. - Определение, цели и методы (рассмотрения, анализы, испытания) — см. 1.4.
- Рассмотрение — экспертная оценка, анализ — объективная и повторяемая [К:146–152].
- «Мы можем получить уверенность в отсутствии несоответствий только если используем все верификационные мероприятия вместе. Только тестов для этого недостаточно, как и рассмотрений или анализов. Вопрос из КР.» [К:564]
- Независимость: «сделал один - проверил другой» [К:182].

### 8.2 Формальная инспекция
- **Организация** [К:200–205]: зафиксировать версию и дату объекта; зафиксировать исходные документы; создать запись ФИ (участники, время); занести результаты и отличия от ожидаемого; цель — донести до автора несоответствия.
- **Роли** [К:238–261]:
  - автор: уточняет вопросы и понимает суть несоответствий; если автора нет, его функции выполняет назначенный человек;
  - ведущий: один; роль часто совмещают с инспектором, совмещать с автором не имеет смысла; следит за регламентом; может вынести спор за рамки ФИ, тогда создаётся СП; решающего голоса не имеет; проходит по чек-листу и ставит ссылки на несоответствия [К:273];
  - инспекторы: их много; не участвовали в разработке;
  - чтец: по желанию.
- **Ход ФИ** [К:258]: объект готов → тимлидер назначает автора, ведущего и инспектора → ведущий идентифицирует объект и данные → инспекторы передают перечень несоответствий → обсуждение с автором и ведущим → регистрация результатов → базовая версия или внесение изменений.
- **Входы ФИ** [К:297–298, 315, 328]: объект; все документы, использованные для него; протокол предыдущей ФИ; обработанный ЗИ; контрольные вопросы; для кода — протокол статического анализа.
- **Выходы ФИ** [К:301]: протокол ФИ, сообщения о проблемах, изменение состояния (создаётся базовая версия или нет).
- **Отметки несоответствий**: открыто, заметка, снято; при повторной ФИ — устранено или не устранено [К:305–312, 327].
- **Решение**: «принято» или «доработать»; повторная ФИ сокращённая или полная [К:322].
- **Итоги** [К:276–279]: коллегиальное решение; все несоответствия зарегистрированы, их тексты согласованы; запись о ФИ в СКУ.
- **Чек-листы**: контрольные вопросы готовят для каждого проекта. Несколько инспекторов сводят свои списки в один документ [К:286–288]. Прочитать «5 пункт из SVP_rev5» [К:280].

### 8.3 Тестирование
- Тестовый пример, тестовая процедура, среда, окружение (драйвер и заглушки), протокол, виды тестирования, классы эквивалентности и граничные значения — см. 1.5.
- Правила разработки ТП [К:714–722]: опираться на требования; проверить все требования; перебрать все варианты поведения; тесты должны быть повторяемы; трассировка тестов на требования и код; результаты трассируются на версии; разработку тестов отделять от выполнения.
- При разработке тестов и плана верификации нужно решить, допустимы ли зависимости между тестовыми примерами [К:579].
- Тесты относятся к КК1, для них нужна ФИ и базовая версия, менять их можно только по ЗИ [К:725].
- **Верификация результатов тестирования** [К:756–759]:
  - рассмотрение тестов и результатов; входы: требования, тесты, результаты тестов;
  - анализ покрытия требований тестами; входы: тесты и требования;
  - анализ структурного покрытия; входы: уровень ПО, исходный код, требования, тесты.
- Инструментарий: автоматическое выполнение, автоматическое формирование протокола, пакетный запуск [К:750–753].

### 8.4 Покрытие
- Покрытие требований и структурное покрытие (операторы < решения < MC/DC) — см. 1.5.
- Причины непокрытия: неполнота тестов, неполнота требований, отключённый код, мёртвый код [К:841–847]. На непокрытое можно написать СП [К:832].
- Покрытие связности по данным и по управлению собирается только при интеграционном тестировании [К:850–874]. Виды связей для C/C++ перечислены в К:877–897.
- Какие связи проверять: лучший вариант — все пары функций в цепочке [К:900–905].
- Как оценить эффективность тестов: специально внести ошибку и посмотреть, поймают ли её тесты [К:791].
- По DO-178C (не из конспекта): уровень A требует MC/DC, B — покрытия решений, C — покрытия операторов, D не требует структурного покрытия; анализ связности по данным и управлению нужен для уровней A–C.

### 8.5 Кодирование
- Определение, входы и выходы, свойства исходного кода, трассируемость на уровне файла и функции — см. 1.2 и 2.4.
- Как повысить верифицируемость [К:380–387]: читаемость (правила оформления, ограничение сложности, ограничение ассемблера) и тестируемость (доступ к аппаратуре локализован в немногих модулях, нет недетерминированного поведения, например неинициализированных переменных).
- Язык [К:392–424]: выбирается при планировании; интерпретируемые языки плохо подходят; в России для бортового ПО чаще всего используют C, иногда C++; у C и C++ есть достоинства и недостатки.
- Стандарт на кодирование [К:437–481]: правила оформления, именования, объявления и определения; ограничения конструкций (например, запрет goto, а также continue и break в теле цикла); ограничения сложности (вложенность, длина файла, размер функции, число параметров, сложность выражений).

### 8.6 Как документы этого семестра понадобятся дальше (вывод)
- Идентификаторы требований из СТ и СПТ станут точками трассировки для тестов и для НУ.
- Без проверяемых требований не получится написать тест-кейсы, а без тест-кейсов оценка за 2-й семестр низкая [Г].
- План УК понадобится для протоколов ФИ, базовых версий и потока СП/ЗИ.
- План разработки понадобится для кодирования, интеграции и среды.
- Стандарт на требования станет основой чек-листа ФИ для СПТ.
