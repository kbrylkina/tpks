## Если коротко

- Пример сильный в инженерной части (архитектура микросервисов, API, БД, стандарты кода с версиями линтеров). Процессная часть по DO-178 сделана наполовину.
- **Системные требования** на деле не требования, а таблицы сценариев «Действие / Результат / Комментарий» с кнопками, pop-up'ами и чекбоксами. Это ровно та «красная кнопка», за которую ругает гайд. Брать стоит идею группировки по сценариям и сквозную нумерацию, а форму записи не брать.
- **Требования к ПО** (148 штук). Удачная система идентификаторов `V-W-XYZ-NNNNN`: по ID видно, из какого системного сценария и шага выросло требование. Но текст требований набит UI и реализацией (кнопки, куки, таблицы БД, reCAPTCHA), а нефункциональных требований и интерфейсов нет совсем.
- **Стандарт на разработку требований** короткий: свойства СПТ и схема ID. Описание процесса (входы, выходы, критерии, роли) лежит не в стандарте, а в плане разработки.
- **План УК** больше всего годится как образец детальности: пошаговая сборка базовой версии со скриншотами и таблица ЕК с шаблонами идентификаторов. Но в нём нет процесса СП → ЗИ, КК1/КК2 и правил merge для кода, а текст расходится со скриншотами.
- **План разработки.** Есть удачная схема ЖЦ: у каждого этапа подписано, как он проверяется и где хранится результат. Есть workflow задач в Jira. Но по полной схеме «окружение → входы → выходы → критерии → роли» расписан только один процесс, разработка требований.
- **Шага интеграции нет нигде**: ни в модели ЖЦ, ни в плане разработки, ни в плане УК. Есть только интеграционное тестирование в плане верификации и слова CI/CD в глоссарии. Гайд прямо предупреждает, что за это преподаватель злится.

## 1. Общая карточка

**Что за система.** Приложение «Город — студенту» собирает для студентов мероприятия, скидки и акции, новости города и вузов (Москва; в легенде проект запускает городская администрация вместе с вузами). Пользовательских частей две:

- **мобильное приложение для студента:** общая и персонализированная лента, поиск по тегам и фильтрам, профиль, отзывы и оценки, жалобы (они называются «репорты»);
- **менеджерская CRM:** регистрация организаторов по заявке, модерация заявок на публикацию событий, обработка репортов (чёрный список, «теневой бан»), регистрация менеджеров, дашборды.

Пользователи: студент, организатор (вуз или частник), менеджер, главный менеджер / администратор (в разных разделах называется по-разному, об этом ниже).

**Архитектура** (раздел «Проектирование», с. 65–70). Три уровня:
- пользовательский: приложение и CRM;
- публичный API: Mobile Gateway и CRM Gateway;
- приватный: Events Backend (события и пользователи), CRM Backend (организаторы, менеджеры, репорты, заявки), брокер сообщений, DWH, сервис расчёта релевантности, почтовый сервис.

Между сервисами 15 пронумерованных «переходов». Ранняя версия архитектуры осталась в документе с пометкой [Deprecated] (с. 24–26).

**Стек** (из стандартов): C# для proxy, Go для микросервисов, REST и gRPC/protobuf, Vue на JS/TS, Python и SQL для data science и аналитики, Greenplum, Tableau.

### 2.1 Системные требования

**Где:** 1.1.2 (с. 6–19) внутри раздела, который называется «Бизнес-требования» и описывает поведение приложения «со стороны заказчика». Рядом лежат глоссарий (с. 4–6), анализ предметной области (с. 20–23) и UML-сценарии (с. 27–31).

**Фактическая структура:**
```
1.1 Бизнес-требования: Назначение раздела · Содержание
  1.1.1 Глоссарий: Назначение подраздела · Список понятий
        (14 терминов, таблица «Понятие / Определение / Аналоги»)
  1.1.2 Системные требования: Описание («сценарии использования, предоставленные заказчиком»)
        0. Базовые сценарии                       7. Регистрация и добавление новых организаторов
        1. Пользовательский профиль               8. Регистрация и добавление новых менеджеров
        2. Просмотр основной ленты событий        9. Добавление событий/скидок и их модерирование
        3. Просмотр персонализированной ленты    10. Обработка репортов пользователей менеджером
        4. Поиск события по тегу(-ам)/фильтру    11. Заполнение заявок организаторами
        5. Написание отзыва                      12. Просмотр дашбордов (пусто)
        6. Написание репорта                     13. Получение апдейтов сервиса (пусто)
  1.1.3 Анализ предметной области: общая характеристика · потребности и процессы
        муниципальной администрации / организаторов / студентов · анализ потока информации
1.3 Пользовательские сценарии: диаграммы последовательностей (профиль, лента, репорты) ·
    диаграмма вариантов использования (Приложение + CRM) · диаграммы кооперации
```

**Содержание (пересказ).** Каждый сценарий описывает, что делает пользователь (студент, менеджер, организатор) и что после этого видит или что происходит в системе.

Студенческая часть:
- первый запуск с онбордингом;
- вход: гость видит популярное, авторизованный ещё и рекомендации;
- предложение оценить приложение не чаще раза в сутки;
- регистрация: логин, возраст, почта, пароль, капча, подтверждение почты, выбор интересов;
- вход по почте и паролю или через соцсети / Госуслуги;
- профиль и его редактирование;
- лента: листание, сортировка (по новизне, популярности, голосам «я пойду», рейтингу), фильтры (тип, дата, возраст, направление, цена);
- поиск, отзывы с оценкой и фото, жалобы на отзыв, событие или скидку.

CRM-часть:
- регистрация организатора по заявке, её одобрение, выдача логина и пароля;
- регистрация менеджеров главным менеджером;
- модерация заявок на события: принять, вернуть на правку или отклонить с причиной, организатору уходит письмо;
- обработка репортов с чёрным списком и теневым баном;
- заполнение заявки организатором: проверка полей, черновик.

Анализ предметной области делит участников на три группы (городская администрация, организаторы, студенты) и для каждой расписывает потребности, процессы и потоки информации. По сути это самая «системная» часть всего раздела.

**Формат записи.** На каждый сценарий своя таблица: номер шага, «Действие», «Результат», «Комментарий». Пара «номер раздела + номер строки» потом служит ссылкой в ID требований к ПО (части V и W). Формы «должна / должны» на 51 строку встречаются всего три раза. Примеры (сокращены):

| № | Действие | Результат | Комментарий |
|---|---|---|---|
| 0.4 | Повторный вход в приложение «в течение определённого интервала времени» после первого закрытия | Появляется pop-up «Предложить оценить приложение» в магазине (не чаще раза в сутки) | «Например, закрыл пользователь приложение и через минут 10 открыл снова» |
| 2.4 | Открытие фильтра | Фильтры по типу, дате, возрасту, направлению, цене «в виде чекбоксов/выпадающих меню/интервалов… В конце две кнопки: убрать фильтр и применить» | — |
| 5.2 | «Есть кнопка “оставить отзыв”» | Форма с полем текста, «5 звёздочек», фото/видео, кнопка «отправить»; отзывы оставляют только авторизованные | Отзыв можно оставить, если человек открывал карточку больше одного раза и «не ранее чем через N промежуток времени» |

**Что хорошо:**
- Функциональность охвачена широко и сгруппирована по сценариям и ролям. Нумерация «сценарий.шаг» реально используется для трассировки в требованиях к ПО.
- Комментарии вынесены в отдельный столбец, то есть сама идея «комментарий отделён от требования» совпадает с гайдом (п. 11 свойств).
- Анализ предметной области (участники → потребности → процессы → потоки информации) даёт хороший вход для системных требований. Для нас аналог — разбор ролей в релизном процессе.
- Глоссарий стоит в начале, UML-диаграммы помогают понять сценарии.

**Что слабо или противоречит гайду:**
- **Это сценарии, а не требования.** Нет формулы «Система должна…». В одной ячейке пачка утверждений (форма, поля, капча, подтверждение почты, интересы), атомарности нет.
- **Реализация и UI прямо в системных требованиях:** кнопки, pop-up, «слайдеры», чекбоксы, выпадающие меню, «5 звёздочек», «вертикальная лента», «третья основная кнопка», «передача изменённых данных в базу данных», «запускается генератор логина-пароля», капча. Это та самая «красная кнопка» из гайда.
- **Ссылки на чужие продукты вместо требований:** «как на AliExpress», «как в ВК», «по типу неотправленного письма на Яндекс Почте».
- **Неоднозначно и непроверяемо:** «определённого интервала времени», «N промежуток времени», «должны обновляться регулярно», «что-то художественное и т. п.». По сути это скрытые TBD без причины и без условия снятия.
- **Комментарии не чисто справочные.** В них висят нерешённые варианты («или можно сделать как доп. функцию (переключатель)», «возможно разделить на несколько вкладок», «можно ещё добавить имя», «(или чем они там занимаются)») и даже бизнес-правила (ограничение на отзывы в 5.2). Если удалить комментарий, смысл изменится, а по гайду не должен.
- **Неполнота.** От сценариев 12 и 13 остались одни заголовки. Нефункциональных требований (производительность, доступность, безопасность и персональные данные, хранение) нет ни одного. Внешние интерфейсы (почта, Госуслуги, соцсети) только упомянуты мимоходом, ограничений нет.
- **Путаница в терминах.** Раздел называется «Бизнес-требования», а внутри «Системные требования». Одна и та же роль называется по-разному: «главный менеджер» (сценарии 8 и 10), «администратор» (глоссарий и требования к ПО), «модераторы» (анализ предметной области). В глоссарии нет терминов «организатор», «главный менеджер», «репорт», «CRM», «заявка», «теневой бан», «тег», а два определения обрываются на полуслове.

### 2.2 План управления конфигурацией ПО (подробности в п. 3.1)

**Где:** 1.5.4, с. 99–107.

**Фактическая структура:**
```
План управления конфигурацией: Назначение раздела · Содержание
  1.5.4.1 Базовые версии
          Требования к базовой версии
          Процесс сборки базовой версии документа: состояние страницы-раздела Confluence ·
              действия перед сборкой · сборка файла с базовой версией
          Процесс загрузки и получения новой версии документа: получение · загрузка
  1.5.4.2 Идентификация единиц конфигурации: определение и свойства ЕК ·
          список ЕК (задача, репозиторий, merge request, страница Confluence)
  1.5.4.3 Инструменты управления конфигурацией: GitLab · Jira · Confluence
```

**Содержание.** Базовая версия здесь — это PDF-выгрузка всего пространства Confluence. В неё попадают только проверенные (то есть заблокированные) страницы, ей присваивается номер, а в отдельный git-репозиторий она загружается через ветку и merge request с ревьюером. ЕК определена как «единица передачи части системы между участниками процесса»; у неё одна или больше версий и уникальный идентификатор.

**Формат записей, примеры:**
- задача Jira: `{проект}-{номер}`, например «CSPT-17 — Посмотреть средства для реализации метрик в мобильных приложениях» (статус ГОТОВО);
- merge request: `{репозиторий}!{номер}`, например «Develop (!1)»;
- базовая версия по правилу из текста: `CSPT-{ДДММГГ}-{ЧЧММ}`, например «CSPT-121121-0815»; в commit message пишется «version {название версии}».

**Хорошо.** Детализация по шагам («кто, где, что нажимает»), со скриншотами, как и просит гайд. Есть определения БВ и ЕК, шаблоны идентификаторов, проверка перед сборкой, правило «проверенное замораживается».

**Слабо.** Нет процесса СП → ЗИ, КК1/КК2, правил merge и базовой версии для кода, нет интеграции. Внутри есть противоречия: правило имени версии расходится со скриншотами, Jira названа «управлением страницами», а в содержании указан раздел, которого нет.

### 2.3 План разработки ПО (подробности в п. 3.2)

**Где:** 1.5.3, с. 93–99. По смыслу к нему относятся 1.5.1 «Глоссарий терминов» (с. 89–90) и 1.5.2 «Ответственность участников разработки» (с. 91–93).

**Фактическая структура:**
```
1.5.1 Глоссарий терминов (задача, спринт, backend, frontend, автотест, деплой, релиз, СУБД, CI, CD)
1.5.2 Ответственность участников разработки (7 «направлений»: обязанности + ответственные)
1.5.3 План разработки: Назначение раздела · Содержание
  1.5.3.1 Модель жизненного цикла: схема · легенда (цвета, связи)
  1.5.3.2 Использование Jira: схема статусов · описание статусов · описание жизненного цикла задачи
  1.5.3.3 Процесс разработки требований к ПО: окружение (рис. 1) · входные данные · выходные данные ·
          условия начала · структура процесса · условия конца · роли и квалификация
```

**Формат записей, примеры.** На схеме ЖЦ каждый блок связан с тем, как он верифицируется и где хранится результат. Например: «Проектирование программной составляющей — процесс ревью — документы в Confluence». Статусы задачи: К РАБОТЕ → В РАБОТЕ → РАССМОТРЕНИЕ → ТРЕБУЕТ ТЕСТИРОВАНИЯ → ТЕСТИРОВАНИЕ → ГОТОВО, отдельно НА УДЕРЖАНИИ.

**Хорошо.** Наглядная схема ЖЦ с легендой. Процесс разработки требований описан по правильному шаблону. Ответственность расписана с именами.

**Слабо.** Из четырёх процессов, которые ждёт гайд (требования, проектирование, кодирование, интеграция), описан только первый. Нет среды разработки и интеграции. Часть важного отправлена «в стандарты проекта», где этого нет.

### 2.4 Стандарт на разработку требований к ПО

**Где:** 1.5.5.7, с. 126–129. Описание самого процесса (окружение, входы, выходы, условия начала и конца, роли) вынесено в план разработки, 1.5.3.3 (с. 97–99).

**Фактическая структура:**
```
Стандарт на разработку требований
  Правила представления спецификации требований к ПО
  Содержание спецификации требований к ПО
  Свойства спецификации требований к ПО
  (без отдельного заголовка) система идентификаторов V-W-XYZ-NNNNN с таблицами расшифровки
```

**Содержание (пересказ).** Формат СПТ согласуется с заказчиком, а если тот молчит, берутся шаблоны проекта. СПТ должна содержать три вещи:
- функциональные требования (функции и внешние интерфейсы);
- «актуальные» нефункциональные требования, включая архитектурные ограничения;
- системные требования.

Перечислены девять свойств: корректность, однозначность, полнота, непротиворечивость, неизбыточность, неделимость, модифицируемость, проверяемость, трассируемость. Трассируемость обеспечивается номером, который «классифицирует требование относительно системных требований и элементов архитектуры».

**Формат идентификатора `V-W-XYZ-NNNNN`:**

| Поле | Значения |
|---|---|
| V | номер системного сценария; `A` — относится ко всем сценариям |
| W | номер действия в сценарии V; `A` — ко всем действиям; пусто, если V = A |
| X | `A` — вся архитектура; `B` — один конкретный элемент; `C` — связь двух элементов |
| Y | `F` frontend, `B` backend, `D` data science, `X` внешние сервисы; пусто, если X = A |
| Z | второй элемент связи (те же буквы); пусто, если X = A или X = B |
| NNNNN | «случайно генерируемый» пятизначный номер, уникальный для данной комбинации |

Как это читается:
- `9-2-BF-00004`: сценарий 9 (модерирование), шаг 2 (принятие заявки), один элемент, frontend;
- `7-1-CFB-00007`: сценарий 7, шаг 1, связь frontend → backend (отправка формы на сервер);
- `6-A-BB-00003`: все шаги сценария 6, backend;
- `0-1-A-00001`: относится ко всей архитектуре.

**Что хорошо:**
- ID «говорящий»: по нему видно, из какого системного сценария и шага выросло требование и какую часть системы оно затрагивает. Половину трассируемости это закрывает без отдельной матрицы, хотя матрица всё равно нужна.
- Список свойств почти совпадает со свойствами СПТ из гайда.

**Что слабо или противоречит гайду:**
- Нет разделов, которые ждёт гайд: введения (цель, область применения, термины), «Способа описания конкретного требования» (шаблон фразы, обязательное «должен», правила для комментариев и примечаний), описания процесса (оно в плане разработки), правил составления спецификации.
- Из свойств выпали «независимость от реализации» и «комментарии». По СПТ это сразу видно: она набита реализацией.
- Неточные определения. Проверяемость: «может быть проверено на реализуемость в ПО», хотя должно быть «есть метод проверить, что требование выполнено, и критерий пройдено / не пройдено». Трассируемость: «уникально идентифицировано», а это только половина свойства, ссылки на источник нет.
- «СПТ должна содержать системные требования» — странно: системные требования служат входом, на них ссылаются, а не включают внутрь.
- ID кодирует разбиение на frontend / backend / data science, то есть уже решение проектирования. Для требований высокого уровня это спорно, да и буквы грубые: `B` — это какой из пяти бэкенд-сервисов?
- Правило «случайного» NNNNN на практике не соблюдалось (номера идут подряд), и в самой СПТ есть ID, которые ломают собственный формат (см. 2.5).

### 2.5 Требования к ПО (СПТ)

**Где:** 1.4.6, с. 39–64, внутри раздела «Разработка», не отдельным документом.

**Фактическая структура:** сначала список подразделов, потом 11 подразделов «Требования к…»:
- модерированию заявок (сценарий 9), обработке репортов менеджером (10), регистрации организатора (7);
- базовым сценариям (0), профилю (1), регистрации менеджеров (8);
- отзывам (5), репортам (6), основной ленте (2), поиску (4), персонализированной ленте (3).

В каждом подразделе (не во всех) есть блок «Входные данные», дальше таблица «Идентификационный номер | Требование». Введения, общего описания, интерфейсов и нефункциональных требований нет.

**Объём.** 148 требований, все ID уникальны.
- По сценариям: 0 — 14, 1 — 8, 2 — 18, 3 — 18, 4 — 7, 5 — 11, 6 — 6, 7 — 26, 8 — 12, 9 — 13, 10 — 15. Для сценария 11 нет ни одного.
- По типам: `BF` (frontend) — 76, `BB` (backend) — 40, связи `C**` — 23, `A` (вся архитектура) — 7, прочие — 2. То есть больше половины про интерфейс.

**Содержание (пересказ).** Для каждого сценария расписано:
- какие поля и списки показывает интерфейс, как сортируются и фильтруются списки заявок и репортов;
- что делает сервер при принятии или отклонении заявки: статусы, письма, генерация логина и пароля, перенос между «базами» заявок;
- как ведёт себя лента: автообновление, подгрузка, кнопка «наверх»;
- что хранится в куки.

**Формат и примеры:**
- Удачный: `9-1-BF-00001` — список заявок CRM должен содержать поля «Дата» (формат ДД.ММ.ГГГГ ЧЧ.ММ.СС), «Номер» (уникальный), «Отправитель», «Тема». Конкретно и проверяемо, хотя и не атомарно.
- Обработка недопустимого ввода: `7-1-BF-00025` — если данные введены некорректно, система должна вывести сообщение об ошибке и указать на проблемные поля формы. По свойству полноты это хорошо (есть реакция на недопустимые входы), но привязано к «нажатию кнопки».
- Перекрёстная ссылка: `1-2-BF-00002` — «…персональную информацию пользователя (см. 1-4-BF-00001)…».
- Типично плохой: `0-1-A-00001` — «Необходимо хранить куки пользователей…» (реализация, да ещё и в мобильном приложении); `0-5-BB-00001` — таблица пользователей в БД должна содержать столбцы «логин», «электронная почта», … (это уже схема БД, уровень проектирования); `9-3-BB-00008` — «Должен быть реализован обработчик изменений в заявке…».
- **Комментариев** в СПТ нет совсем: ни столбца, ни пометок.
- **Трассировка** держится только на частях V-W в ID и на блоке «Входные данные» в начале подраздела (сценарии, «описание архитектуры системы», «План разработки ПО», «Стандарты на разработку требований к ПО»). Матрицы трассировки нет, хотя в плане верификации для неё заявлены Excel и Draw.io.

**Что хорошо:**
- У каждого требования уникальный ID, и при вставке их не перенумеровывали. Позже добавленные требования получили новые номера: в разделе 7 после 00006 идут 00024 и 00025. Это и есть «уникальный неизменный идентификатор» из гайда.
- Многие требования конкретны: поля, форматы дат, что считается результатом поиска («единственная заявка при успешном поиске»), статусы «принято» / «отклонено», кому и когда уходит письмо.
- Учтены негативные ветки: некорректные данные, отклонение заявки, повторное рассмотрение.
- В части подразделов указаны входные данные. Привычка правильная.

**Что слабо или противоречит гайду:**
- **Это скорее требования низкого уровня или описание проекта, чем ВУ.** Кнопки, радиогруппа, чекбоксы, pop-up, «в его начале справа указана усреднённая оценка», reCAPTCHA, куки, таблицы и столбцы БД, «обработчик», «база отклонённых заявок». Около трети требований (50 из 148) упоминают кнопки, окна, вкладки, чекбоксы, экран, куки или таблицы, ещё около 30 говорят про «базу данных», «сервер» или «обработчик». По гайду (и по конспекту) в требованиях высокого уровня реализации быть не должно.
- **Не требования, а описания.** 45 из 148 обходятся без «должен / должна / необходимо»: «Открывается окно…», «После открытия события есть кнопка…», «Отправка в список репортов CRM с полями…».
- **Неатомарность:** одно требование содержит список из 4–7 пунктов (поля форм; четыре функции чёрного списка в `10-2-BB-00008`).
- **Непроверяемые формулировки:** «лимит прогрузки» (какой?), «своевременная актуализация», «сортировка должна сохраняться временно и очищаться долгосрочно», «регулярно очищаемая база».
- **Несогласованность:**
  - дата то «ЧЧ.ММ.СС», то «ЧЧ:ММ:СС», а их же стандарт на SQL требует ISO 8601;
  - по системному требованию 0.6 вход идёт по почте и паролю, а по `0-6-BF-00001` по логину и паролю;
  - одинаковый текст классифицирован по-разному: `2-4-CBF-00014` и `3-4-BF-00014`;
  - в разделе основной ленты по ошибке скопировано про «персонализированную ленту» (`2-3-BF-00011`, `2-3-BB-00012`).
- **Избыточность.** Разделы 2 и 3 (основная и персонализированная лента) почти дословно повторяют друг друга: 36 требований там, где хватило бы общих.
- **Неполнота и потерянная трасса:**
  - сценарий 11 не покрыт вовсе;
  - варианты сортировки из 2.3 (по популярности, «я пойду», рейтингу) в требования к ПО не перешли;
  - ограничения на отзывы из 5.2 (только авторизованные, интерес больше одного раза, через N времени) потерялись;
  - и наоборот, появились функции без системного источника (опция «Отправить заявку на доп. рассмотрение» при регистрации организатора), и как производные они не помечены.
- **Нет структуры IEEE 830 из гайда:** введения, общего описания, внешних интерфейсов, нефункциональных требований. При этом их собственный стандарт требует «актуальные нефункциональные требования».
- **Входные данные** есть только в 6 подразделах из 11, причём в трёх из них указан не тот сценарий: регистрация организатора и отзывы ссылаются на «сценарии обработки репортов», регистрация менеджеров — на «модерирование заявок».
- **ID, которые ломают собственный формат:** `10-2-BXD-00010` (при X = B буквы Z быть не должно), `10-3-BF-000013` (шесть цифр), `0-2-А-00001` (кириллическая «А»), `2-2–CFB-00003` (длинное тире), странные `CFF` и `CXX` (связь frontend с frontend и внешнего сервиса с внешним).
- **Термины** из требований (репорт, теневой бан, CRM, организатор, главный менеджер) нигде не определены.

## 3. Подробно: План УК и План разработки, что перенять

### 3.1 План управления конфигурацией

#### Базовые версии

- **Зачем нужна БВ:** на неё ссылаются в ходе разработки, она считается эталоном на момент времени, по ней отслеживается версия документа.
- **Требования к БВ:** корректность (документ прошёл ревью до сборки) и версионность (у каждой БВ свой номер).
- **Жизненный цикл страницы Confluence:**
  1. автор правит страницу в рамках задачи;
  2. рассмотрение: корректность, соответствие задаче и проекту;
  3. страница признаётся «стабильной» и блокируется;
  4. если нужна правка, заводится отдельная задача, и у администратора Confluence просят разблокировку.
- **Перед сборкой:**
  - все нужные страницы заблокированы; если какая-то открыта, проверить, не в работе ли она по задаче текущего спринта, иначе идти к ответственному;
  - репозиторий БВ доступен, иначе сборку откладывают.
- **Сборка:** Настройки раздела → Manage space → Export space → PDF → пользовательский экспорт (выбрать разделы, «указать номера страниц») → Download PDF → переименовать по правилу `CSPT-{ДДММГГ}-{ЧЧММ}`.
- **Хранение:** отдельный GitLab-репозиторий, папка `documents`, ветка `main`.
  - Получить версию: открыть `documents`, взять файл с самым свежим «last update».
  - Загрузить версию: New branch с именем версии → Upload file → commit message «version {версия}» → Create merge request (Assignee — себя, Reviewer — администратор репозитория БВ) → после подтверждения Merge → версия оказывается в `main`.
- **Для кода** есть только общая фраза: любой коммит в GitLab «может быть выбран в качестве очередной базовой версии», версия растёт только вперёд, ветки позволяют откатиться. Конкретного правила (какой коммит или тег считается БВ кода, кто это решает) нет.

**Плюсы.** Пошагово, со скриншотами, с предусловиями. Правило «проверено → заморожено → правка только через новую задачу» по сути реализует КК1 из лекций. В основную ветку можно попасть только через MR с ревьюером.

**Минусы:**
- БВ одна на всё пространство (страница Confluence названа «составной частью базовой версии документа об организации разработки»). У нас 5 отдельных документов, у каждого должна быть своя версия.
- Правило имени расходится со скриншотами: в тексте «CSPT-121121-0815», а на картинках файлы «Документ v.2021.455.pdf» и ветка «v.2021.463». Преподаватель такое находит сразу.
- Версию выбирают по дате «last update», а не по номеру.
- В коде основная ветка называется `master`, в репозитории документов `main`.
- Нет БВ для кода, сборок и тестов.

#### Идентификация единиц конфигурации

| ЕК | Где | Идентификатор | Как версионируется |
|---|---|---|---|
| Задача | Jira | `{проект}-{номер}` (CSPT-17) + неуникальное название и тип: эпик, история, задача, подзадача, баг | история изменений задачи |
| Репозиторий | GitLab | уникальное имя | git: `master` — основная, `develop` — «подготовленное к релизу», от `develop` — ветки задач (имя «зачастую совпадает с названием задачи») |
| Merge request | GitLab | `{репозиторий}!{номер}` + неуникальное название | история обсуждений и коммитов |
| Страница Confluence | Confluence | полный путь от начала пространства | версия = вид страницы в момент блокировки |

Кроме того, в стандартах кодирования есть свои таблицы «Идентификация элементов конфигурации» для кода:
- Python: пакет, класс, функция — полный путь через точку от `data_science`;
- SQL-скрипт — путь от `sql`;
- frontend: `package.json`, `vue.config.js`, компоненты `.vue`, `.scss`, `App.vue`, `main.js`, `router.js`, статика — путь от `frontend`.

Это полезная мысль: правило именования элементов кода записано в стандарте, а план УК на него опирается.

**Чего нет в списке ЕК:** самих требований (системных и к ПО); планов и стандартов как отдельных документов (всё уходит одной выгрузкой); тест-кейсов и протоколов тестирования; протоколов ФИ; СП и ЗИ; сборок, исполняемого кода и релизов; среды (версий инструментов). Примеры репозитория и MR, судя по названиям (`go-events-atomhack-summer-2021`, `go-articles-sbercode-spring-2021`), взяты из других проектов лидера. В нашем плане примеры лучше брать из своего репозитория.

#### Инструменты

- **GitLab** — репозитории: рассказано про коммиты, ветки, откат.
- **Jira** — в списке подписана как «управление страницами». Это ошибка: ниже по тексту речь о задачах, канбан/скрам-досках и баг-трекинге.
- **Confluence** — редактор документов: версия фиксируется блокировкой страницы, экспорт в PDF даёт БВ.

Jenkins, тест-менеджер со схемы ЖЦ и Draw.io здесь не упомянуты, хотя это тоже среда, которую стоило бы держать под контролем.

#### Процесс изменений

Отдельного раздела нет, процесс собирается по кусочкам из разных мест:
1. Любая работа идёт через задачу в Jira. Когда ЕК готова к ФИ, задача переходит в РАССМОТРЕНИЕ. Нет замечаний — в ГОТОВО; есть замечания — обратно В РАБОТЕ, а протокол ФИ кладётся в комментарий к задаче (из плана верификации).
2. Код: MR из рабочей ветки, Assignee — автор, Reviewer — координатор ФИ. Замечания оставляют к конкретным строкам, запись о ФИ — на странице MR.
3. Документы: перед ФИ страницы блокируются, замечания оставляют комментариями. Прошли — страницы остаются заблокированными, не прошли — их разблокируют на правку.
4. Уже заблокированное меняется только через новую задачу и разблокировку у администратора.
5. Для ошибок есть тип задачи «Баг», а в плане верификации Jira заявлена как инструмент «управления запросами на изменение и сообщениями о проблемах».

**Не описано:**
- кто принимает решение по СП и как из него появляется ЗИ (по конспекту это делает группа управления изменениями);
- какие ЕК относятся к КК1, а какие к КК2 (по конспекту тесты — КК1, протокол тестирования — КК2);
- учёт состояния конфигурации, архив и резервные копии, выпуск;
- кто и при каких условиях сливает `develop` в `master`;
- как коммит и MR связываются с задачей (кроме «название ветки часто совпадает с задачей»).

#### Что перенять в наш План УК

- Уровень детализации «по кнопкам» со скриншотами: гайд требует именно этого.
- Определения БВ и ЕК и «требования к БВ» (прошла проверку, имеет номер).
- Таблицу ЕК «где хранится / как идентифицируется / как версионируется», только расширенную до всех наших ЕК: требования, 5 документов, код, тесты и протоколы, протоколы ФИ, issue (СП/ЗИ), MR, сборки и релизы, конфигурация CI.
- Шаблоны идентификаторов вида `{проект}-{номер}` и `{репо}!{номер}`.
- Правило «проверено → заморожено → изменить можно только через новую задачу (ЗИ)», то есть КК1.
- MR с назначенным ревьюером как единственный путь в основную ветку.
- Проверки перед сборкой БВ.
- **Доделать то, чего у них нет:**
  - КК1/КК2;
  - цикл «СП → решение → ЗИ → ветка → MR + ФИ → merge → новая БВ» с ответом на «кто, где, что делает»;
  - правила веток и merge в master;
  - БВ кода (по гайду в плане УК можно писать «последний коммит master»);
  - интеграцию: что из сборки и развёртывания находится под УК;
  - учёт состояния, архив, контроль среды;
  - одну схему имени версии, которой соответствуют и скриншоты.

### 3.2 План разработки

#### Модель жизненного цикла (схема, с. 94–95)

В тексте ЖЦ разделён на два блока: «первичная разработка» (бизнес-требования, требования к ПО, планирование) и «программная разработка» (циклы программирования, верификации, тестирования и «доставки продукта клиенту»). На схеме это выглядит так:

| № | Блок схемы (цвет) | Верификация (синие пузыри) | УК: где лежит результат (зелёные облака) |
|---|---|---|---|
| 1 | Начало разработки (жёлтый) | — | — |
| 2 | Формирование бизнес-требований (красный) | обсуждение, синхронизация требований с идеей | документы в Confluence |
| 3 | Планирование объёмов разработки (красный) | оценка объёмов работ, обсуждение необходимых шагов | документы в Confluence, задачи в Jira |
| 4 | Разработка требований к ПО. Формализация бизнес-требований (красный) | «оценка объёмов работ, обсуждение необходимых шагов» (дословно как в п. 3) | документы в Confluence |
| 5 | Проектирование программной составляющей (красный) | процесс ревью | документы в Confluence |
| 6 | «Процесс программной разработки» (серый ромб) → написание программной логики и создание автоматизированного тестового покрытия (оранжевые: необязательные, асинхронные) | — | — |
| 7 | «Процесс программной разработки» (серый ромб на выходе) | процесс ревью | код на GitLab, тест-кейсы в тест-менеджере |
| 8 | Ручное тестирование (красный) | верификация продукта относительно требований | — |
| 9 | Завершение цикла разработки (жёлтый) | — | — |

Фиолетовые стрелки показывают возвраты: от требований к ПО обратно к бизнес-требованиям, от проектирования к требованиям к ПО, после ревью кода к проектированию, после ручного тестирования снова в разработку, от конца цикла к новому проектированию (итерации). В легенде разобраны 7 цветов (жёлтый — начало и конец, красный — обязательные стадии, серый — обязательные с пропускаемыми частями, оранжевый — необязательные асинхронные, синий — верификация, зелёный — УК и сохранение артефактов, фиолетовый — циклы и резервные пути) и 3 вида связей (стрелка — переход в ЖЦ, линия с точками на концах — связь с УК, пунктир — связь с верификацией).

**Плюсы.** С одного взгляда видно, что на каждом этапе проверяется и где лежит результат. Итеративность и пути возврата нарисованы. Такую схему стоит повторить у себя.

**Минусы:**
- Этапы не совпадают с процессами DO-178: нет кодирования и интеграции как отдельных процессов, а планирование появляется только как «планирование объёмов».
- Нет блока интеграции, сборки или развёртывания, хотя в тексте упомянута «доставка продукта клиенту».
- Верификация требований подписана как «оценка объёмов работ» (копия с предыдущего блока), а ниже в тексте сказано, что требования проверяются формальной инспекцией.
- Процесса гарантии качества нет.

#### Использование Jira (с. 95–97)

- **Статусы:** К РАБОТЕ, НА УДЕРЖАНИИ, В РАБОТЕ, РАССМОТРЕНИЕ, ТРЕБУЕТ ТЕСТИРОВАНИЯ, ТЕСТИРОВАНИЕ, ГОТОВО. У каждого есть описание.
- **Переходы с описанием:** создание задачи, начало работы, досрочное закрытие (из-за неактуальности), рассмотрение (ревью), закрытие без тестирования (для задач без кода или полностью покрытых автотестами), требует доработок (из рассмотрения или тестирования), требует тестирования, тестирование (тестировщик взял задачу), на удержание.
- **Расхождения схемы и текста:** на схеме есть ещё «закрытие задачи» (ТЕСТИРОВАНИЕ → ГОТОВО) и «возобновление задачи» (НА УДЕРЖАНИИ → К РАБОТЕ), а в тексте их нет. По тексту «требует тестирования» ведёт из РАССМОТРЕНИЯ сразу в ТЕСТИРОВАНИЕ, а на схеме в ТРЕБУЕТ ТЕСТИРОВАНИЯ. Мелочь, но ровно такие расхождения преподаватель и ищет.

#### Процессы, входы и выходы

Подробно описан только **процесс разработки требований к ПО** (с. 97–99):

- **Окружение** (рис. 1, в стиле IDEF0). Входы: «входные данные» и «запросы на изменения». Управление: «стандарты, используемые при разработке требований». Механизм: «разработчик требований». Выходы: «спецификация программных требований» и «отчёты о дефектах во входных данных». Дальше СПТ уходит на формальную инспекцию (её механизмы — ведущий и инспекторы). ФИ возвращает в процесс «список несоответствий в программных требованиях» и выдаёт «изменение статуса спецификации».
- **Входные данные:** бизнес-, функциональные и пользовательские требования, архитектурные ограничения и описание программно-аппаратных интерфейсов, стандарты проекта (в том числе стандарт на требования). При повторном проходе к ним добавляются описания несоответствий, найденных в других процессах или заказчиком. В пояснении к рисунку упомянуты «спецификации системных требований и архитектуры».
- **Выходные данные:** СПТ и сообщения о проблемах. При этом «список выходных данных, места их хранения и дальнейшее предназначение определяются в стандартах проекта».
- **Условия начала** «определяются в стандартах проекта»; минимум — наличие хотя бы части входных данных.
- **Структура:** восемь видов деятельности.
  1. Выделить требования из входов, отделив функциональные от нефункциональных, бизнес-правил и предполагаемых решений.
  2. Разложить до нужной детализации.
  3. Распределить по компонентам.
  4. Согласовать приоритеты.
  5. Понять важность атрибутов качества.
  6. Найти пробелы и лишнее.
  7. Задокументировать.
  8. Утвердить.
- **Условия конца:** итерация заканчивается, когда разработчик решил, что документ готов к ФИ. Процесс повторяется, пока ФИ не подтвердит соответствие входам, а «таким образом» концом названо извещение руководителя проекта.
- **Роли:** разработчиком требований назначают «компетентных участников, хорошо знающих предметную область».

**Плюсы.** Шаблон описания процесса правильный (окружение, входы, выходы, начало, структура, конец, роли), гайд ждёт ровно его в стандарте на требования. Нарисована петля через ФИ. ЗИ учтён как вход.

**Минусы:**
- Остальные процессы (планирование, проектирование, кодирование, интеграция) так не описаны вовсе. Гайд и билеты требуют входы и выходы каждого процесса.
- Отсылки «определяются в стандартах проекта» ведут в пустоту: в стандарте на требования ни условий начала, ни списка выходов нет.
- Упомянут стандарт проекта «Формальные инспекции», которого среди стандартов нет. Есть только раздел ФИ в плане верификации.
- В списке входов нет явно ни «системных требований», ни «плана разработки», хотя сама СПТ указывает план разработки среди своих входов.
- Конец процесса сформулирован двусмысленно: ФИ пройдена или руководитель извещён?
- Восемь видов деятельности остаются общими словами, без привязки к своим артефактам и инструментам.

#### Роли (1.5.2, с. 91–93)

Работа поделена на «направления», у каждого обязанности и ответственные:
- **управление командой** — Мардер: планирование, декомпозиция, спринты, распределение задач, отчёты;
- **документооборот и стандартизация** — семь человек: планы, стандарты, Confluence;
- **backend** — Чистов, Тихонов: архитектура, микросервисы, схемы БД, код, автотесты, код-ревью;
- **frontend** — Пак, Воронин: макеты, код, интеграционные тесты без серверной части, код-ревью;
- **математическая модель** — Арсентьев;
- **функциональное и регрессионное тестирование** — Морозевич: тест-кейсы и прогон;
- **средства поддержки разработки и администрирование** — Мардер, Тихонов: требования к технологиям, CI/CD, подготовка к релизу.

**Минусы:**
- Роли поделены по технологиям, а не по процессам. Нет ролей «разработчик требований», «проектировщик», «программист», «интегратор», «верификатор / инспектор», «ведущий ФИ», «ответственный за УК».
- У аналитика (Кузьмин) нет ни одного направления.
- Администратор Confluence и администратор репозитория БВ из плана УК не названы по именам.
- Независимость проверяющих оговорена только в плане верификации.

**Глоссарий процессных терминов** (1.5.1): задача, спринт, backend, frontend, автотест, деплой, релиз, СУБД, CI, CD (одиннадцатая строка пустая). Держать процессные термины отдельно от предметных — хорошая идея.

- Таблицу ответственности с именами, но переделанную под роли процессов.
- Отдельный глоссарий процессных терминов.

## 4. Есть ли шаг интеграции

**Нет.** В модели ЖЦ после ревью кода сразу идут «ручное тестирование» и «завершение цикла». Отдельного процесса интеграции нет ни в плане разработки, ни в плане УК.

Что встречается «около» интеграции:
- **глоссарий:** «деплой», «релиз», CI («процесс непрерывного автоматизированного анализа написанного кода»), CD («автоматизированное развёртывание всех изменений в коде на тестовой среде»);
- **ответственность:** «разработка и поддержка инструментов CI/CD» и «подготовка приложений к релизу» (Мардер, Тихонов);
- **план УК:** ветка `develop` хранит «версии репозитория, подготовленные к релизу», но как и кем они попадают в `master`, не сказано;
- **план верификации:**
  - Jenkins — «среда непрерывной интеграции / непрерывной доставки, используемая для прогона тестов»;
  - интеграционное тестирование проверяет взаимодействие двух и более сервисов, сценарии трассируются на системные требования;
  - ручной вариант — на тестовом стенде с конфигурацией, «схожей с боевой»; автоматизированный — на Python (requests, selenium, psycopg2/PyMySQL, pytest);
- **текст ЖЦ:** «доставка продукта клиенту», но на схеме ей не соответствует ни один блок.

Выходит, интеграцию подменили интеграционным тестированием, а это верификация, не интеграция.

**Что такое интеграция по курсу** (конспект, раздел «Процесс интеграции»):
- интеграция ПО — получение исполняемого объектного кода из исходного (компиляция и компоновка) и компонента параметрических данных;
- интеграция ПО и аппаратуры — загрузка исполняемого кода в целевой вычислитель;
- вход — результат кодирования (исходный код, параметры сборки, описание проекта);
- выход — исполняемый код, протокол сборки, командные файлы сборки, протокол загрузки;
- процедура загрузки описывается в плане разработки, контроль целостности загруженного кода — в плане УК.

**Как это может выглядеть у нас** (это наше предложение, в примере такого нет). Для «Системы автоматизации управления ЖЦ релиза ПО» интеграция — это:
- сборка артефактов из коммита или тега master в CI; скрипты сборки и их параметры находятся под УК;
- публикация артефакта с номером версии;
- развёртывание на стенд (наш аналог «загрузки в целевую среду») с протоколом;
- проверка, что развёрнута именно нужная версия и она цела.

В плане разработки это описывается как процесс (входы, выходы, кто, где), в плане УК — какие из этих вещей являются ЕК, как идентифицируется сборка, где лежат протоколы.

Отдельная засада нашей темы: «релиз» у нас одновременно сущность предметной области (то, чем управляет система) и наш собственный процесс выпуска. В глоссарии эти значения стоит развести.

## 5. Что из примера брать, а что не брать

### Брать

1. **Нумерацию системных сценариев и шагов и «говорящий» ID требований к ПО**, который ссылается на системный уровень (идея `V-W-…`). Только кодировать в нём не frontend/backend, а подсистему или функциональную область системного уровня. И записать в стандарте, что номер никогда не используется повторно.
2. **Правило неизменных ID:** новое требование получает новый номер, старые не перенумеровываются.
3. **Блок «Входные данные»** в начале каждого раздела СПТ, причём правильный и в каждом разделе.
4. **Конкретику, уместную на уровне ВУ:** перечни данных, форматы (дата одна на весь проект), что считается результатом поиска или фильтра, реакция на недопустимый ввод.
5. **Анализ предметной области** (участники → потребности → процессы → потоки информации) как фундамент для системных требований.
6. **Комментарии отдельно от требования** (столбец или блок «Комментарий»), но только справочные.
7. **Из плана УК:** детализацию по шагам со скриншотами; определения БВ и ЕК; таблицу ЕК с шаблонами ID; правило «проверено → заблокировано → правка только через новую задачу»; MR с ревьюером; проверки перед сборкой БВ; идею описывать правила именования элементов кода в стандартах.
8. **Из плана разработки:** схему ЖЦ с легендой «этап — верификация — хранение»; шаблон описания процесса с рисунком окружения; workflow задач со статусами; таблицу ответственности с именами; отдельный глоссарий процессных терминов.
9. **Связку статусов задач с ФИ** (РАССМОТРЕНИЕ → ГОТОВО или обратно В РАБОТЕ, протокол ФИ в комментарии). Пригодится и в плане УК, и в плане разработки.

### Не брать

1. Системные требования в виде «Действие → Результат» с UI (кнопки, pop-up, чекбоксы, звёздочки, «как на AliExpress»). У нас каждое требование звучит как «Система должна…», атомарно и без реализации.
2. Неформальные комментарии, в которых висят нерешённые варианты и спрятаны бизнес-правила.
3. Пустые разделы и скрытые TBD («N промежуток», «определённый интервал», «лимит прогрузки»). Либо конкретное значение, либо TBD с причиной и условием снятия.
4. UI и реализацию в требованиях к ПО: кнопки, радиогруппы, reCAPTCHA, куки, таблицы и столбцы БД, «должен быть реализован обработчик», «база отклонённых заявок». Это проектирование и требования низкого уровня.
5. Требования без «должен» («Открывается окно…») и требования-списки на 5–7 пунктов.
6. Почти одинаковые разделы-дубли (основная и персонализированная лента) вместо общих требований.
7. СПТ без введения, интерфейсов и нефункциональных требований. У нас структура IEEE 830 из гайда.
8. Стандарт на требования без «Способа описания требования» и без описания процесса. У нас стандарт строится по структуре гайда, и процесс описан в нём. Не отсылать «в стандарты проекта» туда, где этого нет, и не ссылаться на несуществующие стандарты.
9. ID, нарушающие собственный формат: лишние буквы, шесть цифр, кириллица, разные тире.
10. Модель ЖЦ без интеграции, роли по технологиям вместо ролей процессов, план разработки, где описан всего один процесс.
11. План УК без процесса СП/ЗИ, без КК1/КК2, без правил merge и без БВ для кода. Расхождения текста и скриншотов (имя версии), «Jira — управление страницами», пункты содержания, которых нет в документе.
12. Одну PDF-выгрузку всего пространства в роли базовой версии. У нас 5 документов, у каждого своя версия и БВ.
13. Примеры ЕК из чужих репозиториев.

### Чек-лист самопроверки (вытекает из ляпов примера)

- [ ] Каждое требование содержит «должна / должно», одно утверждение, без UI и названий технологий.
- [ ] Все термины из требований есть в глоссарии, роли называются одинаково во всех документах.
- [ ] Форматы (даты, ID) едины и совпадают с тем, что написано в стандартах.
- [ ] У каждого раздела СПТ указаны правильные входные данные.
- [ ] Каждая строка системных требований покрыта требованиями к ПО, и у каждого требования к ПО есть источник (матрица трассировки; производные требования помечены).
- [ ] Схемы и текст говорят одно и то же: статусы, переходы, имена версий.
- [ ] Оглавления совпадают с реальными разделами, пустых заголовков нет.
- [ ] Каждая ссылка вида «см. стандарт X» ведёт в существующий документ, где это действительно написано.
- [ ] Интеграция есть в модели ЖЦ, в плане разработки (как процесс со входами и выходами) и в плане УК.
