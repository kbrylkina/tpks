# AGENTS.md — инструкция для ИИ-агентов

Прочитай этот файл целиком, прежде чем что-то делать. Claude Code подключает его через `CLAUDE.md`, Codex, Cursor и другие агенты читают сами. Людям сюда не нужно: для них есть `ДЛЯ_ЛЮДЕЙ_TLDR.md`. Ссылка «§N» без имени файла — раздел этого файла, «`README.md` §N» — раздел README.

## 0. Главная команда: «Сделай задание на <дату>»

Люди из команды пишут тебе одну фразу: «Сделай задание на 17.10», «Сделай то, что сдаём в субботу», «Сделай План УК». Выполни её целиком по шагам ниже, не дожидаясь подробных указаний.

1. **Определи дату.** Пары по субботам: 03.10, 17.10, 31.10, 14.11, 28.11, 12.12.2026. Возьми дату из фразы. Если она не совпадает с парой, возьми ближайшую пару не раньше неё. Если даты нет («на субботу», «на следующую пару»), возьми ближайшую пару не раньше сегодняшнего дня. Если вместо даты назван документ, делай этот документ.
2. **Найди, что сдаём.** В таблице «План по датам» (§3) указано, что сдаём впервые, какие документы правим и какие промпты из `README.md` §5 нужны.
3. **Возьми документ себе.** Сначала `git pull --rebase --autostash`, чтобы видеть свежую версию. Открой `docs/README.md`. Если у документа в колонке «Кто» стоит другой человек, спроси, точно ли его трогать. Если на дату два новых документа, а человек не сказал какой, спроси, какой он берёт. Впиши в «Кто» имя человека (спроси, если не знаешь: логин из `git config` — не имя), поставь статус «в работе» и сразу сохрани `docs/README.md` по §7. Так два человека не возьмут один документ.
4. **Подготовься.** Прочитай этот файл целиком, `README.md` разделы 2–4 и всё, что для документа указано в §4. Если документ опирается на предыдущие (Требования к ПО — на `docs/01` и `docs/04`), прочитай и их. Если их ещё нет, скажи об этом и опирайся на черновики в `notes/`. Состав команды шапка подставляет сама из `docs/project.tex`. Роли людей для планов бери из таблицы «Команда» в `docs/README.md`; если там пусто, ставь `\clarify{…}`.
5. **Покажи план:** оглавление по `README.md` §4 и одна-две строки о каждом разделе верхнего уровня. Шапку, содержание и лист регистрации изменений шаблон делает сам (`README.md` §4.0). Дождись «ок». Если человек сразу сказал «без вопросов», не жди.
6. **Напиши документ** в LaTeX в его файл из §3 по промпту из `README.md` §5. Если файла ещё нет, скопируй `docs/00_example.tex` и замени `\doctitle`, `\docversion`, `\docdate`. Требования, термины, таблицы и `[уточнить]` оформляй как в этом примере (команды — в §9). Пиши целиком, а не заготовку: все разделы оглавления, все требования, все процессы. Новые термины добавь в `docs/glossary.tex` строкой `\term{…}{…}` по алфавиту.
7. **Сделай правки**, если они положены на эту дату. Замечания лежат в таблице «Замечания преподавателя» в `docs/README.md`. Исправь каждое, в колонке «Исправлено» поставь дату и добавь строку в лист изменений документа. Если замечаний нет (пара ещё не прошла или таблицу не заполнили), пропусти шаг и скажи об этом человеку. Правки не выдумывай.
8. **Проверь себя «как Козырев»** по промпту 5.8 из `README.md` и исправь найденное. То, что нельзя исправить без решения людей, пометь `\clarify{вопрос}` (в PDF это красное «[уточнить: …]»).
9. **Отредактируй язык.** Если тебе доступен скилл `redaktura` (в Claude Code — `redaktura-skills:redaktura`), прогони документ по промпту 5.9; если в репозитории есть `.agents/redpolitika.md`, следуй ему. Если скилла нет, сам убери канцелярит по правилам §6 и скажи человеку, как поставить скилл (`README.md` §6): ставит его человек.
10. **Собери PDF:** `./build.sh docs/<файл>.tex`. Ошибки сборки исправь сам и собирай снова, пока PDF не соберётся без ошибок. Нет LaTeX или не хватает пакета — поставь по §9. Открой PDF и проверь глазами шапку, таблицы и красные пометки.
11. **Обнови статус** в `docs/README.md` с датой: «на вычитке, <дата>», если прошёл шаги 6–10; «черновик, <дата>», если сделал не всё; «исправлен, <дата>» после правок. Остальные статусы ставят люди.
12. **Сохрани в git** прямо в `main`, без веток и pull request, по порядку из §7: свой `.tex`, свой PDF из `pdf/`, `docs/README.md` и `docs/glossary.tex`, если менял.
13. **Отчитайся коротко:** что сделано, хэш коммита, что человеку проверить глазами, список `[уточнить]` (найти их: `grep -n clarify docs/<файл>.tex`) и что сказать на паре о планах на следующий раз. `[уточнить]` раздели: вопросы к преподавателю допиши в `README.md` §8, вопросы к команде — туда же в «Решить внутри команды».

Если ты веб-чат без доступа к файлам, попроси приложить `AGENTS.md`, `README.md`, `docs/00_example.tex`, `docs/glossary.tex` и файлы из §4, а готовый `.tex` выдай целиком в ответе. Человек положит его в `docs/` и соберёт `./build.sh`. Без своего компьютера можно собрать в Overleaf: загрузить туда `docs/tpks.cls`, `project.tex`, `glossary.tex` и документ, в настройках выбрать компилятор XeLaTeX.

Другие короткие команды:
- «Запиши замечания с пары <дата>: …» — добавь по строке на замечание в таблицу «Замечания преподавателя» в `docs/README.md` и сохрани по §7. Исправишь их по шагу 7 к следующей паре.
- «Что сдаём на <дату>?» — ответь по «Плану по датам» (§3) и статусам в `docs/README.md`, ничего не меняя.

- **Курс:** «Технология программирования кибернетических систем: управление проектами» (ТПКС), преподаватель Козырев Владимир Петрович. В основе курса авиационный стандарт DO-178B/C (русский перевод — КТ-178).

- **Тема команды:** «Система автоматизации управления жизненным циклом релиза ПО». Аналог — DPM из Sber Tech Platform V; его используем только как референс предметной области (см. §6).
- **Итог семестра:** 5 документов. Крайний срок — **12.12.2026 включительно**, но по плану всё сдаём к 28.11, а 12.12 — запас. Пары раз в две недели по субботам: 03.10, 17.10, 31.10, 14.11, 28.11, 12.12. План по датам — в §3.

## 6. Правила написания

**Требования**
- В каждом требовании есть «должна/должно». Требование описывает, ЧТО делает система, а не КАК.
- Требование проверяемое: есть критерий «пройдено / не пройдено».
- Одно требование — одно утверждение. Если в нём «и», проверь, не два ли это требования.
- Только положительная форма: вместо «не должна» пиши «должна не …».
- Никаких технологий и интерфейсных деталей в системных требованиях и в требованиях к ПО: без «кнопки», «окна», «PostgreSQL», «Kubernetes», «Jenkins». Внешнюю систему называй по функции: «внешняя система сборки», «хранилище дистрибутивов».
- У каждого требования уникальный неизменяемый ID. Требование к ПО ссылается на своё системное требование, кроме производных (их помечаем как производные).
- Без TBD. Если без него не обойтись, напиши причину и условие, при котором TBD снимается.

**Процессы (в планах и стандарте)**
- Процессов 9, интеграция — отдельный процесс. Без интеграции преподаватель документ не примет.
- У каждого процесса указаны входы, выходы, критерий начала, критерий окончания и роли.
- Входы и выходы разработки требований к ПО бери ровно со слайда 18 (`notes/05` §3.2).

**Термины**
- Основная ветка в наших документах — `main`, не master. У прошлой команды [Эл] в одном плане было то main, то master.
- Каждый термин и каждое сокращение определены в документе. Общий список ведём в `docs/glossary.tex`, и во всех пяти документах термины одинаковые: терминологический конфликт — тоже ошибка.

**Язык**
- Пиши как человек: коротко, без канцелярита и «нейросетевых» оборотов. Лучшая из прошлых команд советует вообще не генерировать текст нейросетью, поэтому сгенерированное должно читаться как написанное студентом по шаблону.
- После черновика прогоняй текст через скилл `redaktura` из [redaktura-skills](https://github.com/N1arko/redaktura-skills) (как установить — в `README.md`).

**Копирование**
- Документация DPM Platform V запрещает модификацию и воспроизведение. Бери оттуда только идеи и термины предметной области и пиши своими словами, урезая под студенческий проект. **PDF и страницы DPM в репозиторий не клади**, только ссылки (`README.md` раздел 2).
- Сокращения не путай: «КТ» — это КТ-178, поэтому контрольная точка качества — «КТК». ЕК, ЗИ, СП и «базовая версия» — термины Плана УК, в описании продукта их не используй.
- Работы прошлых команд — образцы структуры. Текст не копируй дословно, а адаптируй под нашу тему.

**Если не уверен**
- Не выдумывай требования преподавателя. Спорное помечай `[уточнить]` и добавляй в раздел «Открытые вопросы» в `README.md`.

## 7. Работа с репозиторием

- Репозиторий публичный: https://github.com/kbrylkina/tpks. Читать может любой, коммитить — только соавторы (Collaborators). Ветка одна — `main`. Веток и pull request не делаем: каждый соавтор коммитит прямо в `main`.
- **Как сохранять работу:**
  1. Перед началом: `git pull --rebase --autostash`.
  2. Добавляй только свои файлы, например `git add docs/02_scm_plan.tex pdf/02_scm_plan.pdf docs/README.md docs/glossary.tex`. Не `git add -A`. PDF чужого документа не пересобирай и не коммить.
  3. `git commit -m "<что сделано>"` — коротко и по-русски: «План УК ПО v1», «Системные требования: правки после 03.10».
  4. `git pull --rebase --autostash`, потом `git push`. Если push отклонён, потому что кто-то успел раньше, повтори этот пункт.
- **Конфликт при pull.** В общих таблицах (`docs/README.md`, `docs/glossary.tex`) оставь строки обеих сторон. В чужом документе ничего не решай сам: покажи конфликт человеку.
- **Нельзя:** `git push --force`, `git reset --hard`, переписывать уже запушенные коммиты. Так стирается чужая работа. Свой неудачный коммит отменяй через `git revert <коммит>`.
- **Push не проходит** («Permission denied», 403 или git просит логин): человек ещё не соавтор или не вошёл в GitHub на этом компьютере. Пусть пришлёт владельцу свой логин GitHub и примет приглашение (придёт на почту или по ссылке https://github.com/kbrylkina/tpks/invitations). Войти проще всего через GitHub CLI: `gh auth login` (в Claude Code — `! gh auth login`). Сам ты этого не сделаешь: вход интерактивный.
- Это порядок работы над нашими документами. План УК ПО описывает другое: как разрабатывается сам «Диспетчер релизов» (ветки, pull request, СП и ЗИ, `README.md` §4.2). Наш упрощённый порядок в план не переноси.
- `materials/` не меняем. В `notes/` дописываем новое, только указывая источник.
- Нашёл новый материал — положи его в `materials/`, сделай рядом `.txt` и добавь строку в реестр в `README.md`. Исключение — документация СберТеха: только ссылка.
- После изменений обнови статус в `docs/README.md`.

## 8. Чего не делать

- Не читать PDF целиком, если есть `.txt` и выжимка в `notes/`.
- Не тащить в требования реализацию, интерфейс и технологии.
- Не терять интеграцию и входы/выходы процессов: на этом прошлые команды теряли больше всего баллов.
- Не копировать дословно документацию СберТеха и чужие работы.

## 9. LaTeX и сборка

Каждый документ — файл `docs/0N_<имя>.tex`. Оформление целиком в `docs/tpks.cls`: в документах не настраивай шрифты, поля и пакеты.

**Команды шаблона** (образец всех — `docs/00_example.tex`)

| Команда | Что делает |
|---|---|
| `\doctitle{…}`, `\docversion{N}`, `\docdate{ДД.ММ.ГГГГ}` | данные документа, до `\begin{document}` |
| `\docauthors{…}` | необязательно: авторы вместо всей команды |
| `\makeheader` | шапка (проект и команда из `project.tex`) и содержание |
| `\begin{req}{SYS_04_02}{1} … \end{req}` | требование: ID по `README.md` §4.6 и версия. Повтор ID или ID не по схеме — ошибка сборки |
| `\reqsource{…}`, `\reqverify{…}`, `\reqnote{…}` | внутри `req`: источник, способ проверки, комментарий |
| `\reqref{SYS_04_02}` | ссылка на требование |
| `\printterms{ЕК, СП}`, `\printallterms` | определения из `docs/glossary.tex` |
| `\clarify{вопрос}` | красное «[уточнить: вопрос]» |
| `\begin{tabl}{\|l\|L\|}{Подпись}[tab:метка]{заголовки} … \end{tabl}` | таблица на всю ширину; `L` — колонка с переносом текста |
| `\begin{changelog} \change{версия}{дата}{что}{кто}{основание} \end{changelog}` | лист регистрации изменений, всегда в конце |
| `\printteam` | таблица состава команды |

**Как писать текст.** Абзацы разделяй пустой строкой. `_` пиши как есть (`SYS_04_02`). Символы `# % & $ { }` экранируй: `\# \% \& \$ \{ \}`. Кавычки «ёлочки», тире «—», диапазон «--». Картинки клади в `docs/img/` и вставляй `\includegraphics`.

**Сборка.** `./build.sh docs/02_scm_plan.tex` собирает один документ, `./build.sh` — все. Готовый PDF появляется в `pdf/`, логи — в `docs/build/` (их не коммитим). Скрипт сам выбирает движок: `latexmk` (если есть и он, и `xelatex`, и `perl`), иначе `xelatex` напрямую, иначе Tectonic. Выбрать вручную: `ENGINE=tectonic ./build.sh …` (также `latexmk`, `xelatex`). На Windows запускай из Git Bash (ставится вместе с Git).

**Ошибка сборки.** Скрипт печатает строку вида `./02_scm_plan.tex:57: …` — исправь эту строку и собери снова. Если не хватает пакета, скрипт подскажет команду установки.

**Нет LaTeX — поставь сам.** Проверка: `command -v latexmk xelatex tectonic`.

| Система | Рекомендуем | Другие варианты |
|---|---|---|
| macOS, M1–M4 | `brew install tectonic` — без пароля, пакеты докачивает сам | полный LaTeX: `brew install --cask mactex-no-gui` (около 5 ГБ); меньше: `brew install --cask basictex`, затем `sudo tlmgr update --self && sudo tlmgr install latexmk polyglossia titlesec xltabular enumitem caption collection-langcyrillic` |
| macOS Intel или без Homebrew | `curl --proto '=https' --tlsv1.2 -fsSL https://drop-sh.fullyjustified.net \| sh`, затем `mkdir -p ~/.local/bin && mv tectonic ~/.local/bin/` и добавь `~/.local/bin` в `PATH` (brew на Intel собирает Tectonic из исходников — долго) | MacTeX или BasicTeX, как выше |
| Windows | MiKTeX: `winget install MiKTeX.MiKTeX`, затем `initexmf --set-config-value=[MPM]AutoInstall=1` (пакеты будут ставиться сами без вопросов) и открой Git Bash заново | `scoop install tectonic`; если он не найдёт Times New Roman, шаблон возьмёт CMU Serif. В winget Tectonic нет |
| Linux | тот же curl-скрипт, что для macOS Intel; Arch: `sudo pacman -S tectonic` | Ubuntu/Debian: `sudo apt install texlive-xetex texlive-latex-extra texlive-lang-cyrillic latexmk fonts-liberation` |

Команды с `sudo` и установщики с паролем запускает человек: попроси его ввести команду через `! …` в Claude Code. Первая сборка через Tectonic качает пакеты 1–3 минуты, дальше быстро.

Не хватает пакета в TeX Live или MacTeX: `sudo tlmgr install <пакет>`. Если нужен пароль, а человека рядом нет, собери через Tectonic. Нет шрифта Times New Roman — шаблон сам подставит Liberation Serif или CMU Serif; скажи об этом человеку.
